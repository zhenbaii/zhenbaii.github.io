中断线程化是Linux内核中的一种中断处理机制：把中断处理中比较耗时、可能睡眠的部分，从硬中断上下文搬到专门的内核线程中执行。

其核心思想是：
-  硬中断上下文只处理最紧急，最短的事务：判断是不是自己的中断、应答/清中断、记录状态。
-  耗时处理单独创建一个内核线程处理，这个线程可以睡眠，持锁，被调度器调度。

### 中断线程的创建流程

在Linux中，驱动编写者可以通过`request_threaded_irq(handler, thread_fn, ...)`方法来注册一个中断线程。这个函数的接口是：
```
int request_threaded_irq(unsigned int irq,
                         irq_handler_t handler,      // primary handler
                         irq_handler_t thread_fn,    // threaded handler
                         unsigned long flags,
                         const char *name,
                         void *dev);
```

其中，`handler`就是所谓的硬中断上下文，不可睡眠，不可阻塞，必须快速完成后返回; 而`thread_fn`就是驱动编写者可以主动传入的一个函数，这个函数通常承担耗时较长，可以睡眠阻塞调度的任务。

上述接口内部会做一些判断后，调用`kthread_create`接口。通过查阅源码，我们可以看到创建过程：
```c
/* kernel/irq/manage.c — setup_irq_thread() */
t = kthread_create(irq_thread, new, "irq/%d-%s", irq, new->name);
new->thread = get_task_struct(t);
```

`kthread_create`实际上是一个宏:
```c
#define kthread_create(threadfn, data, namefmt, arg...) \
    kthread_create_on_node(threadfn, data, NUMA_NO_NODE, namefmt, ##arg)
```

对于宏背后的函数，我们可以不用过多了解，我们主要聚焦宏的参数的含义：

|参数|说明|
|---|---|
|`threadfn`|线程启动后要执行的函数，原型为 `int (*)(void *data)`。|
|`data`|传递给 `threadfn` 的参数指针，可为 `NULL`。|
|`namefmt, ...`|线程名的 `printf` 风格格式串，例如 `"irq/%d-%s"`。|

到这里我们就可以发现，**无论是什么设备注册的中断线程，大家统一都运行同一个线程函数`irq_thread`，这个函数作为公用的统一的入口函数**。那这就引出了一个问题：不同的中断线程所执行的任务应当是不同的，内核怎么做到在同一个`irq_thread`线程函数下执行不同的实际任务呢？ 我们可以来看看`irq_thread`的定义：
```c
static int irq_thread(void *data)
{
    struct callback_head on_exit_work;
    struct irqaction *action = data;
    struct irq_desc *desc = irq_to_desc(action->irq);
    irqreturn_t (*handler_fn)(struct irq_desc *desc, struct irqaction *action);

    if (force_irqthreads && test_bit(IRQTF_FORCED_THREAD, &action->thread_flags))
        handler_fn = irq_forced_thread_fn;
    else
        handler_fn = irq_thread_fn;

    init_task_work(&on_exit_work, irq_thread_dtor);
    task_work_add(current, &on_exit_work, false);

    irq_thread_check_affinity(desc, action);

    while (!irq_wait_for_interrupt(action)) {
        irqreturn_t action_ret;

        irq_thread_check_affinity(desc, action);

        action_ret = handler_fn(desc, action);
        if (action_ret == IRQ_WAKE_THREAD)
            irq_wake_secondary(desc, action);

        wake_threads_waitq(desc);
    }

    task_work_cancel(current, irq_thread_dtor);
    return 0;
}
```

其中很大一部分都是一些条件判断，以及CPU亲和性的处理。我们抛开这些噪音，这个函数最核心的思想就是下面这几行代码：
```c
static int irq_thread(void *data)
{
    struct irqaction *action = data;
    // 循环，直到有人请求停止这个线程
    while (!irq_wait_for_interrupt(action)) {
        // 执行用户注册的 thread_fn
        action->thread_fn(action->irq, action->dev_id);
    }
    return 0;
}
```

`irq_wait_for_interrupt(action)`是整个循环的关键，他在内部会去检查`action`的某个标志位，如果不满足要求，就会一直睡眠在这里。这个函数的行为可以概括如下：

|情况|行为|返回值|
|---|---|---|
|没有活要干|**主动 `schedule()` 让出 CPU，进入睡眠**|被唤醒后才返回|
|被中断唤醒，且有活|清除标志，立刻返回|`0`|
|收到停止请求|直接返回|非零|

整个流程可以概括成：
```
第一次进来：
  irq_wait_for_interrupt() 被调用
    → 没活，schedule() 睡觉
    → 【线程停在这里，不占 CPU】

硬中断到来，__irq_wake_thread() 唤醒它：
  irq_wait_for_interrupt() 从 schedule() 返回
    → 检查标志，发现 IRQTF_RUNTHREAD 被置位
    → test_and_clear_bit() 清掉
    → 返回 0
  while 条件 !0 = true → 进入循环体
    → 执行 thread_fn()

执行完回到 while 条件：
  irq_wait_for_interrupt() 再次被调用
    → 没活，schedule() 又睡觉
    → 【线程再次停在这里】

下一次中断到来：
  → 重复上述过程
```

外部中断在上半部返回`IRQ_WAKE_THREAD`, 之后，在OS通用中断处理层中，看到handler返回这个标志位，表示需要去唤醒对应的线程，于是会执行一个`__irq_wake_thread()`方法：
```c
if (action->handler(irq, dev_id) == IRQ_WAKE_THREAD)
    __irq_wake_thread(desc, action);
    
void __irq_wake_thread(struct irq_desc *desc, struct irqaction *action)
{
    // 1. 置位标志：告诉线程“有活”
    if (test_and_set_bit(IRQTF_RUNTHREAD, &action->thread_flags))
        return;

    // 2. kick：把线程从睡眠中唤醒
    wake_up_process(action->thread);
}
```

可以看到，其实这个函数就是做了两件事情：置位`irqaction`的标志位，用来告诉中断线程来活了，然后主动唤醒该线程，使得其可以醒来检查标志位并执行任务。


到这里，我们对整个中断线程的创建过程就比较清楚了。其实主要就是要抓住以下几点：
-  中断线程的入口函数永远是一个固定的`irq_thread`, 而不是驱动编写者提供的`thread_fn`
-  或者说，`irq_thread`是所有中断线程的公用母本函数
-  中断线程的生命周期和设备一致，设备卸载时，线程也要随之消亡
