第一次看到`TranslationBlock`时，很容易把它理解成“装着一段host机器码的结构体”。这个说法不算错，但只说到了结果。对QEMU来说，一块TB既要保存翻译产物，也要回答另外三个问题：

- 这块代码是在什么guest状态下翻译出来的？
- guest代码所在的物理页发生变化时，怎样找到并作废它？
- 它已经和哪些前后TB链接起来了，失效时怎样拆开这些链接？

所以，`TranslationBlock`更像TCG缓存中的一个完整节点。host机器码只是它保存的内容之一。

理解这个结构体之前，还要认识一个更小的结构体`TCGTBCPUState`。二者的关系可以先记成：

> `TCGTBCPUState`描述“我现在想找一块什么样的TB”，`TranslationBlock`则是缓存中真正存在的那块TB。

前者是查找条件，后者是缓存对象。

相关定义分别位于：

- `include/accel/tcg/tb-cpu-state.h`：`TCGTBCPUState`
- `include/exec/translation-block.h`：`TranslationBlock`

TB如何查找、链接和失效的完整过程见[TB的查找、链接与失效](/虚拟化/2026/09/20/TB的查找-链接与失效/)；这一篇只围绕结构体本身展开。

### TB的“身份证”

`TCGTBCPUState`只有四个字段：

```c
typedef struct TCGTBCPUState {
    vaddr pc;
    uint32_t flags;
    uint32_t cflags;
    uint64_t cs_base;
} TCGTBCPUState;
```

`TranslationBlock`的开头也保存了同名字段。生成新TB时，QEMU会把这份查找条件抄进TB；以后再遇到相同执行环境，就可以拿当前状态与它比较。

#### 源码中的`TranslationBlock`定义

下面是`qemu-camp-2026-k230/include/exec/translation-block.h`中的原始定义。`TranslationBlock`内部使用了`struct tb_tc`，所以也把它一并列在这里。先不用急着逐行理解，后文会按照查找条件、翻译产物、页跟踪和直接链接四部分分别解释。

```c
struct tb_tc {
    const void *ptr;    /* pointer to the translated code */
    size_t size;
};

struct TranslationBlock {
    /*
     * Guest PC corresponding to this block.  This must be the true
     * virtual address.  Therefore e.g. x86 stores EIP + CS_BASE, and
     * targets like Arm, MIPS, HP-PA, which reuse low bits for ISA or
     * privilege, must store those bits elsewhere.
     *
     * If CF_PCREL, the opcodes for the TranslationBlock are written
     * such that the TB is associated only with the physical page and
     * may be run in any virtual address context.  In this case, PC
     * must always be taken from ENV in a target-specific manner.
     * Unwind information is taken as offsets from the page, to be
     * deposited into the "current" PC.
     */
    vaddr pc;

    /*
     * Target-specific data associated with the TranslationBlock, e.g.:
     * x86: the original user, the Code Segment virtual base,
     * arm: an extension of tb->flags,
     * s390x: instruction data for EXECUTE,
     * sparc: the next pc of the instruction queue (for delay slots).
     * riscv: an extension of tb->flags,
     */
    uint64_t cs_base;

    uint32_t flags; /* flags defining in which context the code was generated */
    uint32_t cflags;    /* compile flags */

/* Note that TCG_MAX_INSNS is 512; we validate this match elsewhere. */
#define CF_COUNT_MASK    0x000001ff
#define CF_NO_GOTO_TB    0x00000200 /* Do not chain with goto_tb */
#define CF_NO_GOTO_PTR   0x00000400 /* Do not chain with goto_ptr */
#define CF_SINGLE_STEP   0x00000800 /* gdbstub single-step in effect */
#define CF_MEMI_ONLY     0x00001000 /* Only instrument memory ops */
#define CF_USE_ICOUNT    0x00002000
#define CF_INVALID       0x00004000 /* TB is stale. Set with @jmp_lock held */
#define CF_PARALLEL      0x00008000 /* Generate code for a parallel context */
#define CF_NOIRQ         0x00010000 /* Generate an uninterruptible TB */
#define CF_PCREL         0x00020000 /* Opcodes in TB are PC-relative */
#define CF_BP_PAGE       0x00040000 /* Breakpoint present in code page */
#define CF_CLUSTER_MASK  0xff000000 /* Top 8 bits are cluster ID */
#define CF_CLUSTER_SHIFT 24

    /*
     * Above fields used for comparing
     */

    /* size of target code for this block (1 <= size <= TARGET_PAGE_SIZE) */
    uint16_t size;
    uint16_t icount;

    struct tb_tc tc;

    /*
     * Track tb_page_addr_t intervals that intersect this TB.
     * For user-only, the virtual addresses are always contiguous,
     * and we use a unified interval tree.  For system, we use a
     * linked list headed in each PageDesc.  Within the list, the lsb
     * of the previous pointer tells the index of page_next[], and the
     * list is protected by the PageDesc lock(s).
     */
#ifdef CONFIG_USER_ONLY
    IntervalTreeNode itree;
#else
    uintptr_t page_next[2];
    tb_page_addr_t page_addr[2];
#endif

    /* jmp_lock placed here to fill a 4-byte hole. Its documentation is below */
    QemuSpin jmp_lock;

    /* The following data are used to directly call another TB from
     * the code of this one. This can be done either by emitting direct or
     * indirect native jump instructions. These jumps are reset so that the TB
     * just continues its execution. The TB can be linked to another one by
     * setting one of the jump targets (or patching the jump instruction). Only
     * two of such jumps are supported.
     */
#define TB_JMP_OFFSET_INVALID 0xffff /* indicates no jump generated */
    uint16_t jmp_reset_offset[2]; /* offset of original jump target */
    uint16_t jmp_insn_offset[2];  /* offset of direct jump insn */
    uintptr_t jmp_target_addr[2]; /* target address */

    /*
     * Each TB has a NULL-terminated list (jmp_list_head) of incoming jumps.
     * Each TB can have two outgoing jumps, and therefore can participate
     * in two lists. The list entries are kept in jmp_list_next[2]. The least
     * significant bit (LSB) of the pointers in these lists is used to encode
     * which of the two list entries is to be used in the pointed TB.
     *
     * List traversals are protected by jmp_lock. The destination TB of each
     * outgoing jump is kept in jmp_dest[] so that the appropriate jmp_lock
     * can be acquired from any origin TB.
     *
     * jmp_dest[] are tagged pointers as well. The LSB is set when the TB is
     * being invalidated, so that no further outgoing jumps from it can be set.
     *
     * jmp_lock also protects the CF_INVALID cflag; a jump must not be chained
     * to a destination TB that has CF_INVALID set.
     */
    uintptr_t jmp_list_head;
    uintptr_t jmp_list_next[2];
    uintptr_t jmp_dest[2];
};
```

```text
当前CPU状态
    │
    │ get_tb_cpu_state()
    ▼
TCGTBCPUState                         TranslationBlock
┌─────────┐                           ┌─────────────────┐
│ pc      │ ───────查找、比较────────→ │ pc              │
│ flags   │ ───────查找、比较────────→ │ flags           │
│ cflags  │ ───────查找、比较────────→ │ cflags          │
│ cs_base │ ───────查找、比较────────→ │ cs_base         │
└─────────┘                           ├─────────────────┤
                                      │ host机器码       │
          没有命中时生成新TB ────────→ │ 页跟踪信息       │
                                      │ chaining信息     │
                                      └─────────────────┘
```

四个字段各自回答不同的问题：

|字段|含义|由谁填写|
|---|---|---|
|`pc`|这块TB从哪条guest指令开始|目标架构的`get_tb_cpu_state()`|
|`flags`|哪些guest CPU状态会改变翻译结果|目标架构的`get_tb_cpu_state()`|
|`cs_base`|架构附加信息；RISC-V用它保存`flags`放不下的状态|目标架构的`get_tb_cpu_state()`|
|`cflags`|本次翻译允许采用哪些TCG公共策略|TCG执行主循环|

这里有两个容易混淆的地方。

首先，`flags`并不等于全部CPU状态。它只保存“会改变翻译结果，而且希望在翻译期固定下来”的那部分状态。

其次，`cflags`虽然也参与TB匹配，却不是guest架构状态。它保存的是`CF_*`这类TCG编译约束，例如是否禁止chaining、是否启用icount、这块TB最多翻译多少条指令。RISC-V的`riscv_get_tb_cpu_state()`不会填写它，主循环会通过`curr_cflags()`或`cpu->cflags_next_tb`另外补上。

### 为什么不能只用PC查找TB

同一个guest地址上的机器码，在不同CPU状态下可能具有完全不同的语义。例如：

```asm
csrr t0, sstatus
```

如果当前处于S-mode，这条指令可以正常读取CSR；如果处于U-mode，它应该触发非法指令异常。因此，地址相同并不意味着能够复用同一份host代码。

RISC-V中常见的例子还有：

|需要进入`flags`或`cs_base`的状态|为什么会改变翻译结果|
|---|---|
|`PRIV`|决定CSR和特权指令是否合法|
|`XL`、`AXL`|决定整数运算宽度和访存地址宽度|
|`FS`、`VS`|决定浮点、向量指令能否执行|
|`MEM_IDX`|决定load/store使用哪套MMU上下文|
|`MISA_EXT`|决定某条扩展指令是否存在|
|`BIG_ENDIAN`|决定访存的字节序|

但下面这些状态通常不需要进入TB索引：

|不进入索引的状态|原因|
|---|---|
|通用寄存器当前值|`addi`的翻译方式不依赖`t0`此刻等于1还是100|
|绝大多数CSR的数值|运行时读取即可，不会让生成的IR换一种形状|
|中断pending状态|由TB入口检查和主循环处理，而不是靠另建TB表达|
|中断使能状态|解除中断屏蔽的指令需要主动退出TB，让主循环重新检查中断|
|`satp`的具体数值|system mode下TB按代码所在物理页管理；换页表时重新进行地址转换和TLB处理，而不是把整个`satp`塞进每块TB|

这里的判断标准不是“状态重不重要”，而是“这个状态变化后，原来生成的host代码是否还成立”。

### 真正查找时比了什么

哈希表慢路径会比较`flags`、`cflags`和`cs_base`。普通TB还要比较`pc`；开启`CF_PCREL`后，TB采用相对PC方式，可以不要求保存的`tb->pc`完全相等。system mode下还要核对guest代码第一页对应的RAM物理地址：

```c
if ((tb_cflags(tb) & CF_PCREL || tb->pc == desc->s.pc) &&
    tb_page_addr0(tb) == desc->page_addr0 &&
    tb->cs_base == desc->s.cs_base &&
    tb->flags == desc->s.flags &&
    tb_cflags(tb) == desc->s.cflags) {
    /* 命中 */
}
```

因此，把TB索引简单说成`pc + flags`只是概念上的简写。更完整的说法是：QEMU使用`pc、flags、cflags、cs_base`描述翻译环境，并在system mode下结合代码页的物理地址确认它是不是要找的TB。

### `TranslationBlock`还保存了什么

前面四个字段解决了“这是谁”的问题，剩下的字段则负责保存翻译结果以及TB之间的关系。按用途看，可以分为三组：

```text
TranslationBlock
├── 查找条件
│   └── pc、flags、cflags、cs_base
├── 翻译产物
│   └── size、icount、tc
├── 代码页跟踪
│   └── page_addr[2]、page_next[2]，或user mode的itree
└── 直接链接
    └── jmp_*、jmp_list_*、jmp_lock
```

#### guest原文与host译文

|字段|含义|
|---|---|
|`size`|这块TB覆盖了多少字节的guest代码，即`pc_next - pc_first`|
|`icount`|这块TB包含多少条guest指令，不是host指令数|
|`tc.ptr`|生成的host机器码入口，`cpu_tb_exec()`最终跳到这里|
|`tc.size`|这段host机器码的长度|

`size`和`icount`描述guest原文，`tc`描述host译文。二者不能混在一起：五条guest指令可能展开成许多条host指令，也可能因为优化只留下很短的一段代码。

QEMU还会利用`[tc.ptr, tc.ptr + tc.size)`判断某个host PC落在哪块TB中。host代码执行期间发生异常时，这是恢复guest现场的重要线索。

一块TB覆盖的guest代码长度至少为1字节，最多为`TARGET_PAGE_SIZE`，所以至多跨越两个相邻页面。

#### 代码页跟踪

system mode下，QEMU需要知道一块TB来自哪些RAM物理页。原因很直接：guest若修改了自己的代码，原来翻译出的host代码就失效了。

|字段|含义|
|---|---|
|`page_addr[0]`、`page_addr[1]`|guest代码所在的RAM物理页；第二项为`-1`表示没有跨页|
|`page_next[0]`、`page_next[1]`|把TB挂进对应物理页的TB链表|

`page_next`指针的最低位还编码了当前链接对应TB的第0页还是第1页。这样，一块物理页被写入时，QEMU就能沿链表找到所有依赖该页的TB并让它们失效。

user mode没有这套物理页链表，而是用`itree`区间树按照guest虚拟地址范围跟踪TB。

#### 两个直接跳转槽

对应前端生成的`goto_tb + exit_tb`。

|字段|含义|
|---|---|
|`jmp_insn_offset[n]`|第`n`个host跳转指令相对`tc.ptr`的偏移；patch代码时修改这里|
|`jmp_reset_offset[n]`|slot未绑定时应跳到的回退代码；`0xffff`表示该slot没有生成`goto_tb`|
|`jmp_target_addr[n]`|这个slot当前指向的host地址|

刚生成TB时，slot指向本TB内部的回退路径。这条路径会写好下一个guest PC，然后通过`exit_tb`回到主循环。第一次找到目标TB后，`tb_add_jump()`可以把slot直接改为`tb_next->tc.ptr`；以后执行到这里，就能从一块host代码直接跳进下一块host代码。

目标TB失效时，`tb_reset_jump()`再把slot恢复到`tc.ptr + jmp_reset_offset[n]`。因此，jump slot不是一条永远固定的跳转，而是一处可以在运行时接线和拆线的host代码位置。

#### 谁跳向了我

知道“本TB跳向谁”还不够。某块TB失效时，QEMU还必须找到所有指向它的前驱，否则前驱会继续跳进已经作废的host代码。

|字段|含义|
|---|---|
|`jmp_dest[n]`|本TB第`n`个出口当前链接到哪个TB；最低位还可表示目标正在失效|
|`jmp_list_head`|所有指向本TB的入边链表头；最低位编码来源使用的slot|
|`jmp_list_next[n]`|本TB作为一条入边时，在目标TB入边链表中的下一个节点|
|`jmp_lock`|保护链接关系以及`CF_INVALID`状态|

可以把这组字段想成一张双向维护的控制流图：jump slot是出边，`jmp_list_head`是入边。建立链接时两边都要登记，失效时才能把所有关联关系安全拆掉。

### `flags`为什么由目标架构自己定义

TCG公共代码只知道`flags`是一个`uint32_t`，并不知道某一位代表特权级还是端序。哪些CPU状态会改变翻译结果，只能由目标架构决定。例如x86会直接把自己的`hflags`放进来，RISC-V则定义了一套`TB_FLAGS`位域。

RISC-V相关代码主要分布在三个位置：

|环节|文件|作用|
|---|---|---|
|定义布局|`target/riscv/cpu.h`|用`FIELD(TB_FLAGS, ...)`和`FIELD(EXT_TB_FLAGS, ...)`声明位域|
|打包状态|`target/riscv/tcg/tcg-cpu.c`|`riscv_get_tb_cpu_state()`从`CPURISCVState`提取状态|
|翻译使用|`target/riscv/translate.c`|`riscv_tr_init_disas_context()`把位域拆进`DisasContext`|

`FIELD`只声明某段位域的位置和宽度，并不会自动修改任何结构体。真正写入和读取分别依靠`FIELD_DP32/64`与`FIELD_EX32/64`。

RISC-V要记录的状态超过了32位，因此它使用两块空间：

```text
tb->flags    ← TB_FLAGS，32 bit
tb->cs_base  ← EXT_TB_FLAGS，64 bit
```

`cs_base`这个名字来自x86代码段基址，但公共结构体并不规定它必须存段地址。在RISC-V中，它就是`flags`装不下时的扩展区域。因此，对RISC-V来说，**`flags + cs_base`合起来才是完整的架构相关翻译上下文。**

### RISC-V的TB flags布局

当前笔记所对应源码中的布局如下：

```text
flags (uint32)
  0–2   MEM_IDX
  3–4   FS
  5–6   VS
  7–9   LMUL
 10–12  SEW
 13     VL_EQ_VLMAX
 14     VILL
 15     VSTART_EQ_ZERO
 16–17  XL
 18–19  VTA / VMA
 20     ITRIGGER
 21     VIRT_ENABLED
 22–23  PRIV
 24–25  AXL
 26     FCFI_ENABLED
 27     FCFI_LP_EXPECTED
 28     BCFI_ENABLED
 29–30  PM_PMM
 31     PM_SIGNEXTEND

cs_base (uint64)
  0–31  MISA_EXT
 32     ALTFMT
 33     BIG_ENDIAN
```

下面不按bit顺序逐个背，而是按它们共同影响的翻译行为来看。

#### 特权级和访存环境

`PRIV`保存当前执行特权级，编码为`0=U、1=S、3=M`。翻译CSR、特权指令和异常行为时都需要它。

`MEM_IDX`选择load/store使用的软件TLB和MMU上下文，它并不是简单复制`PRIV`。例如，S-mode打开`SUM`后会使用`MMUIdx_S_SUM`；虚拟化场景还可能带上`MMU_2STAGE_BIT`。生成`qemu_ld/qemu_st`时，翻译器会把这个index一并写入访存操作。

`VIRT_ENABLED`表示当前是否运行在H扩展提供的VS/VU虚拟化环境。开启后，CSR视图、两阶段地址转换等行为都会改变。

#### 执行宽度和地址宽度

`XL`是当前特权级的有效XLEN，编码为`1=RV32、2=RV64、3=RV128`。它决定整数运算、立即数和移位等基础语义。

`AXL`是显式load/store使用的地址XLEN。通常它与`XL`相同；M-mode打开`MPRV`并借用较低特权级访存环境时，二者可以不同。具体推导过程见[RISC-V的XL与AXL](/虚拟化/2026/09/20/RISC-V的XL与AXL/)。

#### 浮点和向量状态

`FS`与`VS`来自`mstatus.FS/VS`，表示浮点或向量上下文当前是否可用：

|值|状态|对翻译的影响|
|---|---|---|
|0|`DISABLED`|相关指令应产生非法指令异常|
|1|`INITIAL`|扩展可用，第一次修改状态时需要标记为dirty|
|2|`CLEAN`|扩展可用，第一次写入时需要标记为dirty|
|3|`DIRTY`|上下文已经被修改，可以正常执行|

处于虚拟化环境时，QEMU还要结合HS层保存的FS/VS，取能够正确约束当前执行环境的结果，不能只看guest自己的状态。

向量翻译还会从`vtype`、`vl`和`vstart`中提取一小组状态：

|字段|含义|
|---|---|
|`SEW`|当前向量元素宽度|
|`LMUL`|寄存器分组倍率，包括分数LMUL，使用3位有符号编码|
|`VILL`|`vtype`是否合法；没有V扩展时也会置为1|
|`VTA`、`VMA`|tail和mask元素采用agnostic还是undisturbed策略|
|`VSTART_EQ_ZERO`|`vstart`是否为0，决定能否走整段向量快路径|
|`VL_EQ_VLMAX`|`vl`是否等于`vlmax`，并满足一次至少处理8字节的GVEC条件|

`vl`的完整数值没有直接塞进flags。翻译器真正需要的是若干能够选择快慢路径的性质，所以这里只记录`VL_EQ_VLMAX`这样的布尔结果。

旧版本源码曾在18–19位放置`PM_MASK_ENABLED/PM_BASE_ENABLED`，当前布局已经由`VTA/VMA`复用。阅读不同版本的QEMU时要以对应版本的`FIELD(TB_FLAGS, ...)`为准。

#### Pointer masking

Pointer masking允许软件把虚拟地址高位的一部分用作tag，真正访存前再裁掉这些位。

|字段|含义|
|---|---|
|`PM_PMM`|选择关闭、保留模式、`PMLEN=7`或`PMLEN=16`|
|`PM_SIGNEXTEND`|裁掉tag后，高位填0还是做符号扩展|

这两个字段会直接改变地址生成代码，所以必须成为TB查找条件。

#### 控制流完整性和调试

|字段|含义|
|---|---|
|`FCFI_ENABLED`|是否启用前向控制流完整性检查，间接跳转目标需要符合`lpad`要求|
|`FCFI_LP_EXPECTED`|这块TB的第一条指令是否被期待为`lpad`；它来自前一次`jalr`等操作留下的`env->elp`状态|
|`BCFI_ENABLED`|是否启用后向控制流完整性或shadow stack|
|`ITRIGGER`|是否存在需要逐指令检查的instruction trigger|

`FCFI_LP_EXPECTED`体现了为什么某些看似短暂的状态也要进入TB flags：即使guest PC相同，“这一条是否应该是`lpad`”不同，生成的检查代码也不同，必须使用两块TB。

#### `cs_base`中的扩展状态

|字段|含义|
|---|---|
|`MISA_EXT`|当前启用的ISA扩展；运行时可关闭的扩展会改变指令是否合法|
|`ALTFMT`|向量alternate format状态|
|`BIG_ENDIAN`|当前访存端序|

`MISA_EXT`本身就占32位，再加上`ALTFMT`与`BIG_ENDIAN`，自然无法继续塞进32位`flags`，所以这组状态被放进`cs_base`。

### 一块TB从查找到生成经历了什么

把前面的结构体和字段放回执行流程，就能看出每个字段是什么时候产生的。

```text
CPURISCVState
    │
    │ riscv_get_tb_cpu_state()
    │ 提取会影响翻译的guest状态
    ▼
TCGTBCPUState { pc, flags, cs_base }
    │
    │ cpu_exec_loop()补上cflags
    ▼
完整查找条件 { pc, flags, cflags, cs_base }
    │
    ├─ tb_lookup()命中
    │      └─ 直接执行已有TranslationBlock
    │
    └─ 没有命中
           │
           └─ tb_gen_code()
                  ├─ 把查找条件写入TranslationBlock
                  ├─ RISC-V前端把flags拆进DisasContext
                  └─ 按这份上下文生成TCG IR和host代码
```

#### 架构钩子是怎样接上的

RISC-V CPU初始化时会把`TCGCPUOps`挂到`CPUClass`：

```c
cc->tcg_ops = &riscv_tcg_ops;
```

`riscv_tcg_ops`中至少有两个与这条路线直接相关的钩子：

```c
const TCGCPUOps riscv_tcg_ops = {
    /* ... */
    .translate_code = riscv_translate_code,
    .get_tb_cpu_state = riscv_get_tb_cpu_state,
};
```

公共的`accel/tcg/`代码不需要知道RISC-V各个bit是什么意思，只需在查找前调用`get_tb_cpu_state`，在生成时调用`translate_code`。

#### 当前状态先被打包成查找条件

`cpu_exec_loop()`先从架构前端取得状态，再补上公共的`cflags`：

```c
TCGTBCPUState s = cpu->cc->tcg_ops->get_tb_cpu_state(cpu);
s.cflags = cpu->cflags_next_tb;

if (s.cflags == -1) {
    s.cflags = curr_cflags(cpu);
}

tb = tb_lookup(cpu, s);
if (tb == NULL) {
    tb = tb_gen_code(cpu, s);
}
```

RISC-V一侧则负责把CPU状态压进`flags`和`ext_flags`。下面只保留与主线有关的部分：

```c
// target/riscv/tcg/tcg_cpu.c@riscv_get_tb_cpu_state
flags = FIELD_DP32(flags, TB_FLAGS, PRIV, env->priv);
flags |= riscv_env_mmu_index(env, 0);
flags = FIELD_DP32(flags, TB_FLAGS, FS, fs);
flags = FIELD_DP32(flags, TB_FLAGS, VS, vs);
flags = FIELD_DP32(flags, TB_FLAGS, XL, env->xl);
flags = FIELD_DP32(flags, TB_FLAGS, AXL, cpu_address_xl(env));
flags = FIELD_DP32(flags, TB_FLAGS, PM_PMM, riscv_pm_get_pmm(env));
flags = FIELD_DP32(flags, TB_FLAGS, PM_SIGNEXTEND, pm_signext);

ext_flags = FIELD_DP64(ext_flags, EXT_TB_FLAGS,
                       MISA_EXT, env->misa_ext);
ext_flags = FIELD_DP64(ext_flags, EXT_TB_FLAGS, BIG_ENDIAN,
                       mo_endian_env(env) == MO_BE);

return (TCGTBCPUState) {
    .pc = env->xl == MXL_RV32 ? env->pc & UINT32_MAX : env->pc,
    .flags = flags,
    .cs_base = ext_flags,
};
```

向量、CFI和调试相关字段也在同一个函数中打包，只是这里没有全部展开。返回结构体没有显式初始化`cflags`，正是因为它属于TCG公共编译策略，稍后由主循环填写。

#### 没有命中时，查找条件才变成TB的一部分

`tb_gen_code()`建立新TB时，先保存这份查找条件：

```c
if (!(s.cflags & CF_PCREL)) {
    tb->pc = s.pc;
}
tb->cs_base = s.cs_base;
tb->flags = s.flags;
tb->cflags = s.cflags;
```

然后才调用目标架构的`translate_code`。这个顺序很重要：翻译器不是读取一份仍在变化的`CPURISCVState`来猜当前环境，而是以TB中已经固定的上下文为依据生成代码。

如果`tb_lookup()`命中了旧TB，就不会重新写这些字段。旧TB保存的始终是它当初生成时所依赖的状态。

#### 翻译器再把位域拆成容易使用的字段

进入RISC-V翻译器后，`riscv_tr_init_disas_context()`从TB取回这些状态：

```c
uint32_t tb_flags = ctx->base.tb->flags;
uint64_t ext_tb_flags = ctx->base.tb->cs_base;

ctx->priv = FIELD_EX32(tb_flags, TB_FLAGS, PRIV);
ctx->mem_idx = FIELD_EX32(tb_flags, TB_FLAGS, MEM_IDX);
ctx->mstatus_fs = FIELD_EX32(tb_flags, TB_FLAGS, FS);
ctx->mstatus_vs = FIELD_EX32(tb_flags, TB_FLAGS, VS);
ctx->virt_enabled = FIELD_EX32(tb_flags, TB_FLAGS, VIRT_ENABLED);
ctx->xl = FIELD_EX32(tb_flags, TB_FLAGS, XL);
ctx->address_xl = FIELD_EX32(tb_flags, TB_FLAGS, AXL);
```

后面的`trans_*`通常直接读取`ctx->priv`、`ctx->xl`或`ctx->mem_idx`，而不再反复解析原始`tb->flags`。例如翻译`csrr`时，`ctx->priv`不同就可能生成正常CSR访问，也可能直接生成非法指令异常。

### 最后把结构体重新拼起来

理解`TranslationBlock`不需要死记每一个字段，先记住它同时扮演四个角色：

```text
pc / flags / cs_base  → 说明这块host代码适用于哪种guest执行环境
cflags                → 说明这次翻译采用了哪些TCG公共约束
size / icount / tc     → 保存guest范围和真正生成的host代码
page_* / jmp_*         → 让TB能够被追踪、链接，并在失效时安全拆除
```

而一块RISC-V TB的状态来源可以压缩成下面这条线：

```text
CPURISCVState中的全部状态
        │
        │ 只挑出会改变翻译结果的部分
        ▼
TCGTBCPUState
        │
        ├─ 用于查找已有TB
        │
        └─ 未命中时写入TranslationBlock
                    │
                    ▼
          拆成DisasContext中的priv、xl、mem_idx等字段
                    │
                    ▼
              生成这块TB专属的host代码
```

所以，`TCGTBCPUState`不是另一种TB，`flags`也不是CPU状态的完整快照。它们共同完成的事情只有一个：为一块已经翻译好的host代码划清适用边界。
