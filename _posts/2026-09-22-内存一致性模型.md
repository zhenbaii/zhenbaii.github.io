缓存一致性协议解决的是：**对于同一个地址（实现中通常以 cache line 为粒度），各个 CPU 应当如何对它的写入顺序和当前值达成一致。**

内存一致性模型解决的是：**对于多个地址上的多次内存访问，其他 CPU 可以按照什么顺序观察到它们。**

例如：

```text
CPU 0
A = 1;
B = 1;
```

即使 `A` 和 `B` 各自都严格遵守 [缓存一致性协议——MESI](/操作系统/2026/08/28/缓存一致性协议-MESI/)，另一个 CPU 也不一定必须按照：

```text
A = 1
然后
B = 1
```

的顺序观察到它们。

原因不在于 MESI 失效，而在于真实处理器为了隐藏一致性事务的延迟，在协议路径上加入了 Store Buffer、Invalidate Queue、推测执行和各种消息队列。这些优化仍然必须维护单地址的一致性，但会改变不同地址的操作何时以及按照什么顺序对外可见。

本文的主线是教材中的两种典型结构：

```text
Store Buffer：推迟本核 store 真正进入一致性顺序的时间
Invalidate Queue：推迟本核真正处理远端失效请求的时间
```

随后再讨论它们与 MESI 瞬态、内存屏障之间的关系。

## 先看一条完整的写事务

假设 `X` 最初同时存在于三个 cache 中：

```text
CPU 0: X=0, S
CPU 1: X=0, S
CPU 2: X=0, S
```

CPU 0 执行 `X=1` 时，Store Buffer 和 Invalidate Queue 分别在事务的两端工作：

```text
CPU 0 流水线       CPU 0 Store Buffer      一致性系统       CPU 1/2 Invalidate Queue
     |                      |                    |                       |
执行 store X=1             |                    |                       |
     |--- 写入 entry ------>|                    |                       |
     |                      |--- Upgrade/GetM -->|                       |
     | 继续执行后续指令      |                    |--- Invalidate X ---->|
     | 不在这里等待 ACK      |                    |                       |
     |                      |                    |<-- 立即 ACK ----------|
     |                      |                    |    失效请求先入队       |
     |                      |                    |                       |
     |                      |      等待全部 ACK   |                       |
     |                      |<----- Grant M ------|                       |
     |                      |--- 将 X=1 写入 L1   |                       |
     |                      |--- 释放该 entry     |                       |
     |                      |                    |        后台处理队列 ---> S -> I
```

这幅图最重要的是区分“谁不等待”和“谁仍然必须等待”：

- **CPU 0 的执行流水线不必原地等待 ACK。** 它把 store 放入 Store Buffer 后，可以继续执行后续指令；
- **CPU 0 的一致性控制器仍然必须等待 ACK。** 在所有旧 sharer 的确认满足协议条件以前，它不能把这次 upgrade 当成已经完成；
- **CPU 1/2 不必完成全部本地失效动作再 ACK。** 教材中的 Invalidate Queue 允许它们先把请求入队、立即回复 ACK，稍后再处理；
- 如果 Store Buffer 满了、后续指令依赖尚未就绪的数据，或者遇到 fence，CPU 0 最终仍可能停下来。Store Buffer 只是把等待从“每条 store 都同步阻塞流水线”变成“后台异步推进”。

图中把 `S -> I` 画在最后只是为了突出解耦；queue entry 也可能很快被处理，在 writer 收齐全部 ACK 之前就已经完成实际失效。

“继续流水线”也不等于该 store 已经全局完成。处理器可以执行更年轻的指令；store 是否可以从 ROB 退休、何时可以释放 Store Buffer entry，仍由精确异常、提交规则和内存模型共同决定。

### ACK 到底是什么

ACK 是 coherence transaction 的响应消息。它告诉等待方：

> 这一个目标 sharer 已经按本协议对 invalidate 承担了责任，requester 可以把它计入本次权限回收的完成条件。

多个 sharer 时通常会有一个 ACK 计数：

```text
pendingAcks = sharer 数量

收到 CPU 1 ACK：pendingAcks--
收到 CPU 2 ACK：pendingAcks--

pendingAcks == 0
        ↓
upgrade 才能完成
```

ACK 可以直接发给 requester，也可以先发给 home/directory，由 home 在收齐后再发送 grant；这是具体协议选择。普通 clean sharer 的失效 ACK 通常只确认权限，若响应方持有最新脏数据，则还可能需要携带数据或使用另一种 data response。

在采用 Invalidate Queue 的教材模型中，ACK 确认的是“请求已经被可靠接收并进入协议处理”，不一定表示物理 cache tag 在回复那一拍已经写成 `I`。后文会继续区分“已 ACK”“已逻辑排序”和“已物理改写 tag”。

## Store Buffer

### Store Buffer 是什么

Store Buffer 是写请求一侧、位于执行流水线与 cache 之间的暂存结构。概念上，每个 entry 至少需要记录：

```text
地址
待写入的数据
字节有效掩码
相对于其他 store 的顺序
当前状态：等待地址/等待数据/申请权限/可以写入 cache
```

它的两项核心工作是：

1. **解耦流水线与一致性延迟**：流水线把 store 交给 buffer 后继续执行，由 buffer/cache controller 在后台申请 `M`；
2. **向本核转发尚未写入 cache 的数据**：避免后续同址 load 读回旧值。

它不是 MESI 状态，也不是网络中的 ACK 队列。一个 Store Buffer entry 可以存在于 `S -> M` 权限申请的整个过程中。

教材往往把这套功能统称为 Store Buffer；真实乱序核可能进一步拆成保存推测 store 的 Store Queue，以及保存已提交、等待写入 L1 的 write buffer。这个实现划分不改变这里讨论的协议作用：写方流水线与取得一致性写权限的过程被解耦。

### 为什么需要 Store Buffer

假设 CPU 0 当前以 `S` 状态持有 `X`，现在要执行：

```text
X = 1
```

它不能直接修改 cache line，因为其他 CPU 可能也持有 `S` 副本。完整过程至少包括：

```text
CPU 0 发出 Upgrade / GetM
        ↓
目录或总线向其他 sharer 发送 invalidate
        ↓
其他 sharer 接受 invalidate 并回复 ACK
（是否已在同一时刻物理写成 I，取决于是否使用 Invalidate Queue）
        ↓
CPU 0 收齐 ACK，取得独占写权限
        ↓
CPU 0 才能完成 cache line 的修改
```

如果流水线一直等待整个过程，store miss 或 `S -> M` 升级的延迟会直接暴露给 CPU。

Store Buffer 的基本思想是：先把 store 的地址和数据保存下来，让流水线继续执行，再由缓存系统在后台取得写权限并排空该 store。

```text
执行 store X=1
        ↓
+-----------------------+
| Store Buffer          |
| X, data=1, mask=...   |
+-----------------------+
        ↓ 后台申请 M
      L1 Cache
```

这里必须区分三个时间点：

1. store 指令已经执行，并进入 Store Buffer
2. cache controller 正在申请 `M`，store 尚未全局可见。
3. 写权限已经取得，store 已写入 cache，其他核之后的同地址请求必须看到它或更新的值。

“进入 Store Buffer”不等于“已经对其他 CPU 可见”。

### Store-to-load forwarding

如果本核随后又读取同一个地址：

```text
X = 1;
r = X;
```

此时 cache 中可能仍是旧值，但本核不能读回旧值。因此 load 会查询比它更老的 Store Buffer entry，并直接得到 `1`：

```text
Store Buffer 中的 X=1
        ↓ forwarding
      load X 得到 1
```

这只适用于地址和字节范围匹配的访问。如果 store 地址尚未计算出来、数据尚未就绪，或者 load 与 store 只有部分字节重叠，CPU 可能需要等待、合并数据，或在之后检测到冲突时重放 load。

所以，Store Buffer 并不是“后续所有内存访问都从中读取”，而是本核 load 的一个额外数据来源。

### Store Buffer 引入的顺序现象

考虑经典的 Store Buffering 例子，初始 `X = Y = 0`：

```text
CPU 0                    CPU 1
X = 1                    Y = 1
r0 = Y                   r1 = X
```

可能发生：

```text
CPU 0 把 X=1 放入自己的 Store Buffer
CPU 1 把 Y=1 放入自己的 Store Buffer
CPU 0 从 cache 读取 Y，仍得到 0
CPU 1 从 cache 读取 X，仍得到 0
```

结果为：

```text
r0 == 0 && r1 == 0
```

这并没有破坏缓存一致性：

- 对 `X` 而言，CPU 1 的读可以被排在 CPU 0 的写之前；
- 对 `Y` 而言，CPU 0 的读可以被排在 CPU 1 的写之前；
- 没有任何 CPU 对同一个地址的写入顺序产生分歧。

它体现的是跨地址的：

```text
Store -> Load
```

顺序没有被强制保持。这属于内存一致性模型，而不是 MESI 四个状态能单独决定的问题。

`0,0` 是否允许，最终由 ISA 内存模型决定；例如 TSO 仍允许典型的 Store→Load 旁路，而相应的 full fence 会禁止该结果。若用 C/C++ 编写实验，还必须使用原子对象或正确的 litmus harness，普通变量的数据竞争不能直接当成硬件内存模型结果。

## Invalidate Queue

更规范的名称是 **Invalidate Queue（失效队列）**。有些材料也写成 Invalidated Queue，但前者表达的是“等待处理的失效请求”。

### Invalidate Queue 是什么

Invalidate Queue 是失效请求接收一侧的暂存结构。概念上的 entry 会记录：

```text
要失效的 cache-line 地址
请求或事务标识
ACK 应回复给谁
该失效是否已经应用到 cache / load pipeline
```

收到 invalidate 后，控制器可以先完成：

```text
接收消息 -> 分配 queue entry -> 回复 ACK
```

再在后台完成：

```text
选择 queue entry
    -> 与本地 cache pipeline 仲裁
    -> 处理同址推测 load
    -> 将 S/E 等状态改为 I
    -> 释放 entry
```

因此它的核心作用是：**让失效发送方不必同步等待接收方完成所有本地微架构动作。** 如果 queue 已满，接收方就不能继续无条件 ACK，必须产生 backpressure、拒绝请求或让上游稍后重试。

“Queue”也只是功能描述；真实实现可以是 FIFO，也可以是按地址关联的 pending 表、probe entry 或其他结构。

### 为什么需要 Invalidate Queue

当一个 cache 收到远端的 invalidate 时，真正完成失效可能要与以下操作协调：

- cache tag/data pipeline；
- 当前正在命中该 line 的 load；
- 已经推测执行但尚未退休的 load；
- 正在进行的 replacement、refill 或 writeback；
- 同地址的其他一致性事务。

如果必须等这些动作全部结束才回复 ACK，writer 获得 `M` 的时间就会被每个 sharer 的本地流水线延迟拖长。

教材常用下面的抽象模型解释优化：

```text
收到 invalidate X
        ↓
把 X 记入 Invalidate Queue
        ↓
尽早回复 ACK
        ↓
稍后完成本地 tag 更新、load 检查或 replay
```

### “先 ACK、后处理”真正要求什么

这里最容易产生误解。

这里要把“物理处理时间”和“这次 load 在一致性顺序中的位置”分开。

一种保守实现会在 ACK 前把该 line 标成 pending-invalid/locked，使新的同址 load 等待或 replay。此时虽然 tag RAM 可能还写着 `S`，旧副本已经不能使用。

教材中的经典 Invalidate Queue 模型还允许更激进的行为：先接收并排队 invalidate、回复 ACK，本核在真正应用该 invalidate 前仍可能从旧副本取值。

这并不自动违反单地址 coherence。假如该 load 读到旧值，协议必须能够把它放在远端 store **之前**：

```text
一致性顺序：本核 load X -> 远端 store X

物理执行时间却可能是：
远端已经收到 ACK -> 本核 load 才从尚未处理的副本取值
```

不同 CPU 之间没有一个仅凭墙上时间就建立的先后关系。没有同步时，这次 load 仍可被解释为排在远端写之前。

真正不允许的是：

```text
本核已经通过 acquire 等同步关系
把 load X 排在远端 store X 之后
        ↓
load X 却仍返回 store 之前的旧值
```

所以 early ACK 的准确含义不是固定的“tag 已经是 I”，而是接收方已经承担了协议规定的失效义务。它还能否暂时满足旧值 load，取决于具体协议和内存模型；如果允许，该 load 只能被排序在远端写之前。

目录中的 `M` 与旧 cache 中尚未清理的 `S` tag 也不能简单理解成两个稳定 MESI 权限同时存在。后者由 transient/pending 状态约束，其产生的读必须仍能放入合法的单地址顺序。

真实处理器不一定有一个字面意义上就叫 `Invalidate Queue` 的 FIFO。pending bit、Probe Queue、snoop queue、MSHR、load replay 标记等结构都可以实现相同的协议语义。这里的 Invalidate Queue 首先是教材中的功能模型。

### Invalidate Queue 引入的顺序现象

假设：

```text
CPU 0                    CPU 1
A = 1                    while (B == 0) {}
B = 1                    r = A
```

即使 CPU 1 已经观察到 `B == 1`，也不能仅凭 MESI 推出 `A == 1`：

- CPU 0 对 `A` 的 store 可能仍滞留在 Store Buffer，而 `B` 先传播出去；
- 或者 `A` 的 invalidate 已经到达 CPU 1，但尚处在待处理状态，而 CPU 1 随后读取了其他地址 `B`；
- 对不同 cache line 的两个一致性事务，本来就可能在网络和控制器中独立推进。

要让 `B` 承担“发布 A”的含义，程序必须明确建立跨地址顺序。

教材中的配对写法是：

```text
CPU 0                         CPU 1
A = 1                        while (B == 0) {}
write_barrier                read_barrier
B = 1                        r = A
```

写侧阻止 `B` 越过 `A` 成为发布结果，读侧阻止读取 `A` 越过已经观察到的 `B`，或继续使用与该同步关系冲突的 pending invalidate。

## 内存屏障如何约束这两个队列

Store Buffer 和 Invalidate Queue 平时一直在排空，并不是执行 fence 时才开始工作。屏障的作用是建立一个顺序边界。

### 写屏障 / release

写屏障与 release 的精确覆盖范围由语言和 ISA 定义，不能在所有体系结构上机械地视为同一条指令；这里讨论的是它们共同承担的“约束发布之前的访问”这一功能。

概念上，写屏障要求：

```text
屏障之前的 store
        ↓
达到架构规定的顺序点
        ↓
屏障之后的 store 才能对外成为可观察结果
```

因此：

```text
A = 1;
write_barrier();
B = 1;
```

不能让 `B=1` 先成为发布结果，而 `A=1` 仍以违反该屏障语义的方式滞留。

这常被简化成“写屏障清空 Store Buffer”，但真实实现只需满足 ISA 规定的顺序和完成条件，不一定要求整个 buffer 为空，也不要求把 cache 写回内存。

AArch64的`STLR`如何在不等待其他核心的情况下履行这项约束，以及release属性可能怎样被LSQ、Store Queue和下游内存系统消费，见[ARM STLR如何保证Release顺序](/操作系统/2026/09/27/ARM-STLR如何保证Release顺序/)。

### 读屏障 / acquire

读屏障与 acquire 同样不是所有 ISA 中完全相同的指令类别；这里关注的是它们共同承担的“约束获取之后的访问”这一功能。

概念上，读屏障要求：

```text
屏障之前观察到的同步事件
        ↓
建立顺序边界
        ↓
屏障之后的 load 不得使用违反该顺序的旧值
```

教材可能把它描述成“清空 Invalidate Queue”。更准确的说法是：

> 屏障之后的访问不能越过与它相关的、尚未完成的 coherence 事件。

实现可以阻止 load 发射，也可以先推测执行、冲突时 replay，还可以只检查同地址 pending invalidation；不必真的清空一个全局 FIFO。

### release/acquire 发布

用 C++ 原子表达上述意图：

```cpp
int data = 0;
std::atomic<int> ready{0};

// CPU 0
data = 42;
ready.store(1, std::memory_order_release);

// CPU 1
if (ready.load(std::memory_order_acquire) == 1)
    assert(data == 42);
```

这里同时依赖两类保证：

1. coherence 保证 `ready` 自身的修改顺序和读取来源一致；
2. release/acquire 保证 `data` 与 `ready` 之间的跨地址顺序；
3. 语言内存模型用 synchronizes-with / happens-before 定义程序语义。

如果把 `ready` 改为 relaxed，coherence 仍然存在，但“看到 ready 就必须看到 data”的发布关系消失了。

## MESI 瞬态中的边界情况

稳定 MESI 只有 `M/E/S/I`，但真实事务有传播延迟，所以协议还必须有瞬态状态、事务表和等待队列。

下面讨论之前对话中的问题。

### 多个 S 正在失效时，又有一个 I 发起读取

初始状态：

```text
CPU 0: X=0, S
CPU 1: X=0, S
CPU 2: X=0, S
CPU 3:       I
```

CPU 0 要执行 `X=1`，于是发出 upgrade：

```text
CPU 0: S -> SM
```

`SM` 表示：CPU 0 想从 `S` 升级到 `M`，但尚未收齐其他 sharer 的 ACK。

此时 CPU 3 从 `I` 发出 `GETS(X)`。结果取决于两个请求在该 cache line 的顺序点上谁先被接受。

#### 情况一：upgrade 先被接受

```text
Upgrade(CPU 0) < GETS(CPU 3)
```

此时该地址已经有事务进行中。CPU 3 的请求必须被：

```text
stall / NACK / retry / 排入同地址等待队列
```

中的某种机制挡住，不能绕过 upgrade 偷偷取得一个 `S`。

正常顺序是：

```text
CPU 1、CPU 2 放弃 S 并回复 ACK
        ↓
CPU 0 收齐 ACK：SM -> M
        ↓
CPU 0 把 X 修改为 1
        ↓
协议再处理 CPU 3 的 GETS
        ↓
CPU 0 提供最新的 X=1，并从 M 降级
        ↓
CPU 0、CPU 3 最终持有新值的 S
```

这里 CPU 3 得到的是新值 `1`。

#### 情况二：GETS 先被接受

```text
GETS(CPU 3) < Upgrade(CPU 0)
```

CPU 3 可以先合法地取得旧值 `0`，并成为新的 sharer。随后 CPU 0 的 upgrade 还必须把 CPU 3 也纳入失效范围。

这不违反 coherence，因为 CPU 3 的这次读在同一地址的一致性顺序中位于 CPU 0 的写之前。

关键不在于 CPU 3 “恰好在哪一纳秒发出请求”，而在于协议最终把它排在写之前还是写之后。

### 已经变为 I 的 CPU 立即再次读取

这正对应最容易疑惑的混合瞬态。假设当前是：

```text
CPU 0: SM，正在等待写权限
CPU 1: I，已经处理 invalidate 并回复 ACK
CPU 2: S，invalidate 尚未处理
```

此时 CPU 1 立即执行 `load X`。由于它已经是 `I`，不能命中旧副本，只能发出新的 `GETS`。

如果 CPU 0 的 upgrade 尚未结束，这个 `GETS` 与前面的 CPU 3 请求一样，必须等待、重试或被暂存。等 CPU 0 完成写入后，它才能取得排在该写之后的数据。

CPU 2 此刻虽然还保留 `S`，也不能绕过正在进行的 upgrade，直接用旧值满足 CPU 1 的新 `GETS`。该地址的事务已经被占用；directory/home 必须先完成或重新排序现有事务。

所以不会出现：

```text
CPU 1 已经真正处理失效并进入 I
CPU 1 又在 upgrade 的缝隙中取回旧值
CPU 0 随后才完成写入
```

注意，“已经进入 `I`”比“使用 early ACK 回复了 ACK、但 invalidate 仍在队列中”更强。后者属于下一节讨论的情形。

### ACK 已回复，但物理状态还没从 S 写成 I

这出现在采用 early ACK 的实现抽象中。之后可以有两种策略：

```text
策略 A：把 line 锁成 pending-invalid
        新 load 等待或 replay

策略 B：经典 Invalidate Queue 模型
        新 load 暂时仍可能读到旧值
```

策略 B 得到旧值时，这次 load 必须在该地址的一致性顺序中位于 writer 的 store 之前。若 load 已借助 acquire 被约束在 writer 的发布之后，就必须先处理相关 invalidate，或者把错误推测的 load replay。

因此，不能只根据 ACK 推断 SRAM tag 已变为 `I`，也不能只根据 SRAM 中还保留旧数据就断言 coherence 已被破坏；要看 pending 状态以及 load 最终被排在写的哪一侧。

当前 gem5 `MESI_Two_Level` 没有模拟这个 early-ACK 窗口：L1 在同一个 SLICC transition 中执行 `S + Inv -> I` 并发送 ACK。因此不能把 gem5 的网络消息队列直接称为教材中的 Invalidate Queue。

### ACK 已收齐，但 writer 还没把新值写入 cache

这也是瞬态必须处理的边界。

协议不能在下面两件事之间放行一个新的 `GETS`：

```text
writer 获得独占权限
        |
        | 不能让新读请求越过
        v
writer 写入 store data
```

常见做法是让该 cache line 的事务仍保持 busy/blocking，等 store data 被接受并发出 unblock 后，再唤醒同地址请求。

否则 reader 可能被排在 store 之后，却拿到 store 之前的旧数据，这会破坏单地址一致性。

### writer 为 M 时，内存中必须已经是新值吗

不必须。

`M` 正表示 cache 中的数据可能比下层内存更新。其他 CPU 随后的 `GETS` 可以由 owner 提供最新数据，owner 再从 `M` 降级；不需要先写回 DRAM，再让 reader 从内存读取。

因此：

```text
读失败 / GETS
```

并不必然意味着：

```text
owner 先完整写回内存
```

cache-to-cache transfer 同样能完成事务。

### 推测 load 已经读到旧值，随后 invalidate 到达

乱序 CPU 的 load 可能已经从 L1 取到值，但还没有退休。此时 cache controller 只改变 MESI 状态还不够，还需要通知 Load Queue 检查飞行中的 load。

若该 load 不能再合法地排在远端写之前，CPU 必须：

```text
squash / replay / 重新执行
```

因此，“cache line 已经失效”与“依赖旧值的推测指令已经被处理”也是两个不同时间点。协议通过 snoop 通知和 CPU replay 机制把两者连接起来。

### 队列满了怎么办

Store Buffer、Invalidate Queue、MSHR 和协议消息队列都是有限资源。队列满时不能丢请求或假装事务已经完成，只能施加 backpressure：

```text
阻止新指令进入
暂停发射
NACK 并稍后 retry
或让上游请求保持 pending
```

容量影响性能和拥塞，但不应改变协议允许的最终结果。

## gem5 如何验证上述边界，而不是替代协议解释

本地 gem5 `stable@f5c5a6e390f5` 的 `MESI_Two_Level` 可以验证前述瞬态结论：

- `MESI_Two_Level-L1cache.sm` 中，`S + Store -> SM`；
- L1 的 TBE 使用 `pendingAcks` 跟踪尚未完成的失效确认；
- `MESI_Two_Level-L2cache.sm` 中，upgrade 会让共享状态进入阻塞瞬态 `SS_MB`；
- 该地址上的新请求通过 `stall_and_wait` 等待，而不是越过 upgrade；
- `SM + Ack_all -> M` 时执行 store hit，并发送 `Exclusive_Unblock`；
- L2 收到 unblock 后才唤醒该地址等待的请求；
- `S + Inv -> I` 与发送 ACK 位于同一 transition，因此这个协议没有实现教材式“ACK 后仍等待处理”的 Invalidate Queue；
- O3 CPU 的 `LSQUnit::checkSnoop()` 会检查飞行中的 load，并在需要时把它们标记为重新执行。

这些代码证明的是协议必须具备的能力：

```text
瞬态状态
+ 每地址事务记录
+ ACK 计数
+ 同地址阻塞/重试
+ 推测 load replay
```

它们不是在证明所有真实 CPU 都使用同名模块或完全相同的状态机。

相关代码入口：

```text
src/mem/ruby/protocol/MESI_Two_Level-L1cache.sm
src/mem/ruby/protocol/MESI_Two_Level-L2cache.sm
src/mem/ruby/network/MessageBuffer.hh/.cc
src/mem/ruby/slicc_interface/AbstractController.cc
```

## 缓存一致性与内存一致性的关系

| 问题 | 缓存一致性 | 内存一致性 |
| --- | --- | --- |
| 主要范围 | 单个地址/cache line | 多个内存操作、多个地址 |
| 核心目标 | 单写者、写传播、同址写顺序一致 | 规定哪些跨操作观察顺序合法 |
| 典型机制 | MESI、directory、invalidate、ACK、瞬态状态 | TSO、RVWMO、Arm ordering、fence、acquire/release |
| 典型反例 | 两个核同时认为自己可独占写同一行 | Store Buffering 得到 `0,0` |

它们的关系可以概括为：

1. **coherence 是 consistency 的底层基础之一。** 如果同一个地址都不能达成一致，就无法构造有意义的多地址内存模型；
2. **coherence 不等于 consistency。** MESI 不负责自动保持不同地址间的程序顺序；
3. **buffer 和 queue 通常不破坏 coherence。** 它们改变的是请求何时进入同址顺序，以及不同地址的事务如何交错；
4. **barrier 不取代 coherence。** barrier 依靠 coherence 提供的数据与权限事件，再对这些事件施加跨地址顺序；
5. **语言内存模型还在更上层。** C/C++ 普通变量存在数据竞争时属于未定义行为，不能只根据某次硬件运行结果解释程序。

一个不承担发布职责的统计原子可以只使用 relaxed：

```cpp
std::atomic<uint64_t> requests_done{0};

// worker
process_one_request();
requests_done.fetch_add(1, std::memory_order_relaxed);

// monitor
auto n = requests_done.load(std::memory_order_relaxed);
```

coherence 保证计数器本身的原子修改顺序，但 monitor 看到某个计数值，并不表示它必须同时看到 `process_one_request()` 对其他地址造成的全部修改。这正是“单地址一致”与“跨地址同步”的区别。

## 解析协议时应始终追踪的内容

遇到新的 MESI 边界场景时，不要只看四个稳定状态，而要依次确认：

1. 该 cache line 当前是否已有事务；
2. requester、owner、sharer 和 home/directory 分别是谁；
3. requester 处于什么瞬态，例如 `IS`、`IM`、`SM`；
4. 还在等待哪些 ACK、data 或 grant；
5. 新请求是在已有事务之前还是之后被序列化；
6. 冲突请求会 stall、NACK、retry、merge 还是 replay；
7. ACK 代表消息已收到，还是旧权限已经不可再使用；
8. 旧副本只是物理存在，还是仍可向架构 load 返回数据；
9. store 是刚进入 Store Buffer，还是已经获得写权限并写入 cache；
10. 问题涉及同一地址的 coherence，还是不同地址的 consistency。

最终必须维护三个不变量：

```text
在稳定、逻辑一致性状态中至多有一个可写 owner

排在某次写之后的 load，不得再从更旧的写取得值

同地址的新请求必须与正在进行的事务形成明确先后
```

Store Buffer 和 Invalidate Queue 可以让物理状态暂时比四个稳定字母复杂，也可以延迟工作、隐藏延迟、允许推测，却不能产生无法串行化的同地址结果。它们造成的跨地址可观察顺序，则由内存一致性模型和屏障来约束。
