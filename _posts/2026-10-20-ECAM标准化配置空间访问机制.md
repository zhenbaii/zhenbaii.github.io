在前面的章节中，我们讲到了PCI/PCIe的硬件拓扑和逻辑拓扑，以及用于配置Function的配置空间的定义。那么，操作系统又是如何通过MMIO等方式去访问到这部分Function的实际的硬件寄存器，从而可以对他们发起配置请求呢？这就是这一节要讲的ECAM标准化配置空间访问机制。

在传统的x86 PCI中，并不是通过MMIO等机制来访问配置空间的，而是通过所谓的访问I/O的方式来进行的。SoC会规定两个内存地址专门用于访问配置空间，CPU通过不断访问这个I/O port来实现配置：
- `0xCF8`：写入目标 Bus、Device、Function 和寄存器位置。
- `0xCFC`：读取或写入目标配置寄存器的数据。

可以概括为下图：
```
CPU
 |
 +-- 向 0xCF8 写入目标 BDF 和 Offset
 |
 +-- 通过 0xCFC 读取配置数据
 |
 v
Host Bridge
 |
 v
目标 PCI Function
```

而在PCIe中，则通过ECAM，把配置空间直接暴露在MMIO中，使得CPU可以方便地访问对应的配置项。ECAM的全称是Enhanced Configuration Access Mechanism, 即增强的配置访问机制。现在，流程变成了这样：
```
CPU
 |
 | 访问 ECAM Base + BDF + Offset
 v
Root Complex / Host Controller
 |
 v
目标 PCI Function
```

CPU访问对应的MMIO窗口时，这个访问请求被路由到了root complex/host controller, 由它去访问真正的Function configuration space. 目前，ECAM已经成为PCIe配置访问最主流的方案。

## ECAM MMIO空间定义

ECAM的MMIO排布按照Bus-Device-Function的层次编排。前面我们已经知道，在PCIe中，每个Function的Configuation Space占据4KB. 而根据PCIe标准，每个设备最多有8个Function, 每个Bus最多有32个Device，一个PCIe Segment最多支持256条总线。因此，我们可以很容易地算出整个ECAM MMIO所需的大小：
$$
MMIO\,\,SIZE=4KB \times 8 \times 32 \times 256 = 256MB 
$$

即256MB。 每个Bus 1MB，每个Device 32KB, 每个Function 4KB。

## 设备树定义

ECAM通常通过设备树节点方式来声明MMIO空间。我们可以去Linux主线代码中找到诸多例子：
```
// ARM FVP 主线 DTS
pcie {
    compatible = "pci-host-ecam-generic";
    bus-range = <0x0 0xff>;       // 256 buses

    reg = <0x0 0x40000000
           0x0 0x10000000>;       // 0x10000000 = 256MB
};

// 主线 Alpine DTS
pcie {
	compatible = "pci-host-ecam-generic";
	
	reg = <0x0 0xfbc00000
	       0x0 0x100000>;        // 0x100000 = 1MB
	
	bus-range = <0x00 0x00>;     // 1 bus
};
```

可以发现两个特点：
-  compatible = "pci-host-ecam-generic";
- bus-range和reg中的size字段绑定，并不总是256MB

某些compatible不是ecam的节点则不适用ECAM协议，而可能是其他用途，或者厂商自定义的。
