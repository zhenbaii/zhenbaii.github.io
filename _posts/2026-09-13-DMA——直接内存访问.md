DMA, 即Direct Memory Access, 直接内存访问，是一种重要高效的内存技术，它允许内存和外设之间的数据交互不经过CPU，而直接通过总线访问。数据搬运完成后，发起中断通知CPU，从而大大提高了CPU的异步性和数据搬运效率。如果没有DMA，那么搬运数据时，都要经由CPU load+store指令来完成，效率相对比较低下。

## DMA的发起者

DMA虽然十分高效，但是并不是所有外设都具备发起DMA请求的能力，比如简单的串口设备，i2c等就不具备直接发起DMA请求的能力。一般而言，要能够发起DMA请求，这个外设必须可以成为总线的master. 因此，要不外设自身是master, 可以直接发起DMA请求，要不外设需要依靠某个具备发起DMA请求的总线master来代为完成DMA请求。

### DMA controller
这就属于我们刚才说的**依靠某个具备发起DMA请求的总线master来代为完成DMA请求**. DMA控制器会和一些外设连接，外设可以主动向DMA控制器发出信号，从而来提出DMA请求。DMA控制器代替它处理请求后，把结果转发回对应外设。许多串口，i2c，spi，音频控制器等都采用了这种方式。下图很好地展示了DMA controller的作用：
```
外设 FIFO  <--->  DMA 控制器  <--->  内存
                      ▲
                 CPU 配置通道
```

### 外设自身是bus master
这种情况下，外设自己就可以发起DMA请求并处理这个请求。常见的有PCIe网卡，NVMe, GPU等。比如网卡收到数据包后，可以：
- 从接收队列中取出一个 DMA 地址；
- 把数据包直接写到该地址；
- 更新完成描述符；
- 向 CPU 发送中断。
从而不需要CPU反复执行load/store. 


## DMA地址

在发起DMA请求时，并不是直接写物理地址的，而是用DMA地址。我们可以把系统里的地址分为三层：
```
CPU 虚拟地址 X
     │ CPU 页表
     ▼
CPU 物理地址 Y
     │ 总线映射 / IOMMU
     ▼
DMA 地址 Z —— 写进设备描述符的地址
```

可以发现，DMA地址和物理地址之间存在一个映射关系，类似虚拟地址和物理地址之间的关系。驱动会把DMA地址写进设备寄存器，设备把这个数字放到总线上，或者交给IOMMU翻译为物理地址。

根据映射方式的不同，DMA地址和物理地址之间一般存在好几种关系。

### 恒等映射
在最简单的系统中，`DMA地址=CPU物理地址`，即恒等映射的方式。例如：
```
CPU VA：  0xffff_ffc0_9000_0000
             │ MMU
             ▼
CPU PA：  0x0000_0000_9000_0000
DMA：     0x0000_0000_9000_0000
```

设备把`0x9000_0000`放到总线上，内存控制器直接就找到`0x9000_0000`. 需要强调的是，我们这里并不是说DMA地址和物理地址在概念上等价，而是说他们之间的映射是恒等映射关系。DMA地址和物理地址之间不一定采用恒等映射的关系。

### 固定偏移
这种映射方式就是把DMA地址和物理地址之间设置一个固定的偏移。这样子，同一块内存，在内存控制器视角下和设备视角下拥有不同的地址，且两个地址之间的偏移是固定的：
```
CPU 物理地址：0x8000_0000
设备总线地址：0x0000_0000
```

### 动态翻译
这种方式就十分接近虚拟地址到物理地址的映射方式了。不过，这种方式需要借助IOMMU等硬件的辅助方式，而不能由总线自身完成。
这种方式下，DMA地址有一个别名，叫做IOVA, 即I/O Virtual Address. IOMMU会维护一份页表，页表中保存了`IOVA -> PA`的映射关系。下面的流程图就展示了这一过程：
```
设备
  │ 发出 DMA 地址 0x4000_0000
  ▼
IOMMU
  │ 查询 I/O 页表
  ▼
物理地址 0x1_2000_0000
  ▼
内存控制器
```


## 谁来建立映射？谁来负责翻译？

这两个问题都是DMA的核心问题。搞明白了这两个问题，我们就明白了DMA技术各方的职责和地位。

### 谁负责建立映射？
操作系统。映射关系由操作系统来接管，翻译官只是无条件遵循操作系统提供的映射关系。在Linux系统中，设备驱动根据设备的情况不同，有多种接口可供选择：
```
dma_addr_t dma_map_single(struct device *dev, void *ptr, size_t size,
                          enum dma_data_direction dir);

dma_addr_t dma_map_page(struct device *dev, struct page *page,
                        unsigned long offset, size_t size,
                        enum dma_data_direction dir);

int dma_map_sg(struct device *dev, struct scatterlist *sg,
               int nents, enum dma_data_direction dir);
```

上述这些接口，都是创建临时mapping用的。也就是说，对于某次DMA请求，上述接口就会临时分配出buffer供这次请求使用，请求完毕后，这些buffer则会被回收。每次来请求，就分配一次，用完后就释放。还有一个接口是用于分配永久驻留的DMA内存的，即`dma_alloc_coherent`，不过一般比较少用到这个接口。

在调用这些接口之前，驱动还需要做几件事情，来设置一些东西。
第一件，就是在probe阶段，**设置设备的DMA mask**, 这个mask主要用来告诉内核，这个设备支持的寻址范围是多少位。这决定了接口采取什么方式来为设备处理DMA请求。如果不设置，默认为32位，这可能不符合我们的设备实际能力。
第二件，就是通过一些特殊的分配器，分配好一块供DMA请求使用的buffer. 不同的接口，对这个buffer做出的要求也是不同的。

#### `dma_map_single`:
这是最常用的接口，不过它对缓冲区也有比较严格的要求。其`ptr`参数是任意的虚拟地址。但是，这个接口要求这个VMA对应的物理地址是连续的，也就是说其要求线性映射的缓冲区。这是**硬性要求。** 这意味着，`vmalloc`等接口是不可以用的，通常会使用`kmalloc`. 
同时，这个接口也强烈要求分配缓存行对齐的缓存。也就是说，缓存块的起始地址刚好位于某个缓存行的边界，并且其长度为缓存行长度的整数倍。这是因为，在非一致性架构上，DMA操作需要软件进行缓存的维护，缓存行对齐可以避免损害到无关的数据。

#### `dma_map_page`:
和`dma_map_single`不同，这个接口不是接收一个虚拟地址，而是接收一个`struct page`.这个接口的语义是"取一页的某一部分作为DMA请求用的buffer"，因此，这个接口用于一页内的映射，映射范围千万不可以跨出一页。在拿到page后，他会先得到page的起始物理地址，然后加上offset, 得到一个新的物理地址。从这个物理地址开始的size长度作为DMA buffer：
```
phys = page_to_phys(page) + offset;
// 然后把 [phys, phys + size) 当作一段连续物理地址去映射
```

这个接口内部不会去校验offset和size, 因此，这依赖驱动开发者自觉遵守规范。

#### `dma_map_sg`:
这是功能最强大的一个接口。专门用于物理上不连续的多个缓冲区。它接收的不是虚拟地址，也不是`struct page`, 而是所谓的`scatterlist`.  `sg`参数就是`sactterlist`的指针数组，`nents`参数表示这个数组的有效条目的数量。这个结构体长这样子:
```c
struct scatterlist {
    unsigned long   page_link;   // 关键字段
    unsigned int    offset;
    unsigned int    length;
    dma_addr_t      dma_address;
#ifdef CONFIG_NEED_SG_DMA_LENGTH
    unsigned int    dma_length;
#endif
};
```

`page_link`是一个支持链式扩展的综合字段，其最低两位被用作标志位：
```c
#define SG_CHAIN 0x01UL
#define SG_END   0x02UL
```

如果`SG_CHAIN`被置1, 那么当前的`scatterlist`是一个链节点，page_link的高位指向下一个`scatterlist`的指针，否则，说明该条目是数组最后一个元素。支持链式扩展是为了适应一些非常大的I/O请求，允许多个数组串起来，防止一次性分配一个巨大的数组。不过，这个仅作了解即可。一般而言，我们不会用到这个扩展功能。

在一般情况下，这个字段的剩余高位部分用来存放`struct page *`指针。驱动编写者需要提供`struct *page, offset, length`字段，之后，`dma_address`字段被内核填充，后续我们可以通过宏来这里拿地址。本质上，这个接口就是提供一个快速的方式为多个页面建立映射。
```
sg[0] -> 一段物理内存
sg[1] -> 另一段物理内存
sg[2] -> 又一段物理内存
```

如果存在连续分布的页，那么对应entry可能被合并，即`length`超过一页的大小，这一点我们也说过，是不会被内核拒绝的。


#### 不同的平台条件
根据平台不同，DMA分配通常有如下几种情况， 他们对物理内存连续性，以及物理内存地址的分布位置的要求都不同：
##### 无IOMMU，无SWIOTLB
这适用于最最简单的嵌入式平台，整个链路如下：
```
CPU VA ──MMU──► PA ──────────────► DMA 地址 = PA

   CPU 虚拟地址            物理地址 = DMA 地址
   ┌──────────┐            ┌──────────┐
   │  buf     │──MMU──────►│ 0x8000_0000 │◄── 设备直接访问
   └──────────┘            └──────────┘
```

这种情况下，要求buffer的物理地址是连续的，因为设备只做这种最保守的假设。

##### 有IOMMU
前面我们提到，在没有IOMMU时，要求物理地址连续，因为没有一个外设可以帮助设备做地址翻译工作，设备只能保守地认为OS提供给我的地址是连续的。现在，有了IOMMU，就可以帮助设备完成地址翻译工作了，相当于是工作在I/O场景下的MMU：
```
   CPU 虚拟地址           IOVA (DMA 地址)         物理地址
   ┌──────────┐          ┌──────────┐           ┌──────────┐
   │  buf     │──MMU────►│ 0x0000_1000│──IOMMU──►│ 0x8000_0000│
   └──────────┘          └──────────┘           └──────────┘
                              ▲
                              │
                        设备看到的是这个
```

在这个场景下，接口做的事情是：
-  根据VA找到PA
-  在IOMMU里，建立`IOVA -> PA`映射关系
-  返回`IOVA`, 而不是返回物理地址

有了IOMMU后，我们不再要求物理地址连续了！同时，我们也不再要求设备有寻址整个物理内存的能力了！对于只能寻址低24位，32位的设备，我们就可以通过映射的方式，让他们的`IOVA`寻址空间映射到他们寻址不到的物理地址空间！！

有了IOMMU后，几乎所有外设我们都可以为他们赋予DMA能力，即使那些只能寻址低地址空间的外设。
物理地址空间从0x0开始编号，里面会涵盖不同的功能段，比如DRAM，MMIO。在DMA场景中，我们真正关心的，是DRAM部分的位置。不同架构对物理地址的划分也是不同的：
```
x86 PC
0x0000_0000 ┌──────────────┐
            │ 低端 RAM      │ 可用
0x0009_FC00 ├──────────────┤
            │ VGA/BIOS 洞   │ 不可用
0x0010_0000 ├──────────────┤
            │ 常规 DRAM     │ 一直向上
            │              │
0xE000_0000 ├──────────────┤
            │ PCIe MMIO 洞  │ 常见 3~4GB 之间
0x1_0000_0000├─────────────┤
            │ 高位 DRAM     │ 继续向上
            └──────────────┘
            
            
ARM embedded
0x0000_0000 ┌──────────────┐
            │ Boot ROM/外设 │
0x4000_0000 ├──────────────┤
            │   DRAM        │  ← 常见基址 0x40000000
0x8000_0000 ├──────────────┤
            │   DRAM        │  ← 也常见 0x80000000
0xC000_0000 ├──────────────┤
            │   DRAM        │
            └──────────────┘
```

在没有IOMMU时，设备可以寻址的范围，就决定了他的DMA地址寻址范围：
- 32 位设备：能访问 `0x0000_0000 ~ 0xFFFF_FFFF`
- 24 位设备：能访问 `0x0000_0000 ~ 0x00FF_FFFF`

如果DRAM太高，就会导致设备可以访问的合法的DMA地址空间有限，甚至完全无法访问。而有了IOMMU， 我们就可以把低地址DMA空间映射到高地址DRAM区域，从而不会对设备可以访问的DMA地址范围造成限制。

##### 有SWIOTLB
SWIOTLB的全称是Software Input/Output Translation Lookaside Buffer, 即软件控制的I/O TLB。 虽然有TLB， 但是它和CPU的TLB不是一回事，也和IOMMU的TLB不是一回事。本质上，它是**一块由软件管理的"低地址bounce buffer 池"，当设备够不到目标内存时，内核把数据拷贝到这块低地址内存，再让设备访问它。** 
回想之前的场景，考虑一个只能寻址32位地址的设备：
```
物理内存：
0x0000_0000 ┌──────────────┐
            │  低 4GB 区域  │  ← 32 位设备能访问
0xFFFF_FFFF ├──────────────┤
            │  高 4GB 区域  │  ← 32 位设备够不到！
0x1_7FFF_FFFF└─────────────┘
```

解决方案有两种：

| 方案          | 原理                          | 需要硬件吗       |
| ----------- | --------------------------- | ----------- |
| **IOMMU**   | 地址翻译，设备发 IOVA，IOMMU 翻到高物理地址 | 需要 IOMMU 硬件 |
| **SWIOTLB** | 数据拷贝，把数据搬到低地址，设备访问低地址       | 纯软件         |
在没有IOMMU的硬件支持时，SWIOTLB就是一个兜底的方案。

内核在启动的时候，会从低地址内存中预留出一块区域，称作**bounce buffer**:
```
物理内存：
0x0000_0000 ┌──────────────────┐
            │  内核代码/数据     │
            ├──────────────────┤
            │  SWIOTLB 预留区   │  ← 专门用来做 bounce buffer
            │  （大小可配置）    │
            ├──────────────────┤
            │  普通可用内存      │
0xFFFF_FFFF ├──────────────────┤
            │  高地址内存        │  ← 设备够不到
0x1_7FFF_FFFF└─────────────────┘
```

这个区域被切分为许多个slot，每个slot可以分配给一次DMA传输使用。
