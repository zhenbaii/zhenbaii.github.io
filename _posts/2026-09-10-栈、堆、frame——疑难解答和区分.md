在操作系统中，栈，堆，frame等概念频繁出现在各种场景中，很多人在很多场景下对他们的区别其实是模糊的。这种模糊就导致我们很难层次化地理解整个操作系统的内存管理机制，而浮于表面。因此，这篇文章我们来对一些常见的问题做讨论和区分，力求可以更加清晰地解析这几个概念。

### frame——最基本的分配单位

frame, 即帧，or页帧，可以理解为操作系统对物理内存的抽象。这是最基本的内存分配单位。在大多数主流的的操作系统中，页帧的大小一般都用4KB来表示。总的来说：
-  物理实体是DRAM和物理地址空间
-  frame是物理内存的固定大小的划分单位
-  frame allocator管理frame这种资源

### 堆——进程级别的“永久驻留”内存

很多人在理解堆的时候，总是会把它误解成是物理内存中一块全局共享的(即对内核可见，对所有进程也可见)特殊的大区域，然后内核，进程都从这里取出来用，作为各个进程内部动态分配内存的载体。 然而实际上，堆是进程级别的概念，不同进程之间的堆是互相看不见的。在Linux中，用户态的堆，其实就是一个或者多个VMA，或者在我们rCore中，是一个MapArea。而VMA是归属mm_struct管理的，也就是说是归属于进程的虚拟地址空间的。

因此，我们在讨论用户态堆的时候，需要时刻记住以下几点：
-  它不是什么特殊的物理内存区域。它就是进程的一个或者多个VMA，地位上讲，不比其他VMA      更加特殊
-  进程之间的用户态堆是互相不可见的，因为进程地址空间的隔离性
-  线程之间是共享进程的堆的
-  进程刚刚创建时，这块VMA的大小是0, 是空壳，后面通过malloc来扩大
-  这块VMA的属性被标记为lazy, 缺页访问时才会触发frame分配，从而可以支持大块虚拟内存的分  配。

下图就展示了这个情况，用户态堆就是一个普通的VMA：
```
进程虚拟地址空间（高地址在上）

┌──────────────────┐
│     stack        │  ← VMA
├──────────────────┤
│   file / libc    │  ← VMA
├──────────────────┤
│   anon mmap      │  ← VMA（malloc 也可能用）
├──────────────────┤
│     [heap]       │  ← VMA（堆只是普通 VMA）
├──────────────────┤
│     bss          │  ← VMA
├──────────────────┤
│     data         │  ← VMA
├──────────────────┤
│     text         │  ← VMA
└──────────────────┘
低地址
```

#### malloc/free和用户态堆的关系

首先需要明确的一点是，malloc不是系统调用，malloc不是系统调用，malloc不是系统调用！ malloc/free是glibc, musl等用户态库提供的一个接口，他们本质上也只是用户态的一个接口。而这个接口内部，封装了真正的系统调用。我们可以这么理解：
-  glibc提供的malloc/free等接口，本质上是一个经过验证、效果得以保证、提供丰富功能的用户     态接口，由他们代替用户发起系统调用
-  malloc/free等接口是一个统一的对外接口，接口的实现根据用户态分配器的不同可以不同

总的来说，我们可以这么理解：`malloc/free`是一个统一的接口，用户只需要和这两个接口交互。统一的接口背后，可以对应不同的用户态分配器的实现，比如`jemalloc, tcmalloc, mimalloc`， 他们都统一对外暴露相同的`malloc/free`接口，使得我们不必关心具体的用户态分配器是什么。在这些分配器的实现内部，就会发起系统调用，来和用户态堆交互。

##### brk/sbrk
很简单的系统调用，作用就是把进程的program break设置为addr， 即调整用户堆VMA的上界。用户堆VMA长这样：
```
start_brk                     brk
    |--------------------------|
    |        [heap]            |
    |--------------------------|
    低地址                     高地址
```

这两个边界量和用户堆VMA的边界有所区别：
- `start_brk`：堆的起始虚拟地址，页对齐。
- `brk`：当前 program break，堆的上边界，**不要求页对齐**。
- `vm_start`：`[heap]` VMA 的起始地址，页对齐。
- `vm_end`：`[heap]` VMA 的结束地址，页对齐。

也就是brk可以落在某一页中间。

这个系统调用就是调整brk的位置。不过，brk自身的位置也是有一个最高的天花板的，而不是可以无限制地调整。并且，也不能跨过其他的VMA. 在brk设置的位置小于天花板，但是已经超过了vm_end的时候，首先会判断用户态堆VMA是否允许扩展，如果可以，就会扩展，然后设置新的brk.
brk当然也可以减小，如果减小过程中恰好跳出了高地址的某一页，那么那一页的内存也会随之释放，VMA收缩。
sbrk就是brk的用户态封装，这里不展开讲。

总的来说，用户态分配器就是一个在用户态管理用户态堆VMA的一个模块。自始至终，我们只是在操作这个VMA，而不是操作其他东西。

用户态分配器的作用主要是减少系统调用的次数。不同的用户态分配器，通常都会做这些事情：
-  一次向内核申请一大块虚拟内存(malloc)
-  在用户态分成很多小chunk, 放到内存池中维护
-  程序调用malloc时，根据此时的情况，决定直接返回内存池的，还是要发起brk调用
-  free放回池
-  池不够大，才会发起brk

整个层级可以概括如下：
```
用户代码malloc(size)
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 用户态分配器：glibc ptmalloc                          │
|                                                     |── 分支 A：命中用户态内存池
|  判断直接从用户态内存池拿，还是说要系统调用扩容             |      → 返回虚拟地址    
└─────────────────────────────────────────────────────┘      → 用户态完成
    │
    ▼
分支 B：用户态内存池不够，需要向内核要内存
    │
    ▼
┌─────────────────────────────────────────┐
│ 决定用 brk 还是 mmap                      │ ── 分支 A：mmap
│                                         │          → 找空闲VMA，lazy标记
│ 判断条件：                                │          → malloc返回
│  - 主线程主 arena 且是小块 → brk          │
│  - 大块（>= mmap_threshold）→ mmap        │
│  - 非主线程 arena → mmap                  │
└─────────────────────────────────────────┘
    │
    ▼
分支 B：走brk
    │
    ▼
┌───────────────────────────────────┐
│ 系统调用 brk                       │
│ 进入内核态                         │
└───────────────────────────────────┘
    │
    ├─ 检查 new_brk 合法性：
    │- 不低于 start_brk
        │   - 不超 RLIMIT_DATA
        │   - 不与上方 VMA 重叠
        │
        ├─ 如果 PAGE_ALIGN(new_brk) > vm_end：
        │   → 创建或扩展 [heap] VMA
        │   → 更新 vm_end
        │
        └─ 更新 mm->brk
        │
        ▼
    返回用户态
```

### 栈——进程级别的临时内存

和堆一样，栈同样也是一个进程级别的概念，同样也只是一段普通的VMA.  不过和堆不同，每个线程之间的VMA是独立的，而不是共享的，下图就很好地表示了这一概念：
```
进程虚拟地址空间（同一 mm_struct / 页表）
┌──────────────────────┐
│ 主线程 [stack] VMA    │  ← 通常可增长，受 RLIMIT_STACK
├──────────────────────┤
│ 线程 1 用户栈 VMA     │  ← pthread 创建，mmap 匿名，固定大小
├──────────────────────┤
│ 线程 2 用户栈 VMA     │  ← 同上，通常带 guard page
├──────────────────────┤
│ [heap] VMA           │
├──────────────────────┤
│ 全局变量 / 代码 / 库   │
└──────────────────────┘
```

线程的栈空间通过mmap匿名创建出来，一般是固定大小。栈之间**有至少一页大小的guard pages**. 但是需要注意的是，他们仍然都落在进程的虚拟地址空间中。因此，理论上，一个线程如果知道另一个线程某个变量的地址，是可以跨线程访问和修改的。当然，我们要尽量避免这类情况的发生。

栈空间和函数栈等概念联系的十分紧密。

#### 函数栈

每次发生函数调用，就会在当前线程的用户栈(即上面所说的VMA区域)上压入一个新栈帧。一般来说，就是sp向低地址移动一个固定的距离，这个距离表示栈帧的大小。函数返回，就会弹出这个栈帧。一个简单的拓扑如下：
```
高地址
┌──────────────────┐
│  调用者的栈帧      │
├──────────────────┤
│  当前函数的栈帧    │  ← rsp / rbp 指向这里附近
├──────────────────┤
│  被调用者的栈帧    │
└──────────────────┘
低地址
```

函数栈帧的大小是编译期确定的。编译器会根据函数调用时，整个函数上下文的局部变量的大小，来确定函数栈帧的大小。

对于当前函数而言，他的上方是调用者的栈帧，下方则是被调用者，即当前函数发起的函数调用的栈帧。栈帧中，根据ABI的不同，一般会压入不同的内容，不过基本上都有callee-saved寄存器以及caller-saved寄存器(如果本函数也发起了函数调用)，比如下图：
```
高地址
┌──────────────────────┐
│  调用者的栈帧         │
├──────────────────────┤
│  第 7+ 个参数         │  ← 前 6 个参数走寄存器
├──────────────────────┤
│  返回地址             │  ← call 指令压入
├──────────────────────┤
│  保存的 rbp           │  ← 被调用者保存
├──────────────────────┤
│  局部变量             │
│  ...                 │
├──────────────────────┤
│  临时空间 / 对齐填充   │
└──────────────────────┘  ← rsp
低地址
```

我们一开始所说的线程栈的VMA，就是上面函数栈帧的载体，他们都在里面生长：
```text
单个线程的用户栈 VMA（例如主线程 [stack]）
高地址 vm_end
┌─────────────────────────────────────────────┐
│ 未使用区域（可能已映射，也可能未映射）        │
├─────────────────────────────────────────────┤
│ main 栈帧                                   │
│   ├─ 返回地址                               │
│   ├─ 保存的 rbp                             │
│   └─ 局部变量                               │
├─────────────────────────────────────────────┤
│ f 栈帧                                      │
│   ├─ 返回地址                               │
│   ├─ 保存的 rbp                             │
│   └─ 局部变量                               │
├─────────────────────────────────────────────┤
│ g 栈帧                                      │  ← rsp 当前栈顶
│   ├─ 返回地址                               │
│   ├─ 保存的 rbp                             │
│   └─ 局部变量                               │
├─────────────────────────────────────────────┤
│ 未使用但已映射页                             │
├─────────────────────────────────────────────┤
│ 未映射页 / 可增长边界 / guard page           │
└─────────────────────────────────────────────┘
低地址 vm_start 或可增长边界

函数调用：rsp 下移，新栈帧在低地址方向生长
函数返回：rsp 上移，弹出栈帧
```

而进程地址空间中，就是这样的拓扑：
```
进程地址空间（同一 mm_struct / 页表）
┌───────────────────────────────────────────────┐
│ 主线程栈 VMA  [stack]                         │
│   ┌───────────────────────────────┐           │
│   │ main → f → g                  │ 向下生长  │
│   └───────────────────────────────┘           │
├───────────────────────────────────────────────┤
│ 线程 1 用户栈 VMA（pthread mmap）              │
│   ┌───────────────────────────────┐           │
│   │ thread1_fn → ...              │ 向下生长  │
│   └───────────────────────────────┘           │
├───────────────────────────────────────────────┤
│ 线程 2 用户栈 VMA                             │
│   ┌───────────────────────────────┐           │
│   │ thread2_fn → ...              │ 向下生长  │
│   └───────────────────────────────┘           │
├───────────────────────────────────────────────┤
│ heap / mmap / 文件映射 / 全局变量 等其他 VMA   │
└───────────────────────────────────────────────┘
```


下面来回答几个比较重要的问题。
#### 栈溢出是如何发生的？操作系统会阻止吗？或者说有预防手段吗？

这里其实存在两个问题，栈缓冲区溢出，和栈VMA的溢出。下面我们来一一解答。
##### 栈缓冲区溢出
出现在我们分配了一个小数组，但是对他执行了远超缓冲区大小的命令时，比如如下：
```c
void f() {
    char buf[8];
    strcpy(buf, "AAAAAAAAAAAAAAAAAAAAAAAA");
}
```

这里，buf大小只有8字节，但是我们写入了很长的字符串。前面我们知道，函数栈的结构是：
```
高地址
┌──────────────────┐
│ 调用者 main 栈帧  │ ← 可能被覆盖
├──────────────────┤
│ 返回地址          │ ← 可能被覆盖
├──────────────────┤
│ 保存的 rbp        │ ← 可能被覆盖
├──────────────────┤
│ buf[8]            │ ← 起点
└──────────────────┘
低地址
```

`buf`是局部变量，对buf的strcpy是从低地址往高地址的。如果这个溢出过长，就可能覆盖了上面的返回地址，甚至踩到main函数的栈帧。这就是典型的栈缓冲区溢出。这一过程，内核是不会阻止的。因为内核管理的颗粒度是VMA，而这些函数栈帧都处于同一个VMA下，对于内核来说，他们是没区别的。

#### 栈VMA溢出

前面的函数栈缓冲区溢出，发生在VMA内部，这里则是发生在VMA层面。简单来说就是，VMA的整个空间都没撑爆，以至于访问到了VMA以外的区域，这经常发生在太深的递归调用链下，因为每一层调用都会产生一个函数栈帧的分配。或者，单个函数栈帧太大了。内核允许一定限度的栈空间的扩展，但是一旦超出这个限度，就会触发内核的介入，从而杀死进程。



到目前位置，我们对frame， 堆和栈的理解都已经比较深入了。我们可以做如下概括：
-  frame是最基本的，真正全局共享的分配单元
-  堆和栈都是进程概念，他们是进程私有的，而不是全局共享的，依赖frame
