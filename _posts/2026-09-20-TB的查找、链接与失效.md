这一篇是 `docs/devel/tcg.rst`（Translator Internals）的精读笔记。这份文档标题虽叫「翻译器内部机制」，实际讲的却不是翻译过程本身，而是 **TB 的运行时管理**。主线是三件事：

- **查找**：一个 TB 由什么标识（pc + flags），执行完一个 TB 后怎么找到下一个
- **链接**：找到之后如何跳过主循环、直接跳过去（chaining）
- **失效**：什么情况下 TB 必须作废（自修改代码、映射变化）

进主线之前，先明确 TB 本身是什么。**TB（Translation Block）是翻译的基本单位：从某个 guest PC 开始，一路译到执行流发生改变（或单纯太长）为止的一段 guest 指令，对应一块 host 机器码。** 一段指令流被切成 TB 的过程：

```text
  PC       指令
  ────────────────────────────────────────────────
  0x1000   addi t0, t0, 1        ┐
  0x1004   lw   t1, 0(a0)         │
  0x1008   add  t1, t1, t0        │ TB A
  0x100c   sw   t1, 8(a0)         │
  0x1010   beq  t0, zero, 0x1040 ┘
           ────────────────────── ← 截断：条件跳转
                                    下一 PC 有 2 种：0x1014（不跳）/ 0x1040（跳）
  0x1014   addi a0, a0, 16       ┐
  0x1018   j    0x1000           ┘ TB B
           ────────────────────── ← 截断：无条件跳转
                                    下一 PC 只有 1 种：0x1000（跳回 TB A，成环）
  0x1040   sub  t2, t2, t0       ┐
  0x1044   jalr ra, 0(t2)        ┘ TB D
           ────────────────────── ← 截断：间接跳转（jalr / 函数返回 / 跳转表）
                                    目标由寄存器决定，翻译期不可知
```

没有跳转也可能截断——纯顺序代码太长：

```text
  0x2000   add  a2, a2, a0       ┐
  0x2004   ...                    │
           ...（全是顺序指令）     │ TB E：没有任何跳转，
  0x27fc   xor  a3, a3, t1       ┘  但满 512 条（TCG_MAX_INSNS）
           ────────────────────── ← 截断：纯粹因为太长
                                    下一 PC 唯一：0x2800 顺序往下，另起 TB
```

注意 TB B 的 `j 0x1000` 跳回 TB A 形成一个环——**循环意味着 TB 会被反复执行和反复查找，这正是后面 chaining 要加速的场景**。

异常支持、MMU 模拟、profiling 是围绕这条主线的关联机制：异常和 MMU 解释了「查找键和失效为什么要这样设计」，profiling 是工具。

翻译流水线本身（guest → IR → host）不在这份文档里，见 `二进制翻译 & QEMU的TCG引擎.md`；源码落点见 `Qemu的TCG源码梳理.md`；读代码的顺序见 `TCG源码阅读顺序.md`。这一篇只管概念和机制，源码引用只作锚点。

文档六节与主线的对应关系：

| 机制 | 要回答的问题 | 归在 |
| --- | --- | --- |
| CPU state optimisations | 同一段 guest 代码，为什么可能译出不同的 TB | 查找（查找键的设计） |
| Direct block chaining | 执行完一个 TB，怎么尽快跳到下一个 TB | 查找 + 链接 |
| Self-modifying code | guest 改了自己的代码，旧 TB 怎么办 | 失效 |
| Exception support | 异常发生时，怎么找回 guest 现场 | 关联：解释为什么状态要按指令粒度记录 |
| MMU emulation | system mode 下访存为什么这么慢、又怎么加速 | 关联：物理索引、不跨页链接都是为 TB 缓存服务 |
| Profiling JITted code | JIT 出来的代码怎么用 perf 分析 | 关联：工具 |

## 1. CPU 状态优化：TB 与 CPU 状态强绑定

### 1.1 核心思想

目标 CPU 有很多内部状态会改变指令的语义。为了翻译速度，TCG 在**翻译阶段**就假定：某些 CPU 状态在这个 TB 内不会变。这些被假定的状态会记录在 TB 里（即 TB 的 flags）。

如果执行时状态变了（比如特权级切换），就**就地生成一个新 TB**；旧 TB 不会被删，而是缓存起来——下次运行上下文再次匹配旧 TB 记录的状态时，直接复用它。

### 1.2 为什么必须这样：一个 RISC-V 例子

```text
csrr t0, sstatus
```

这条指令就是读 S 模式的状态寄存器，但特权级不同，语义截然不同：

- U 模式：非法指令，trap
- S 模式：正常读取

所以翻译时：

- 处于 S 模式 → 生成读 `sstatus` 的 helper 调用
- 处于 U 模式 → 生成 trap 到异常处理的代码

**要建立的核心认知：CPU 的某些状态会影响翻译结果。同一段 guest 代码，CPU 状态不同，译出的 TB 可以完全不同。** 反过来说，一个 TB 只在它记录的 flags 所描述的状态下才是合法的。

### 1.3 另一个方向：状态相同就可以省代码

x86 上的例子：如果 SS/DS/ES 段基址为 0，翻译器连「段基址加法」都不生成。这是同一枚硬币的另一面——状态不只是正确性的约束，也是优化的依据。

### 1.4 源码锚点

- TB 查找键（哪些状态被记录）：`include/accel/tcg/tb-cpu-state.h`，`pc / flags / cflags / cs_base`
- guest 提供「取当前状态」的钩子：`TCGCPUOps.get_tb_cpu_state()`，RISC-V 侧在 `target/riscv/tcg/tcg-cpu.c`

## 2. 直接块链接（Direct Block Chaining）

### 2.1 最朴素的方式：每个 TB 执行完都回主循环

执行完一个 TB 后，要找到下一个 TB，最笨也最安全的流程是：

```text
当前 TB 执行完
  → TB epilogue 退出
  → 回到主循环
  → 用模拟 PC + CPU 状态查找（或现翻译）下一个 TB
  → 下一个 TB 的 prologue 进入
  → 执行
```

**为什么回主循环是必要的？因为中断。** 注意一个关键事实：TB 记录的那些 CPU 状态（flags）**不包括中断状态**。比如之前某个时刻 guest 关了中断，中断信号被 pending；之后某个 TB 把中断打开了——「打开中断」这个动作不会被 TB 的 flags 记录。因此「根据 flags 找到正确的 TB」这条路天然处理不了中断，改变中断状态这件事无法嵌入 TB 查找逻辑。

所以最保守的策略是：每个 TB 执行完都回主循环，重新评估一次 `cpu_exec_interrupt()`，处理 pending 的中断。文档明确说：**任何可能解除中断屏蔽的 CPU 状态变化之后，必须以这种退出的方式回到主循环**，这是强制性的。

安全，但每个 TB 都往返一次主循环，性能显然不好。于是有了下面两种优化。

### 2.2 优化一：`lookup_and_goto_ptr`

先建立一个重要认知：**一切带 `tcg_gen_*()` 前缀的函数，都是去生成一条 TCG 操作，而不是真的执行里面的动作。** `tcg_gen_lookup_and_goto_ptr()` 实际上是「发射」了一条 `call helper_lookup_tb_ptr` 指令进 IR——我们现在处于翻译阶段，这条 call 要等 TB 被执行时才真正跑。这类接口都是在生成代码，而不是执行代码。

机制：

1. 翻译期：`tcg_gen_lookup_and_goto_ptr()` 发出对 `helper_lookup_tb_ptr` 的调用
2. 执行期：helper 用当前 CPU 状态查找下一个 TB（只检查 TB flags 里记录的那些状态，不含中断）
   - 找到 → 返回目标 TB 的代码地址
   - 没找到 → 返回 JIT epilogue 的地址（做收尾后回主循环）
3. call 之后紧跟一条 TCG 的 `goto_ptr` opcode，跳到返回的地址

效果：要么直接跳进下一个 TB，要么回主循环，省掉了「先回主循环再查找」的固定往返。

适用场景与风险：适用于已经知道当前执行流是普通执行流、不存在会改变「影响翻译或中断的那些 CPU 状态」的情况。文档在实现层面没有强制规定使用条件，**如果对现状判断不当而错误使用，可能产生静默 bug**。

源码锚点：`helper_lookup_tb_ptr` 实现在 `accel/tcg/cpu-exec.c`，声明由 `accel/tcg/tcg-runtime.h` 的 `DEF_HELPER` 宏展开；`goto_ptr` 由后端 `tcg/<host>/` 落地。

### 2.3 优化二：`goto_tb + exit_tb`

#### 先弄清 TB 的边界

TB 的划分依据：从某个 guest PC 开始一路译下去，直到**执行流发生改变**的地方切断，改变后的指令归到下一个 TB。TB 边界可以总结为四种情况（开头图里的 TB E / B / A / D 分别对应情况 1 / 2 / 3 / 4）：

| 情况         | 例子                                      | 下一个 guest PC有几种可能      |
| ---------- | --------------------------------------- | ---------------------- |
| (1) 顺序指令太长 | 超过 TB 容纳的 guest 指令数 / TCG IR opcode 数上限 | 1 种（就是顺序往下）            |
| (2) 无条件跳转  | `j 0x1080`，目标是立即数                       | 1 种                    |
| (3) 条件跳转   | `beq` / `bne`                           | **最多 2 种**（进分支 / 顺序往下） |
| (4) 间接跳转   | `jalr`、函数返回、跳转表，翻译期不知道目标                | 1 种（槽位语义上按一种处理）        |

#### 机制：给每个 TB 挂两个可改写的 slot

在这个方法下，每个 TB 被附加了**最多两个可被改写的跳转槽位**（jump slot）。由上面的边界分析可知，一个 TB 的出口最多两种可能，所以两个槽位足够。

翻译期的三步：

1. `tcg_gen_goto_tb(idx)`：发出一条 `goto_tb` TCG 指令，将来会被译成「跳到 slot idx 关联的地址」。**初始时 slot 里填的是第 2 步代码的地址**
2. 发出更新 CPU 状态的 TCG 指令：把主循环定位下一个 TB 所需的信息写好。对大多数 guest 就是分支目标的 PC。这些信息必须能从 `cpu_get_tb_cpu_state()` 和 `cpu_restore_state()` 两侧推出来
3. `tcg_gen_exit_tb(tb, idx)`：退出当前 TB，返回一个「TB 地址 + slot 序号」拼出来的标记指针

#### 第一次执行：没有加速，但完成了「接线」

```text
                 第一次执行

     Guest TB A
         │
         ▼
      Host TB A
         │
         ▼
    goto_tb(slot0)
         │
    slot0 未绑定 ──→ 跳到第 2 步的代码
         │
         ▼
   cpu_pc = 0x1080        （更新 CPU 状态）
         │
         ▼
     exit_tb(A, 0)        （带著 A 和 slot0 退出）
         │
         ▼
    QEMU dispatcher（主循环）
         │
         ├── 查找 / 翻译 TB B
         │
         ▼
      Host TB B
         │
         └── patch A.slot0 → B     （主循环回填槽位）
```

第一次执行时，`goto_tb` 只是跳到第 2 步，更新状态、退出、回主循环——行为和 2.1 的朴素形式几乎一样。但关键动作发生在主循环里：找到（或现翻译）下一个 TB 之后，**主循环会把上一个 TB 的对应 slot 改写成新 TB 的地址**。

#### 第二次执行：直接跳，不回主循环

```text
                 第二次执行

      Host TB A
          │
          ▼
     goto_tb(slot0)
          │
          │ slot0 已绑定
          │
          └───────────────┐
                          ▼
                      Host TB B
```

之后每次执行到 TB A 的这个出口，slot 已 patch（且目标 TB 还在内存里），就直接跳进目标 TB 的第一条指令，完全绕开主循环。

#### 和优化一的对比

`goto_tb + exit_tb` 相当于把 `lookup_and_goto_ptr` 的**查询开销也省了**——第一次执行时付出一次回主循环的代价完成「接线」，之后就是零查询的直接跳转。非常适合出口目标固定的情况（边界分析里的 (1)(2) 类）。

#### 使用条件（文档硬性规定）

- CPU 状态的变化必须是**常量**：直接跳转可以，间接跳转不行（目标翻译期不可知）
- **直接跳转不能跨页**：内存映射可能变，目标地址处的代码可能已经不是原来那段了

#### 一个细节

第 3 步 `tcg_gen_exit_tb()` 除了 slot 序号，还返回了刚执行的 TB 的地址。这个地址对应的才是**将被 patch 的 TB**——如果主循环进入的那个 TB 之前已经链到了别的 TB，实际执行路径上的「上一个 TB」可能不是主循环直接启动的那个。

#### 源码锚点

- `tcg_gen_goto_tb` / `tcg_gen_exit_tb`：`tcg/tcg-op.c`
- 主循环侧的 patch：`tb_add_jump()` / `tb_set_jmp_target()`，`accel/tcg/cpu-exec.c`
- RISC-V 前端的用法标本：`target/riscv/translate.c` 的 `gen_goto_tb`

### 2.4 中断：谁来打断这条 TB 链

2.1 留下了一个问题：如果 TB 已经链成 `A → B → C → D`，执行流不再经过主循环，**中断岂不是迟迟得不到处理？**

#### 先修正一个错误的心智模型

容易以为 QEMU 是这样做的：

```text
A 执行完
  ↓
检查有没有中断
  ↓
  有中断？ ──yes──→ 回主循环
    │
    no
    ↓
 direct chaining 到 B
```

**QEMU 不是这么做的。** 它不会在「选路」时检查中断——chaining 决策与中断无关。真实设计是两层叠加：

```text
第一层：控制流加速
  goto_tb / lookup_and_goto_ptr
  回答：「下一个 TB 怎么快速过去？」

第二层：异步事件控制
  interrupt_request / exit_request / TB_EXIT_REQUESTED
  回答：「什么时候必须停下这条高速 TB 链？」
```

#### 机制：每个 TB 入口的轻量检查

普通 TB 在翻译时，开头会被插入一段检查（`accel/tcg/translator.c` 的 `gen_tb_start()`）：

```c
count = load(cpu->neg.icount_decr.u32);
if (count < 0) {
    goto exitreq_label;   // 出口处：tcg_gen_exit_tb(tb, TB_EXIT_REQUESTED)
}
```

也就是**每进入一个 TB，先问一句「是不是该退出了？」**，代价只是一次 load + 一次条件分支。只有带 `CF_NOIRQ` 标记的特殊 TB 才跳过这个检查（`include/exec/translation-block.h`）。

所以即使链已经 patch 好：

```text
TB A ──goto_tb──→ TB B ──goto_tb──→ TB C ──→ ...
```

也不意味着可以永远不受控制地跑下去。每进入一个 TB 都相当于：

```text
TB B 入口:
    if (exit_requested)
        return TB_EXIT_REQUESTED;   // 断链，回主循环
    // 否则照常执行 guest 指令
```

**关键认知：chaining 绕过的是「完整的 dispatcher / TB lookup」，不是绕过 QEMU 对执行的控制。**

#### 谁设置 exit request：外部异步 IRQ 到达

比如设备线程产生中断，走 `tcg_handle_interrupt()`（`accel/tcg/tcg-accel-ops.c`）：

```c
cpu_set_interrupt(cpu, mask);              // 记录 interrupt_request
if (!qemu_cpu_is_self(cpu)) {
    qemu_cpu_kick(cpu);                    // 别的线程：kick 目标 vCPU
} else {
    qatomic_set(&cpu->neg.icount_decr.u16.high, -1);   // 自己：直接设标志
}
```

kick 最终落到 `tcg_kick_vcpu_thread()`（`accel/tcg/cpu-exec.c`）：

```c
qatomic_store_release(&cpu->exit_request, true);
qatomic_store_release(&cpu->neg.icount_decr.u16.high, -1);
```

`u16.high = -1` 的用意：`icount_decr` 是个 union，把高 16 位写成全 1，整个 u32 读出来就是负数——于是 TB 入口的 `count < 0` 检查命中。`cpu_exec` 重新进入执行前会把它清零重新武装。

完整时序：

```text
设备线程 / 其他线程          vCPU 线程
        │                       │
  interrupt arrives             │
        │                       │
  cpu->interrupt_request |= ... │
        │                       │
     kick vCPU                  │
        │                  TB A 执行中
  exit_request = true           │
  icount_decr.u16.high = -1     │
        │                       │
        │                  TB A 执行完
        │                       │
        │                  direct chaining 照常发生
        │                       ▼
        │                  进入 TB B
        │                       │
        │                  入口检查 count < 0 → 命中
        │                       │
        │                       ▼
        │                  TB_EXIT_REQUESTED
        │                       │
        │                       ▼
        │                  cpu_exec_loop
        │                       │
        │                       ▼
        │              cpu_handle_interrupt()
```

注意断链的位置：**A → B 的 chaining 仍然发生了**，是在 B 的入口被拦下的。

#### 回到主循环之后：先过中断，再选 TB

`cpu_exec_loop()`（`accel/tcg/cpu-exec.c`）的结构保证了这一点：

```c
while (!cpu_handle_exception(cpu, &ret)) {
    while (!cpu_handle_interrupt(cpu, &last_tb)) {
        get_tb_cpu_state();
        tb = tb_lookup(...);
        cpu_loop_exec_tb(...);
    }
}
```

内层循环**每次准备选下一个 TB 之前，都要先过 `cpu_handle_interrupt()`**。所以链一旦被打断，中断一定在下一个 TB 执行前得到处理。文档里说的 `cpu_exec_interrupt()` 是 guest 侧的 hook（RISC-V 对应 `riscv_cpu_exec_interrupt()`，`target/riscv/cpu_helper.c`），由 `cpu_handle_interrupt()` 在判断可递送时调用。

#### 第二类情况：guest 自己打开了中断使能

和「外部突然来 IRQ」不同，还有一种是 guest 执行某条指令改变了中断使能：

```text
原来：interrupt pending = 1, interrupt enabled = 0
guest 执行某条指令（如 RISC-V 写 mstatus/sstatus）
之后：interrupt enabled = 1  →  那个早就 pending 的中断现在可响应了
```

这时**没有别的线程来 kick vCPU**，exit request 不会被设置，入口检查拦不住。如果翻译器照常 `goto_tb` 链走，这个刚解除屏蔽的中断就被错过了。

所以文档那条强制规则落在这里：**任何可能 unmask 中断的 CPU 状态变化之后，翻译器必须生成普通 TB 退出，回主循环重新评估中断**，不能链接：

```text
改变 interrupt enable
  ↓
exit TB（不 chain）
  ↓
main loop → cpu_handle_interrupt() 重新检查 pending
```

#### 两类情况对照

| 情况 | 谁让 vCPU 停下来 | 机制 |
| --- | --- | --- |
| 外部异步 IRQ 新到达 | 设备线程 / 其他线程 kick | 设置 interrupt_request + exit request，下一个 TB 入口检查命中，断链 |
| guest 改状态使旧的 pending IRQ 可响应 | 翻译器自己 | 这类指令所在的 TB 强制普通退出，回主循环重查中断 |

#### 这回答了 2.1 的问题

2.1 说「TB 的 flags 不包括中断状态」，现在可以说清为什么这样设计是合理的：**中断根本不靠「flags 不同 → 找另一种 TB」来解决**，而是靠：

```text
已有 TB（照常翻译、照常链接）
  + 每个 TB 入口的 exit request 检查
  + 必要时断链回 cpu_exec_loop，先过 cpu_handle_interrupt
```

几个结构至此连成一层：

```text
TB flags          → 决定「这个 TB 在什么 CPU 状态下有效」
direct chaining   → 决定「TB 之间怎么快速跳转」
exit request      → 决定「什么时候打断 TB chain」
cpu_handle_interrupt → 决定「当前 pending 的中断是否该递送」
```

## 3. 自修改代码与翻译代码失效

### 3.1 问题

x86 上模拟自修改代码（SMC）是个特殊挑战：**应用程序修改代码时，不会发出任何指令缓存失效信号**。QEMU 无从得知某段内存里的指令变了，而旧 TB 里还是按旧指令译的。

### 3.2 User mode：写保护 + SIGSEGV

- 每当为一个基本块生成翻译代码时，把对应的 **host 页标记为写保护**（如果本来不是只读）
- guest 往这个页写数据 → Linux 抛出 SEGV 信号
- QEMU 的信号处理里：**失效该页内所有已翻译的代码**，并放开写权限

### 3.3 System mode

写保护通过**软件 MMU** 实现，思路相同：对含翻译代码的页做写保护，写时触发失效。

### 3.4 高效失效的数据结构

- 每个物理页维护一个**链表**，挂着页内所有 TB → 页失效时能精确找到要删的 TB
- 另有链表用于**解除直接块链接**：TB 被失效后，所有指向它的 `goto_tb` slot 都要拆回未绑定状态，否则下次就跳进已死的代码了

### 3.5 RISC 目标上的补充

RISC 架构上，写得规范的软件会用内存屏障和缓存刷新指令，理论上部分保护可以不做。但 QEMU 仍然要求**生成的代码必须始终与内存中的目标指令一致**——这是为了异常时能正确还原现场（见下节）。

源码锚点：TB 失效在 `accel/tcg/tb-maint.c`；user mode 的信号方案在 `accel/tcg/user-exec.c`。

## 4. 异常支持

### 4.1 两条路径

| 异常类型 | 机制 |
| --- | --- |
| guest 指令语义级异常（如除零） | `longjmp()` 跳出 TB 执行 |
| guest 访存非法 | 复用 host 的 SIGSEGV / SIGBUS 信号处理 |

### 4.2 host PC → guest PC 的回溯

QEMU 维护一张 **host PC 到 guest PC 的映射**。异常发生时，根据崩溃点的 host PC 反查出异常发生在哪条 guest 指令。这就是 `-d` 日志和调试能对上 guest 汇编的基础。

源码锚点：`accel/tcg/translate-all.c` 的 `cpu_restore_state()`；翻译时每条 guest 指令的边界由 `insn_start` 记录。

### 4.3 延迟刷新的 CPU 状态

有些虚拟 CPU 状态**直到 TB 结束才写回内存**（`CPUX86State` 这类结构体），典型的是：

- x86 的 condition codes（标志位）
- SPARC 的 delay slot
- Arm 的条件执行

这些状态的共同点：程序很少直接读它们、但在一个 TB 内又变化极频繁——每条指令都写回太亏。代价是：异常发生在 TB 中间时，这些状态是「脏」的、没写回的。

解决办法：**按每条 guest 指令保存一份这些状态的信息**，异常时按指令粒度查表恢复。这也是为什么 3.5 说「生成代码必须和内存指令一致」——否则按 guest PC 恢复出来的现场就是错的。

## 5. MMU 模拟

### 5.1 软件 MMU 与 TLB

system emulation 下 QEMU 用**软件 MMU**：guest 的每一次访存都要做一次虚拟地址到物理地址的翻译。每次都走完整页表太慢，所以用 **TLB（地址翻译缓存）** 加速。

源码锚点：`accel/tcg/cputlb.c`；miss 时回调 guest 的 `tlb_fill`（RISC-V 在 `target/riscv/cpu_helper.c` 的 `riscv_cpu_tlb_fill`）。

### 5.2 物理索引：换页表不用刷 TB

**QEMU 里所有缓存都是物理索引的**——每个 TB 用它的 guest 物理地址做索引。

为什么？如果按虚拟地址索引，guest 一切换页表（进程切换），所有 TB 的虚拟地址含义全变了，就得清空全部翻译缓存。物理索引下，页表切换不改变「物理地址 → 代码」的对应关系，TB 缓存可以保留。

### 5.3 chaining 不跨页

同理，为了避免 MMU 映射变化时还要去拆 TB 链：**只有跳转目标和发起跳转的 TB 在同一页时，才做直接块链接**。跨页的跳转老老实实回主循环（或用 lookup_and_goto_ptr），因为目标页的映射可能变了。

### 5.4 RAM/ROM 与 MMIO 的分流

软件 MMU 还负责区分内存类型：

| 区域 | 访存方式 | 速度 |
| --- | --- | --- |
| RAM / ROM | TLB 里直接缓存了「guest 地址 → host 内存」的偏移，算出 host 指针直接访问 | 快 |
| MMIO | 调出去走 C 代码做设备模拟 | 慢 |

另外 MMU 还负责跟踪 **dirty pages**（热迁移等用）和**被 TB 引用的页**（配合第 3 节的失效机制）。

## 6. JIT 代码的性能分析

Linux `perf` 会把所有 JIT 代码当成一整块匿名代码——JIT 产物没有调试信息，perf 无法把采样到的 PC 关联回函数。解决办法是让 QEMU 生成映射文件：

| 选项 | 内容 | 开销 |
| --- | --- | --- |
| `-perfmap` | 只生成 guest→host 的映射 | 轻量 |
| `-jitdump` | 额外保存 JIT 代码和 guest 调试信息（如果有），需要先注入 `perf.data` 再看报告 | 重 |

```bash
# 轻量方案
perf record $QEMU -perfmap $REMAINING_ARGS
perf report

# 完整方案
perf record -k 1 $QEMU -jitdump $REMAINING_ARGS
DEBUGINFOD_URLS= perf inject -j -i perf.data -o perf.data.jitted
perf report -i perf.data.jitted
```

注意：`qemu-system` 只对 ELF 格式的 `-kernel` 文件生成映射。

源码锚点：`tcg/perf.c`。

## 7. 收束

把六块机制串起来，就是「一个 TB 的一生」中除翻译外的所有环节：

```text
            CPU 状态(flags) 决定 TB 的身份
                        │
                        ▼
   ┌─────────────────────────────────────┐
   │  主循环 cpu_exec_loop                │
   │  按 pc+flags 找 TB（物理索引）        │
   └─────────────────────────────────────┘
              │ hit              │ miss
              ▼                  ▼
        直接执行            翻译新 TB
              │                  │
              ▼                  ▼
        TB 之间用 goto_tb 直接链接（同页、直接跳转）
        或用 lookup_and_goto_ptr 免回主循环
              │
              ├── 中断 → 设置 exit request → 下一个 TB 入口检查命中 → 断链回主循环
              │   （guest 自己 unmask 中断的指令，翻译期就强制普通退出）
              ├── guest 写了代码页 → 写保护触发 → 页内 TB 全部失效、拆链
              ├── 异常 → longjmp / 信号 → host PC 反查 guest PC → 按指令恢复延迟状态
              └── 访存 → 软件 TLB：RAM 直译 host 指针，MMIO 走 C，映射变了不刷 TB
```

一句话总结：**TCG 的运行时设计，处处是在「缓存命中率」和「状态正确性」之间做交易**——flags 绑定换来翻译期优化，物理索引换来页表切换不刷缓存，slot 链接换来零查询跳转，而写保护、延迟状态恢复、每个 TB 入口的 exit 检查，则是为正确性付的账。
