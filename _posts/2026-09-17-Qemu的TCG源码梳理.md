这一篇我们来梳理一下QEMU中TCG相关部分的源码。

源码根目录默认是：

```text
qemu-camp-2026-k230/
```

---

## 1. 先分清三个「target」

读 TCG 源码时，最容易拧的是命名：

| 口语                     | QEMU 目录里常叫            | 本仓库对应                 |
| ---------------------- | --------------------- | --------------------- |
| 被模拟的 CPU / guest ISA   | `target/<arch>/`      | `target/riscv/`       |
| 跑 QEMU 的物理机 / host ISA | TCG 文档里的 *TCG target* | `tcg/x86_64/` 等       |
| QEMU 的「模拟整个机器」         | system mode           | `qemu-system-riscv64` |

`docs/devel/tcg-ops.rst` 写得很直白：TCG 的 *target* 永远是 host，不是 guest。所以：

- `target/riscv/` = **TCG 前端**（guest → IR）
- `tcg/<host>/` = **TCG 后端**（IR → host 机器码）
- `accel/tcg/` = **翻译缓存 + 执行循环**，不是编译器本体

上一篇流程图里的「TCG 前端 / IR / 优化器 / 后端」，在源码里并不是一个目录，而是上面这三块拼出来的。

另外再钉一个单位：QEMU 翻译的是 **Translation Block（TB）**，不是完整 trace。TB 一般译到分支、异常、页边界或指令数上限就停，再靠查找和 chaining 串起来。

## 2. 源码上的三层结构

```text
                    ┌─────────────────────────────────────────┐
                    │  accel/tcg/                             │
                    │  TCG 加速器：找 TB / 生成 TB / 执行 TB    │
                    │  cpu-exec.c  translate-all.c  tb-maint.c │
                    └───────────────┬─────────────────────────┘
                                    │  miss: 需要翻译
                                    v
        ┌───────────────────────────┴────────────────────────────┐
        │                                                        │
        v                                                        v
┌───────────────────────┐                          ┌──────────────────────────┐
│ target/riscv/         │  tcg_gen_* 发出 IR       │ tcg/                     │
│ Guest 前端            │ ─────────────────────►   │ 编译器本体               │
│ translate.c           │                          │ tcg.c  optimize.c        │
│ insn_trans/*.c.inc    │                          │ tcg/<host>/tcg-target*   │
│ *.decode + helper.c   │                          │ region.c（代码缓存）      │
└───────────────────────┘                          └────────────┬─────────────┘
                                                                │ host 机器码
                                                                v
                                                       TranslationBlock.tc.ptr
                                                                │
                                                                v
                                                       tcg_qemu_tb_exec()
```

读代码时按层走，不要按文件名字母序走：

1. `accel/tcg/`：引擎怎么被驱动
2. `target/riscv/`：一条 guest 指令怎么变成 IR
3. `tcg/`：IR 怎么变成 host 代码

## 3. 运行时总框架（按真实调用链）

下面这张图对应源码里的函数，不是抽象编译器流水线。

```text
vCPU 线程入口
  accel/tcg/tcg-accel-ops.c          tcg_cpu_exec()
  accel/tcg/tcg-accel-ops-mttcg.c    每 vCPU 一线程（默认，RISC-V 支持 MTTCG）
  accel/tcg/tcg-accel-ops-rr.c       单线程 round-robin（thread=single / icount）
           |
           v
  accel/tcg/cpu-exec.c               cpu_exec() → cpu_exec_loop()
           |
           +-- 处理 exception / interrupt / halt
           |
           +-- tcg_ops->get_tb_cpu_state()     取 PC + flags，作为 TB 查找键
           |     target/riscv/tcg/tcg-cpu.c
           |
           +-- tb_lookup()                     命中：直接执行
           |     accel/tcg/cpu-exec.c
           |     accel/tcg/tb-maint.c          TB 哈希表 / 失效
           |
           +-- miss → tb_gen_code()            生成一个新 TB
           |     accel/tcg/translate-all.c
           |           |
           |           +-- tcg_ops->translate_code()
           |           |     target/riscv/translate.c
           |           |     riscv_translate_code()
           |           |           |
           |           |           +-- translator_loop()          通用「译到 TB 结束」循环
           |           |                 accel/tcg/translator.c
           |           |                 include/exec/translator.h
           |           |                       |
           |           |                       +-- 每条 guest 指令:
           |           |                             decode_opc()
           |           |                             decode_insn32 / decode_insn16
           |           |                             trans_addi / trans_lw / ...
           |           |                             → tcg_gen_*() 写入 TCGOp 链表
           |           |
           |           +-- tcg_gen_code()             IR → host 机器码
           |                 tcg/tcg.c
           |                       |
           |                       +-- tcg_optimize()            tcg/optimize.c
           |                       +-- liveness / reachable
           |                       +-- tcg_out_*()               tcg/<host>/tcg-target.c.inc
           |                       +-- 写入 code buffer          tcg/region.c
           |
           +-- cpu_tb_exec()
                 accel/tcg/cpu-exec.c
                 → tcg_qemu_tb_exec()          跳进 TB 的 host 代码
                 → 退出后可能 tb_add_jump()    把两条 TB 直接链上（goto_tb）
```

和上一篇流程图的对应关系：

| 上一篇的框 | 源码落点 |
| --- | --- |
| Guest CPU 指令流 | TB 起始 PC；`translator_loop` 按 PC 取指 |
| TCG 前端 | `target/riscv/translate.c` + `insn_trans/` + `*.decode` |
| TCG IR | `include/tcg/tcg-opc.h` 定义的 `TCGOp`；由 `tcg_gen_*` 追加 |
| TCG 优化器 | `tcg/optimize.c`，在 `tcg_gen_code()` 里调用 |
| TCG 后端 | `tcg/<host>/tcg-target.c.inc`，被 `tcg/tcg.c` `#include` |
| Host machine code | `TranslationBlock.tc.ptr`，内存来自 `tcg/region.c` |
| CPU 执行 | `cpu_tb_exec()` → `tcg_qemu_tb_exec()` |

IR 本身没有单独的「IR 文件」。它是翻译时挂在 `TCGContext` 上的操作链表。

## 4. `accel/tcg/`：加速器运行时

这一层回答：何时翻译、译完的代码放哪、下次怎么找到、怎么跳进去执行。它不认识 RISC-V 的具体指令。

### 4.1 执行循环与 TB 查找

| 路径 | 在引擎里的角色 |
| --- | --- |
| `accel/tcg/cpu-exec.c` | 主循环。`cpu_exec` / `cpu_exec_loop` / `tb_lookup` / `cpu_tb_exec` / `tb_add_jump`；TB chaining 的补丁也在这里 |
| `accel/tcg/cpu-exec-common.c` | 与 user/system 共用的执行辅助 |
| `accel/tcg/translate-all.c` | **翻译入口**。`tb_gen_code()` 分配 TB，调用前端 `translate_code`，再调用 `tcg_gen_code()`；顺带 `cpu_restore_state`（host PC → guest PC） |
| `include/exec/translation-block.h` | `TranslationBlock` 定义：guest PC、flags、生成代码指针、jmp slot |
| `include/accel/tcg/tb-cpu-state.h` | TB 查找键：`pc / flags / cflags / cs_base` |
| `include/accel/tcg/cpu-ops.h` | `TCGCPUOps`：每个 guest 必须填的钩子（`translate_code`、`get_tb_cpu_state`、`tlb_fill`…） |

### 4.2 TB 缓存、失效、代码页

| 路径 | 在引擎里的角色 |
| --- | --- |
| `accel/tcg/tb-maint.c` | TB 哈希、插入、物理页失效、`tb_flush` |
| `accel/tcg/tb-context.h` | 全局 `TBContext`（哈希表） |
| `accel/tcg/tb-hash.h` | TB 哈希计算 |
| `accel/tcg/tb-jmp-cache.h` | 每 CPU 的 jmp cache，加速「上一个 TB → 下一个 TB」 |
| `accel/tcg/tb-internal.h` | TB 页锁定、失效内部接口 |
| `include/exec/tb-flush.h` | 对外的 flush API |

自修改代码、页表更换、breakpoint 最终都会走到「让某些 TB 失效」。这一层就是缓存维护，不是译码。

### 4.3 通用翻译循环

| 路径 | 在引擎里的角色 |
| --- | --- |
| `accel/tcg/translator.c` | `translator_loop()`：对所有 guest 共用的「一条条译，直到 TB 该结束」 |
| `include/exec/translator.h` | `DisasContextBase`、`TranslatorOps`（`translate_insn` / `tb_stop`…） |

guest 前端只要实现一组 `TranslatorOps`，再调用 `translator_loop()`。RISC-V 的实现见第 6 节。

### 4.4 软件 MMU / 访存

system mode 下，guest 的 load/store 不能直接当 host 指针用。TCG 生成的是「走软件 TLB」的访存。

| 路径 | 在引擎里的角色 |
| --- | --- |
| `accel/tcg/cputlb.c` | 软件 TLB：VA→host 地址缓存；miss 时调 guest 的 `tlb_fill` |
| `include/exec/cputlb.h` | TLB 对外接口 |
| `include/accel/tcg/cpu-ldst.h` | helper 里用的 `cpu_ld*` / `cpu_st*` |
| `include/accel/tcg/cpu-ldst-common.h` | 与 guest 无关的 ldst 公共部分 |
| `include/accel/tcg/cpu-mmu-index.h` | MMU index（user/kernel/…） |
| `include/accel/tcg/probe.h` | 探测某地址能否访问（不真正完成访存） |
| `include/accel/tcg/iommu.h` | IOMMU 相关 |
| `accel/tcg/backend-ldst.h` | 后端生成 qemu_ld/st 慢路径时用 |
| `accel/tcg/ldst_common.c.inc` / `ldst_atomicity.c.inc` / `atomic_*.h` | 原子访存、对齐、endian 模板 |

RISC-V 的缺页填充不在这里，而在 `target/riscv/cpu_helper.c` 的 `riscv_cpu_tlb_fill`，通过 `TCGCPUOps.tlb_fill` 挂上来。

### 4.5 通用 helper、统计、调试

有些操作 IR 不想直接展开成 host 指令，会生成 `call helper_xxx`。

| 路径 | 在引擎里的角色 |
| --- | --- |
| `accel/tcg/tcg-runtime.c` | 与 guest 无关的 helper：除法、clz、`lookup_tb_ptr`、`exit_atomic`… |
| `accel/tcg/tcg-runtime-gvec.c` | 通用向量 helper |
| `accel/tcg/tcg-runtime.h` | 上述 helper 的 `DEF_HELPER_*` 声明 |
| `accel/tcg/plugin-gen.c` | 翻译时插入 TCG plugin 回调 |
| `accel/tcg/tcg-stats.c` | TCG 统计 |
| `accel/tcg/monitor.c` | HMP/QMP 里和 TCG 相关的监控命令 |
| `accel/tcg/watchpoint.c` | 数据观察点 |
| `accel/tcg/icount-common.c` | 指令计数公共逻辑 |

`helper_lookup_tb_ptr` 就是文档里 `lookup_and_goto_ptr` chaining 的实现：TB 结尾不回主循环，先问一句「下一块 TB 现成吗」。

### 4.6 加速器对象与 vCPU 调度

| 路径 | 在引擎里的角色 |
| --- | --- |
| `accel/tcg/tcg-all.c` | 把 TCG 注册成一种 Accel（和 KVM 并列） |
| `accel/tcg/tcg-accel-ops.c` | `tcg_cpu_exec`、cflags、踢 vCPU |
| `accel/tcg/tcg-accel-ops-mttcg.c` | Multi-threaded TCG：每个 vCPU 一条 host 线程 |
| `accel/tcg/tcg-accel-ops-rr.c` | 旧的单线程 round-robin |
| `accel/tcg/tcg-accel-ops-icount.c` | `-icount`：为了可复现，强制串行 |
| `include/system/tcg.h` | `tcg_enabled()` / `qemu_tcg_mttcg_enabled()` |
| `include/accel/tcg/cpu-loop.h` | cpu loop 相关声明 |

### 4.7 user mode 特有

| 路径 | 在引擎里的角色 |
| --- | --- |
| `accel/tcg/user-exec.c` | linux-user：用 host SIGSEGV 捕捉对代码页的写，从而失效 TB（自修改代码） |
| `accel/tcg/user-exec-stub.c` | system mode 下给上述接口的空实现 |

本仓库跑的是 `qemu-system-riscv64`，日常读 system 路径即可。user mode 是同一套 TCG 编译器，只是「代码失效」机制不同。

## 5. `tcg/`：编译器本体

这一层不认识 RISC-V。它只看见 `TCGOp` 链表，负责优化，并把它编成当前 host 的机器码。

### 5.1 IR 与代码生成核心

| 路径 | 在引擎里的角色 |
| --- | --- |
| `include/tcg/tcg-opc.h` | TCG IR 操作码表：`add` / `ld` / `brcond` / `qemu_ld` / `call`… |
| `include/tcg/tcg.h` | `TCGContext`、临时变量、`tcg_gen_code` / `tcg_qemu_tb_exec` 声明 |
| `include/tcg/tcg-op-common.h` | 与 guest 位宽无关的 `tcg_gen_*` |
| `include/tcg/tcg-op.h` | 带 `target_long` 的 `tcg_gen_*`（前端真正 include 的） |
| `include/tcg/tcg-op-mem.h` | `tcg_gen_qemu_ld/st*` |
| `include/tcg/tcg-op-gvec.h` / `tcg-op-gvec-common.h` | 通用向量 IR |
| `include/tcg/tcg-cond.h` | 比较条件 |
| `include/tcg/tcg-mo.h` | memory order / barrier |
| `include/tcg/tcg-ldst.h` | 后端 ld/st 相关 |
| `tcg/tcg.c` | **编译器主文件**：emit IR、寄存器分配、`tcg_gen_code()`；`#include "tcg-target.c.inc"` 掺入 host 后端 |
| `tcg/tcg-op.c` | `tcg_gen_add_i32` 这类 API 的实现，真正往链表里塞 `TCGOp` |
| `tcg/tcg-op-ldst.c` | guest 访存 IR；可能展开成 TLB 快路径 |
| `tcg/tcg-op-gvec.c` / `tcg-op-vec.c` | 向量 IR 的展开或直出 |
| `tcg/tcg-common.c` | 与 user/system 都链上的公共部分 |
| `tcg/tcg-internal.h` / `tcg-has.h` | 编译器内部头 |

`meson.build` 会给 `tcg/<host_arch>/` 加 `-iquote`，所以 `tcg.c` 里写 `#include "tcg-target.c.inc"` 时，实际读到的是当前 host 那一份。

### 5.2 优化与代码缓存

| 路径 | 在引擎里的角色 |
| --- | --- |
| `tcg/optimize.c` | IR 优化：常量传播、拷贝传播、死代码等。对应日志 `-d op_opt` |
| `tcg/region.c` | 可执行代码缓冲区（JIT region）、TB 按 host PC 反查 |
| `tcg/perf.c` | `-perfmap` / `-jitdump`，让 Linux perf 能对上 JITed 代码 |
| `tcg/debuginfo.c` | 调试信息 |

`tcg_gen_code()` 的顺序大致是：dump 原始 IR（`-d op`）→ `tcg_optimize` → liveness → dump 优化后 IR（`-d op_opt`）→ host 后端 emit → 得到 TB 机器码（`-d out_asm`）。

### 5.3 Host 后端（TCG target）

每个 host 一个子目录，文件角色相同：

```text
tcg/<host>/
  tcg-target.h              寄存器、调用约定、能否直接发射某类 op
  tcg-target.c.inc          真正的指令选择 / 寄存器分配配合 / prologue
  tcg-target-opc.h.inc      该 host 额外的 opcode
  tcg-target-has.h          该 host 具备哪些 TCG 能力
  tcg-target-mo.h           该 host 的 memory order
  tcg-target-con-set.h      constraint set（操作数约束）
  tcg-target-con-str.h      constraint 字符串
```

本树里的 host 后端：

| 目录 | 含义 |
| --- | --- |
| `tcg/x86_64/` | x86-64 host（最常见） |
| `tcg/aarch64/` | ARM64 host |
| `tcg/riscv64/` | RISC-V host（注意：这是 **host**，不是 guest 前端） |
| `tcg/ppc64/` `tcg/s390x/` `tcg/sparc64/` `tcg/loongarch64/` | 其他 native 后端 |
| `tcg/tci/` + `tcg/tci.c` | TCG Interpreter：没有 native 后端时，把 IR 编成字节码再解释执行 |

TCI 不是 guest 解释器。它解释的是 TCG 自己的字节码，用来在没有 native backend 的 host 上跑 TCG。性能差很多，`configure --enable-tcg-interpreter` 才走这条路。

## 6. `target/riscv/`：本仓库的 Guest 前端

这一层认识 RISC-V 指令，不认识 x86。它的工作是：取出 16/32 位编码，调用 `tcg_gen_*`，必要时 `gen_helper_*`。

### 6.1 挂到加速器上

| 路径 | 在引擎里的角色 |
| --- | --- |
| `target/riscv/tcg/tcg-cpu.c` | 填 `riscv_tcg_ops`：`translate_code = riscv_translate_code`，以及 `tlb_fill` / `do_interrupt` 等 |
| `target/riscv/tcg/tcg-cpu.h` | 上述声明 |
| `target/riscv/cpu.c` | `cc->tcg_ops = &riscv_tcg_ops`，把前端接到 CPU 对象 |

没有这份表，`accel/tcg/` 不知道 RISC-V 怎么译。

### 6.2 译码与逐条翻译

| 路径 | 在引擎里的角色 |
| --- | --- |
| `target/riscv/translate.c` | RISC-V 前端总入口。`riscv_translate_code` → `translator_loop`；`decode_opc` 取指；include 所有 `trans_*.c.inc`；GPR/FPR 的 TCG global |
| `target/riscv/insn32.decode` | 32 位指令的 decodetree 模式（构建时生成 `decode-insn32.c.inc`） |
| `target/riscv/insn16.decode` | C 扩展 16 位指令 |
| `target/riscv/xthead.decode` 等 | 厂商扩展的译码表 |
| `scripts/decodetree.py` | 把 `.decode` 生成 `decode_insn32()` 这类匹配函数 |
| `docs/devel/decodetree.rst` | 译码 DSL 说明 |
| `target/riscv/insn_trans/trans_rvi.c.inc` | RV32/64I：`addi` / `lw` / `jal`… 的 `trans_*` |
| `target/riscv/insn_trans/trans_rvm.c.inc` | M 扩展 |
| `target/riscv/insn_trans/trans_rva.c.inc` | A 扩展（原子） |
| `target/riscv/insn_trans/trans_rvf.c.inc` / `trans_rvd.c.inc` | F/D 浮点 |
| `target/riscv/insn_trans/trans_rvv.c.inc` | 向量 |
| `target/riscv/insn_trans/trans_privileged.c.inc` | CSR / 特权指令 |
| 同目录其余 `trans_*.c.inc` | 其他扩展，命名即 ISA 名 |

一条普通整数指令的路径可以记成：

```text
translator_loop
  → riscv_tr_translate_insn          translate.c
  → decode_opc                       按 PC 取 2/4 字节
  → decode_insn32 / decode_insn16    由 .decode 生成
  → trans_addi()                     insn_trans/trans_rvi.c.inc
  → tcg_gen_addi_tl()                include/tcg/tcg-op.h
```

`trans_*` 返回 `true` 表示认出了这条指令。所有 decoder 都认不出，就 `gen_exception_illegal`。

### 6.3 Helper：IR 不想直译的语义

浮点、异常、复杂 CSR、向量里的很多操作，前端会生成对 C 函数的调用，而不是一长串 TCG op。

| 路径 | 在引擎里的角色 |
| --- | --- |
| `target/riscv/helper.h` | `DEF_HELPER_*` 清单，构建时展开成原型和 `gen_helper_*` |
| `include/exec/helper-gen.h` | 展开「生成 call 的前端 API」 |
| `include/exec/helper-proto.h` | 展开 C 原型 `helper_xxx` |
| `include/exec/helper-head.h.inc` | helper 类型系统（`i32`/`tl`/`env`…） |
| `target/riscv/op_helper.c` | 异常、特权、通用 helper 实现 |
| `target/riscv/fpu_helper.c` | 浮点 helper |
| `target/riscv/vector_helper.c` | 向量 helper |
| `target/riscv/cpu_helper.c` | `tlb_fill`、中断、地址翻译（执行期，不只是翻译期） |
| `target/riscv/csr.c` | CSR 读写 |
| 其他 `*_helper.c` | 对应扩展 |

约定：翻译期用 `gen_helper_foo()` 发出 `call`；执行期跳进 `helper_foo()`。两者由同一份 `helper.h` 生成，不要手写一对声明。

### 6.4 CPU 状态（翻译时当「全局变量」）

| 路径 | 在引擎里的角色 |
| --- | --- |
| `target/riscv/cpu.h` | `CPURISCVState`：guest 寄存器、CSR、PC |
| `target/riscv/cpu.c` | CPU 对象、特性、reset |
| `target/riscv/internals.h` | 前端/helper 共享的内部声明 |

`riscv_translate_init()` 里会把 `env->gpr[i]` 注册成 TCG global。之后 `trans_addi` 读写的不是 C 局部变量，而是「指向 `CPURISCVState` 字段的 IR 寄存器」。

## 7. Helper / Plugin / 文档 / 测试 各算哪一层

这些常被搜到，但不属于「编译器核心」。

| 路径 | 算哪一层 |
| --- | --- |
| `include/exec/helper-*.h*` | helper 声明的宏展开，前后端都用 |
| `plugins/` + `include/plugins/` | TCG plugin 运行时（插桩框架） |
| `accel/tcg/plugin-gen.c` | 翻译期把 plugin 变成 IR |
| `docs/devel/index-tcg.rst` | TCG 文档总目录 |
| `docs/devel/tcg.rst` | TB、chaining、SMC、软件 MMU |
| `docs/devel/tcg-ops.rst` | 每条 TCG IR 的语义 |
| `docs/devel/decodetree.rst` | `.decode` 语法 |
| `docs/devel/multi-thread-tcg.rst` | MTTCG |
| `docs/devel/tcg-icount.rst` | icount |
| `docs/devel/tcg-plugins.rst` | plugin |
| `tests/tcg/` | **不是引擎**。这是拿 TCG 跑的 guest 测试程序 |
| `disas/` | `-d in_asm,out_asm` 反汇编 guest/host 用 |

官方文档和源码目录是对齐的，遇到概念先看 `docs/devel/tcg.rst`，再跳进对应 `.c`。

## 8. 和 `-d` 日志的对照

学习时用：

```text
-d in_asm,op,op_opt,out_asm
```

| 日志 | 对应阶段 | 主要源码 |
| --- | --- | --- |
| `in_asm` | 即将翻译的 guest 汇编 | 前端 `disas_log` / translator 取指之后 |
| `op` | 优化前的 TCG IR | `tcg/tcg.c` 里 `tcg_dump_ops`，`CPU_LOG_TB_OP` |
| `op_opt` | 优化后的 TCG IR | `tcg/optimize.c` 之后再次 dump |
| `out_asm` | 生成的 host 汇编 | host 后端 emit 完的机器码 |
| `exec` | 实际执行了哪个 TB | `cpu-exec.c` 的 `cpu_tb_exec` / chaining 日志 |

一条 `addi` 建议按 `in_asm → op → op_opt → out_asm` 看四次，四份日志分别落在第 6、5.1、5.2、5.3 节。

## 9. 建议的阅读顺序

完整顺序（按 TB 的一生、含过关标准）见同目录 `TCG源码阅读顺序.md`。

不要从 `tcg.c` 第一行读起，也不要按文件大小读。TCG 自己的链是：产品（TB）→ 主循环怎么用 → `tb_gen_code` 外壳 → `translator_loop` → IR → `tcg_gen_code` 骨架 → 执行与 chaining → helper / 失效 → 最后才是寄存器分配和 host 后端。前后端只当标本。

## 10. 一张图收束

把上一篇的「编译器流水线」和这一篇的「源码分层」叠在一起：

```text
Guest RISC-V 指令
        │
        │  target/riscv/translate.c
        │  target/riscv/insn_trans/*.c.inc
        │  target/riscv/*.decode  (+ scripts/decodetree.py)
        v
   TCG IR (TCGOp 链表)
        │  include/tcg/tcg-opc.h
        │  tcg/tcg-op.c
        │  复杂语义 → gen_helper_* → target/riscv/*_helper.c
        v
   优化后的 IR
        │  tcg/optimize.c
        v
   Host 机器码（写入 TB）
        │  tcg/tcg.c + tcg/<host>/tcg-target.c.inc
        │  代码缓冲区：tcg/region.c
        v
   查找 / 链接 / 执行 TB
           accel/tcg/cpu-exec.c
           accel/tcg/tb-maint.c
           访存走 accel/tcg/cputlb.c
```

之后如果要对着一条具体指令往下挖，入口就是第 9 节的第 5 步：`trans_rvi.c.inc` 里的某一个 `trans_*`。

## 11. 代码量：只算 TCG 本身

前后端里很大一块是 ISA，不能算进 TCG：

- `target/riscv/`：guest 指令怎么译、CSR/异常/页表怎么模拟 → RISC-V
- `tcg/x86_64/` 等、`tcg/tci.c`：host 指令怎么选、怎么编码 → 宿主机 ISA（或解释器）

TCG 自己只剩下两块：**编译器**（IR / 优化 / 寄存器分配 / 代码缓存）和 **ISA 无关的 DBT 运行时**（TB、翻译循环外壳、查找与 chaining）。

行数是这一棵树的物理行，含空行和注释，只用来建立数量级。

### 11.1 算进 TCG 的

| 口径 | 范围 | 行数 |
| --- | --- | --- |
| 编译器内核 | `tcg/` 根目录（去掉 `tci.c`）+ `include/tcg/` | ~2.4 万 |
| 去掉 TCG 自己的向量 IR 之后 | 上一项再去掉 `*gvec*`、`tcg-op-vec.c` | ~1.9 万 |
| DBT 运行时 | `translator_loop`、`tb_gen_code`、`cpu_exec`、TB 缓存、通用 helper | ~0.6 万 |
| 软件 TLB 机制（不含 RISC-V 走页表） | `cputlb.c` 及配套头 | ~0.4 万 |
| **标量 TCG（推荐口径）** | 编译器（无 gvec）+ DBT 运行时 | **~2.6 万** |
| 再加上软 MMU 机制 | 上一行 + `cputlb` | ~3.0 万 |

真正必须啃的大约 16 个文件、~2.2 万行，而且高度集中：

```text
 7046  tcg/tcg.c                         编译器主文件：op 链表、liveness、寄存器分配、tcg_gen_code
 3272  tcg/optimize.c                    IR 优化
 2622  tcg/tcg-op.c                      tcg_gen_* 怎么变成 TCGOp
 1348  tcg/tcg-op-ldst.c                 qemu_ld/st 这类「TCG 的访存 IR」
 1224  accel/tcg/tb-maint.c              TB 哈希 / 失效
 1090  accel/tcg/cpu-exec.c              主循环、执行、chaining
  982  include/tcg/tcg.h                 TCGContext
  909  tcg/region.c                      JIT 代码缓冲区
  639  accel/tcg/translate-all.c         tb_gen_code
  584  include/tcg/tcg-op-common.h
  522  accel/tcg/translator.c            与 ISA 无关的翻译循环
  其余头文件：translator.h / translation-block.h / cpu-ops.h / tcg-opc.h
```

`tcg-op-gvec.c`（~4100）是 TCG 的向量 IR，不是 RISC-V V。学标量引擎可以整块后置。

### 11.2 不算进 TCG 的（对照）

| 范围 | 行数 | 实际是什么 |
| --- | --- | --- |
| `target/riscv/`（不含 kvm） | ~5.0 万 | guest ISA + 这份 CPU 的模拟 |
| 其中 `csr.c` / `vector_helper.c` / `trans_rvv.c.inc` | ~1.7 万 | 手册级语义 |
| 一个 host 后端 `tcg/x86_64/` | ~0.5 万 | host ISA 指令选择 |
| 全部 host 后端合计 | ~3.3 万 | 换一台宿主机才需要另一份 |

实验的时候仍然会**路过**前端：要用一条 `addi` 看见 IR，就得打开 `trans_rvi.c.inc`。那是标本，不是 TCG 课程本身。看懂 `tcg_gen_addi_tl` 之后发生了什么，才算 TCG。

### 11.3 只学核心 TCG，大概要多久

假设每周 **8～12 小时**，背景是已经有虚拟化/二进制翻译的总览，不把 RISC-V 手册和 x86 指令选择算进进度。

| 目标 | 能做到什么 | 时间 |
| --- | --- | --- |
| 地图 | TB、IR、优化、后端接口、主循环各在哪 | **几天** |
| IR 和 TB 跑通 | 对着 `-d op,op_opt` 讲清一条 TB 如何生成、查找、chain、退出 | **2～3 周**（约 20～30 小时） |
| 比较完整（核心） | 优化器在干什么、`tcg.c` 里临时变量 / liveness / 寄存器分配的主路径、helper call 约定、代码缓存、失效 | **1.5～3 个月** |
| 软 MMU 也算核心 | 上一档 + TLB 快路径 / miss / 为什么 TB 用物理索引 | 再加 **2～4 周** |

更直的一句话：**核心 TCG 按两个月业余时间来规划是合适的**；三个月是把 `tcg.c` 啃到能自己推寄存器分配，而不是把前后端 ISA 读完。

`tcg.c` 7000 行是整份核心里最硬的一块，时间不要按 2.6 万行做除法。`trans_*` 和 `tcg-target.c.inc` 当作实验夹具：需要时打开，不计入 TCG 进度。
