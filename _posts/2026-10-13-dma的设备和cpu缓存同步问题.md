DMA是一种可以不依赖CPU手动搬运数据的高效的数据传输技术，它允许在中断驱动下，让外设和内存直接交互，从而解放CPU的双手。不过，在现代非一致性内存架构的背景下，这种方式也随之会带来缓存同步问题，如果没有得到妥善的处理，就会导致cpu或者设备获取到错误的数据，造成语义的破坏。因此，我们这一节来讨论一下dma场景下外设和cpu的缓存同步问题。

### 缓存一致性协议

为了加速内存的访问，现代CPU采用了多级缓存的技术，使得CPU不必每次都发起昂贵的内存I/O调用，而优先从自己的私有缓存中获取数据。而这就带来了一个数据一致性问题：不同的核心针对同一个缓存行，要怎么同步他们之间的数据？业界提出了多种解决方案来妥善解决这个问题，如MESI， MOESI协议等等。

但是，这些一致性协议是用于CPU核心之间的数据同步问题，非核心的主体，如外设，是不被涵盖在内的。而在DMA背景下，外设和内存之间又产生了直接的联系：外设可以主动读取或者写入某块内存。而由于缓存行的存在，就有可能导致CPU和外设之间的数据不同步：
-  CPU对DMA buffer发起写事务，这个写事务有可能首先进入buffer对应的缓存行，而没有马上write-back. 此时，设备对这块内存的读事务，读到的就是旧数据，而不是CPU新写入的。
-  设备对DMA buffer发起写事务。这个写事务是直接作用到内存上的。然而，由于缓存的存在，CPU可能优先读取其缓存的内容(如果DMA buffer被缓存了， Linux并不会阻止这件事情的发生)，从而导致CPU读取到旧的内容。

以上场景的本质问题在于缓存一致性协议无法协调外设和CPU之间的一致性。因此，在这些有可能破坏一致性的边界处，就需要我们做额外的处理，来保证这个一致性。

### DMA数据流向

Linux中定义了几个方向参数，这个参数需要在调用map_* 接口时提供：

| Direction           | 设备对内存的操作     | 数据流向    | 典型场景           |
| ------------------- | ------------ | ------- | -------------- |
| `DMA_TO_DEVICE`     | Read         | 内存 → 设备 | 网卡发送 TX        |
| `DMA_FROM_DEVICE`   | Write        | 设备 → 内存 | 网卡接收 RX        |
| `DMA_BIDIRECTIONAL` | Read + Write | 双向      | 设备读取并修改 Buffer |
| `DMA_NONE`          | 无            | 无效方向    | 调试用途           |

例如，网卡发送数据包，CPU 先把数据包写入 Buffer，然后网卡通过 DMA 读取 Buffer，所以使用 `DMA_TO_DEVICE`。网卡接收数据包时，网卡通过 DMA 将数据写入 Buffer，然后 CPU 读取，所以使用 `DMA_FROM_DEVICE`。

map_* 用于CPU为某次DMA事务准备缓冲区，而unmap_* 则一般表示设备已经处理完了这次DMA事务，可以把缓冲区归还给内核。还是考虑网卡，考虑接受数据包。内核先map_* 准备缓冲区后，网卡写入，驱动确认写完，然后unmap_* ，CPU再去读取buffer的内容。

在一次事务中，map_* 和unmap_* 是成对的，他们的方向参数也要保持一致：
```c
dma_addr = dma_map_single(dev, buf, size,
                          DMA_FROM_DEVICE);

/* 设备 DMA Write */

/* DMA 完成 */
dma_unmap_single(dev, dma_addr, size,
                 DMA_FROM_DEVICE);

/* CPU 读取 buf */
```

从以上分析我们可以知道，对于不同的方向，在map和unmap处需要做如下缓存事务：

|DMA Direction|`dma_map_*()`|`dma_unmap_*()`|
|---|---|---|
|`DMA_TO_DEVICE`|Clean|无需 Cache 操作|
|`DMA_FROM_DEVICE`|Clean|Invalidate|
|`DMA_BIDIRECTIONAL`|Clean|Invalidate|
### 一致性保持——手动维护

这是最简单的方式了。具体来说，在边界处，我们要如此做：
-  CPU发起写事务后，要马上执行缓存刷新，把缓存中的内容刷到内存中，使得外设可以读到最新的数据。
-  外设发起写事务后，CPU要首先write-back自己的缓存行，然后主动废除自己的缓存行，从而在缓存一致性协议下，强制自己从内存重新读取内容。

我们去Linux的主线内核，可以看到如下的代码段：
```c
// kernel/dma/direct.c — dma_direct_map_phys()
/* 设备不具备一致性能力，并且用户没有说这次操作不需要维护缓存，并且非MMIO访问 */
if (!dev_is_dma_coherent(dev) &&
    !(attrs & (DMA_ATTR_SKIP_CPU_SYNC | DMA_ATTR_MMIO))) {
    /* 架构相关的缓存维护 */
    arch_sync_dma_for_device(phys, size, dir);
    if (flush)
        arch_sync_dma_flush();
}

// kernel/dma/direct.c — dma_direct_unmap_phys
if (!(attrs & DMA_ATTR_SKIP_CPU_SYNC))
	dma_direct_sync_single_for_cpu(
		dev, addr, size, dir, flush);

// dma_direct_sync_single_for_cpu()
if (!dev_is_dma_coherent(dev)) {
    arch_sync_dma_for_cpu(paddr, size, dir);

    if (flush)
        arch_sync_dma_flush();

    arch_sync_dma_for_cpu_all();
}
```

对于arm64, 其同步代码是：
```c
void arch_sync_dma_for_device(phys_addr_t paddr, size_t size,
                              enum dma_data_direction dir)
{
    unsigned long start = (unsigned long)phys_to_virt(paddr);
	/* clean: 把数据从缓存行写回内存 */
    dcache_clean_poc_nosync(start, start + size);
}

void arch_sync_dma_for_cpu(phys_addr_t paddr, size_t size,
                           enum dma_data_direction dir)
{
    unsigned long start = (unsigned long)phys_to_virt(paddr);

    if (dir == DMA_TO_DEVICE)
        return;
	/* invalidate：使CPU的缓存行失效 */
    dcache_inval_poc_nosync(start, start + size);
}
```

可以看到，都是通过手动调用这些架构相关的缓存维护代码来实现一致性。


### 架构支持

除了手动维护，某些架构还原生提供了某些机制，来使得我们不用手动维护这些事务。不过，一般这种架构支持多用于dma_alloc_coherent这种持久buffer的使用，而不用于map_single这种处理临时事务的。这个函数的接口如下：
```c
dma_addr_t dma_handle;

void *cpu_addr = dma_alloc_coherent(
    dev, size, &dma_handle, GFP_KERNEL);
```

dma_handle给到设备，而cpu_addr则给到cpu. 

#### arm64
在这个架构下，Linux在调用dma_alloc_coherent时，其内部会首先访问buddy allocator或者CMA或者专用内存池，获取到对应的物理页。这些物理页根据是否有iommu的支持，可以是连续的或者离散的。下一步很自然地，我们需要返回一段连续的虚拟地址段给到CPU使用。

在ARM64下，有所谓的MT_NORMAL_NC属性，其全称是Normal Non-cacheable, 指的是某段内存不是可缓存的，CPU在对待这段内存时，对其的读写不应该经过缓存系统，而应该直接到达内存。

`kernel/dma/direct.c` 的 `dma_direct_alloc()` 中，典型的 remap 路径是：

```
pgprot_t prot = dma_pgprot(dev, PAGE_KERNEL, attrs);

arch_dma_prep_coherent(page, size);

cpu_addr = dma_common_contiguous_remap(
    page, size, prot, __builtin_return_address(0));
```

接着在 `kernel/dma/remap.c`：

```
vaddr = vmap(pages, count, VM_DMA_COHERENT, prot);
```

这里的 `vmap()` 将已经分配好的物理页映射到 vmalloc 虚拟地址空间。它不是调用 `vmalloc()` 再分配一批新的物理页。`dma_pgprot()` 对 non-coherent 设备会使用 `pgprot_dmacoherent()`，而 AArch64 将其定义为 `MT_NORMAL_NC`。

也就是说，这里会调用vmap在vmalloc段中建立一段虚拟地址段映射到dma buffer, 这一段的pte中携带特殊的标记，来指示CPU不经过缓存访问内存。现在，对于同一段物理内存，有两个有效映射，一个就是这里说的在vmalloc中新建的，一个则是内核启动初期就创建的线性映射段(通过kmalloc获取)。之所以保持两个，或者说要大费周章重新在vmalloc中建立映射，是为了不去破坏线性映射这个底层基础设施。
```
      CPU 虚拟地址                物理内存

  线性映射 (Cacheable)
       VA1 ──────────────────────────┐
				                     │
				                     ▼
				                  ┌──────┐
				                  │ PA 0 │
				                  │ PA 1 │
				                  │ PA 2 │
				                  └──────┘
				                     ▲
				                     │
       VA2 ──────────────────────────┘
  vmalloc (Non-cacheable)
```
