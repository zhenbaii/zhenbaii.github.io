理解设备树最重要的不是背属性名，而是先建立三个模型：

1. **设备树首先是一棵描述硬件关系的树**。父子关系决定某些局部语义，但不等于所有属性都会“继承”。
2. **每个能够给子节点编号或定位的节点，都可能定义一个自己的 namespace/domain**。这个 namespace 可以是 MMIO 地址、SPI 片选号、I²C 从地址、PCI 地址或中断号；它们不必是同一种地址。
3. **设备树中的数组没有自描述能力**。`<...>` 里的 cell 如何分组、每一项表示什么，必须由 DTSpec、总线规范或具体 binding 决定。

贯穿全文的核心问题是：

> 某个值属于谁的 namespace，由谁规定它的编码宽度，又通过什么规则与另一个 namespace 建立联系？

本文以 `/home/holo/Downloads/bcm2711.dtsi` 为主要例子，重点整理父子地址空间、`#xxx-cells`、`ranges`、`dma-ranges`、IOMMU、中断和 provider/consumer 模型。

## 1. 设备树的基本组织方式

### 1.1 节点、属性和树结构

一个典型节点如下：

```dts
uart2: serial@7e201400 {
    compatible = "arm,pl011", "arm,primecell";
    reg = <0x7e201400 0x200>;
    interrupts = <GIC_SPI 121 IRQ_TYPE_LEVEL_HIGH>;
    clocks = <&clocks BCM2835_CLOCK_UART>,
             <&clocks BCM2835_CLOCK_VPU>;
    status = "disabled";
};
```

节点头可以拆成：

```text
uart2: serial@7e201400
  │       │        │
  │       │        └─ unit-address：该节点在父 namespace 中的单位地址
  │       └────────── node-name：设备的通用类别
  └────────────────── label：DTS 源码中的符号名
```

- `label` 用于源码引用，例如 `&uart2`，一般由作者命名。
- `node-name` 应描述设备类别，并受通用命名规则和 binding 约束。
- `unit-address` 通常必须与 `reg` 第一项的地址部分一致；没有 `reg` 时通常不应带 `@...`。

`label` 不是硬件编号，也不是 DTB 中最终保存的节点身份。DTS 编译时，`&label` 会被解析为 phandle 引用；反编译 DTB 时常会看到数值形式的 `phandle = <...>`。

```text
DTS 源码                         DTB/反编译结果

gicv2: interrupt-controller...   phandle = <0x17>;
interrupt-parent = <&gicv2>;     interrupt-parent = <0x17>;
```

phandle 的数值只是设备树内部的节点引用 ID，本身没有类似 MMIO 地址、IRQ 号那样的硬件含义。

### 1.2 父子关系同时承担多种语义

设备树中的父子关系可能表达：

- 一个设备位于某条总线下面；
- 一个复杂 IP 内部包含若干功能块；
- 一个逻辑容器包含一组节点；
- 子设备的地址、片选或其他编号由父节点定义；
- 地址翻译需要从当前父节点逐层走向根节点。

但必须避免一个常见误区：

> **父子关系不等于普通编程语言中的属性继承。**

设备树没有“子节点自动拥有父节点所有属性”的通用规则。每个属性是否看直接父节点、是否沿祖先查找、是否通过 phandle 跳到另一个节点，都由该属性自己的规范决定。

### 1.3 一个节点可以同时是设备和下一级 bus/provider

`spi4` 对 `/soc` 来说是一个 MMIO 设备：

```dts
spi4: spi@7e204800 {
    reg = <0x7e204800 0x0200>;
    #address-cells = <1>;
    #size-cells = <0>;
};
```

但对它自己的子节点来说，它又建立了 SPI 地址域：

```dts
spi4: spi@7e204800 {
    #address-cells = <1>;
    #size-cells = <0>;

    sensor@0 {
        reg = <0>;       // CS0
    };

    flash@1 {
        reg = <1>;       // CS1
    };
};
```

因此：

```text
/soc 的视角：
spi4.reg = MMIO 基址 + 寄存器窗口长度

spi4 的视角：
sensor.reg = SPI chip-select 编号
```

同名的 `reg` 在不同 bus 下可以有完全不同的业务语义。真正稳定的规则只有：

> `reg` 描述当前节点在其**直接父节点所定义的 namespace** 中的位置或编号。

## 2. cell 是设备树数组的基本编码单元

### 2.1 一个 cell 是 32 bit

尖括号中的整数通常按 32-bit cell 编码：

```dts
reg = <0x0 0xfe000000 0x1000>;
```

这里有 3 个 cell，而不是天然存在的“地址、长度”三个字段。如何切分要看上下文。

一个 64-bit 数值常由两个 cell 按高位在前拼接：

```text
<0x00000001 0x23456789>

= 0x00000001_23456789
```

### 2.2 `<...>` 本身不携带字段边界

例如：

```dts
ranges = <0x7e000000 0x0 0xfe000000 0x01800000>;
```

不能仅凭肉眼认定它是四个独立字段。它的结构由当前节点和父节点的 cell 配置共同决定：

```text
child-bus-address  : 当前节点的 #address-cells
parent-bus-address : 父节点的   #address-cells
length             : 当前节点的 #size-cells
```

在 BCM2711 中：

```text
/soc: #address-cells = 1
/soc: #size-cells    = 1
/:    #address-cells = 2
```

所以一条 `/soc.ranges` 记录是：

```text
1 + 2 + 1 = 4 cells
```

严格切分为：

```text
< 0x7e000000 | 0x0 0xfe000000 | 0x01800000 >
  child addr     parent addr        length
    1 cell         2 cells          1 cell
```

## 3. `#address-cells` 和 `#size-cells`

### 3.1 它们描述 children，不描述节点自己

根节点中：

```dts
/ {
    #address-cells = <2>;
    #size-cells = <1>;
};
```

更准确的解释是：

> 根节点的直接子节点在用 `reg` 描述自己位于根地址空间中的资源时，地址占 2 个 cell，长度占 1 个 cell。

它不是在说“根节点自己的地址占两个 cell”。同理：

```dts
soc {
    #address-cells = <1>;
    #size-cells = <1>;
};
```

规定的是 `/soc` 的直接子节点如何编码 `reg`。

可以用箭头记忆：

```text
parent
├─ #address-cells
├─ #size-cells
│
└────规定────> child.reg
```

### 3.2 只看直接父节点，不沿祖先寻找

这是全文最重要的规则之一：

> **解析 `child.reg` 时，只使用 child 的直接父节点所定义的 `#address-cells/#size-cells`。**

错误理解：

```text
当前父节点没写
    ↓
自动向上找最近的“总线节点”
```

实际规则：

```text
当前父节点没写
    ↓
不继承祖先的值
    ↓
client 按规范采用默认值
    #address-cells = 2
    #size-cells    = 1
```

DTSpec 要求有子节点的节点显式给出这两个属性；默认值是缺失时的兼容处理，不是继承。

例如：

```dts
bus {
    #address-cells = <1>;
    #size-cells = <1>;

    container {
        // 没有显式写 #address-cells/#size-cells

        dev@1000 {
            reg = <0x1000 0x100>;
        };
    };
};
```

`dev.reg` 不会使用外层 `bus` 的 `1/1`。它的直接父节点是 `container`；若 `container` 缺失属性，client 按默认的 `2/1` 解释，那么 `reg` 应有 3 个 cell：

```dts
reg = <0x0 0x1000 0x100>;
```

如果希望继续使用 `1/1`，必须在 `container` 上重新明确声明：

```dts
container {
    #address-cells = <1>;
    #size-cells = <1>;

    dev@1000 {
        reg = <0x1000 0x100>;
    };
};
```

### 3.3 `#size-cells = <0>` 的意义

当父节点规定：

```dts
#size-cells = <0>;
```

子节点的 `reg` 中省略 size 部分。例如 SPI：

```dts
spi4 {
    #address-cells = <1>;
    #size-cells = <0>;

    sensor@0 {
        reg = <0>;
    };
};
```

这是因为 SPI 从设备通常只需给出 chip-select，不存在“占据从 CS0 开始、长度为 N 的地址区间”这一语义。

同样的模式也常见于 I²C：child `reg` 表示从设备地址，通常不需要 size。

### 3.4 include 不是属性继承

`bcm2711.dtsi` 开头包含：

```dts
#include "bcm283x.dtsi"
```

公共文件已经给 `/soc` 定义了：

```dts
#address-cells = <1>;
#size-cells = <1>;
```

而 `bcm2711.dtsi` 又把根节点改为：

```dts
/ {
    #address-cells = <2>;
    #size-cells = <1>;
};
```

最终展开后的树是：

```text
/
├─ #address-cells = 2
├─ #size-cells    = 1
└─ soc
   ├─ #address-cells = 1
   └─ #size-cells    = 1
```

这里 `/soc` 的值来自 include 后的节点合并，不是因为 `/soc` 从 `/` 继承了什么。阅读 `.dtsi` 时必须考虑 include 展开后的最终树。

## 4. `reg`：当前节点在父 namespace 中的位置

### 4.1 通用形式

`reg` 通常是任意数量的 `(address, length)` 对：

```text
reg = <address0 length0
       address1 length1
       ...>;
```

每一项的宽度由直接父节点决定：

```text
一项 reg 的 cell 数
    = parent.#address-cells
    + parent.#size-cells
```

当 `parent.#size-cells = 0` 时，`length` 被省略。

### 4.2 BCM2711 的 UART 例子

```dts
uart2: serial@7e201400 {
    reg = <0x7e201400 0x200>;
};
```

由于 `/soc` 是它的直接父节点，并且 `/soc` 使用 `1/1`：

```text
address = 0x7e201400
size    = 0x200
```

这仍然是 `/soc` namespace 中的地址，还不是 CPU 最终使用的根物理地址。要得到根地址，需要继续经过 `/soc.ranges`。

### 4.3 `reg` 不一定表示 MMIO

常见例子：

| 父 bus/domain | child `reg` 常见含义 |
|---|---|
| simple-bus / SoC bus | MMIO 地址和窗口长度 |
| SPI controller | chip-select 编号 |
| I²C controller | 从设备地址 |
| PCI host bridge | PCI BDF、地址空间类型等总线特定编码 |
| `/cpus` | CPU hardware ID，通常无 size |

因此不要把 `reg` 死记为“寄存器物理地址”。它首先是**父 bus binding 定义的地址/编号 specifier**。

## 5. `ranges`：相邻两级地址 namespace 的映射

### 5.1 基本含义

总线节点的 `ranges` 描述：

> 当前 bus 的 child address space 如何映射到该 bus 父节点的 address space。

每条记录是：

```text
<child-bus-address parent-bus-address length>
```

编码宽度：

```text
child-bus-address  → 当前节点的 #address-cells
parent-bus-address → 父节点的   #address-cells
length             → 当前节点的 #size-cells
```

这里的“bus”应理解为一个定义 child address domain 的节点，不一定对应一根肉眼可见的物理导线。但也不要把概念无限泛化：

- `ranges`/`dma-ranges` 描述的是设备树总线的物理或 bus 地址关系；
- CPU 虚拟地址由 CPU MMU 管理；
- IOVA 由 IOMMU 的动态翻译域管理；
- 它们都叫 address space，但不等于都由 `ranges` 建模。

### 5.2 BCM2711 的 `/soc.ranges`

```dts
ranges = <0x7e000000  0x0 0xfe000000  0x01800000>,
         <0x7c000000  0x0 0xfc000000  0x02000000>,
         <0x40000000  0x0 0xff800000  0x00800000>;
```

展开后：

| `/soc` child 地址范围 | `/` parent 地址范围 | 长度 | 用途 |
|---|---|---:|---|
| `0x7e000000..0x7f7fffff` | `0xfe000000..0xff7fffff` | `0x01800000` | BCM283x 通用外设 |
| `0x7c000000..0x7dffffff` | `0xfc000000..0xfdffffff` | `0x02000000` | BCM2711 特有外设 |
| `0x40000000..0x407fffff` | `0xff800000..0xffffffff` | `0x00800000` | ARM-local 外设 |

第一项的翻译公式为：

```text
parent = 0xfe000000 + (child - 0x7e000000)
```

因此 `uart2`：

```text
/soc reg address = 0x7e201400
offset           = 0x00201400
root/CPU PA      = 0xfe000000 + 0x00201400
                 = 0xfe201400
```

`pixelvalve1` 同理：

```text
/soc address = 0x7e207000
root PA      = 0xfe207000
```

而 `gicv2@40041000` 使用第三个窗口：

```text
/soc address = 0x40041000
offset       = 0x00041000
root PA      = 0xff800000 + 0x00041000
             = 0xff841000
```

### 5.3 空 `ranges`、缺失 `ranges` 和非空 `ranges`

三者不同：

```dts
ranges;            // 空属性
```

表示当前 child 地址空间与 parent 地址空间相同，不需要该级翻译。

```dts
// 完全没有 ranges
```

按照 DTSpec 表示没有定义 child 到 parent 的映射，不能擅自当作 identity mapping。个别操作系统代码可能为了兼容历史设备树有例外，但不能把兼容行为当成通用规范。

```dts
ranges = <...>;    // 非空
```

表示存在明确的一个或多个映射窗口。

### 5.4 多级总线要逐层翻译，不是只找最近一个 `ranges`

假设：

```text
device
  ↓ reg 属于 bus-B namespace
bus-B
  ↓ bus-B.ranges
bus-A
  ↓ bus-A.ranges
root
```

要把 `device.reg` 翻译到 root address，需要对每一级边界分别应用对应的 `ranges`。这不是把祖先某个 `ranges` “继承”给 device，也不是跳过中间节点去找最近一个存在的 `ranges`。

## 6. `dma-ranges`：设备 DMA 视角的固定地址窗口

### 6.1 与 `ranges` 相同的三元组编码

`dma-ranges` 同样编码：

```text
<child-bus-address parent-bus-address length>
```

cell 数量规则也相同：

```text
当前节点 #address-cells
+ 父节点 #address-cells
+ 当前节点 #size-cells
```

不同的是事务语义：

```text
ranges:
父侧的软件/CPU如何访问 child bus 上的资源

dma-ranges:
child bus 上的 DMA master 如何访问 parent 可见的内存地址
```

### 6.2 BCM2711 的固定 DMA 窗口

```dts
dma-ranges = <0xc0000000  0x0 0x00000000  0x40000000>;
```

切分为：

```text
child bus address = 0xc0000000
parent address    = 0x00000000_00000000
length            = 0x40000000
```

即：

```text
/soc DMA/bus 地址                  / 根物理地址

0xc0000000..0xffffffff  ────────>  0x00000000..0x3fffffff
```

如果设备发出：

```text
DMA address = 0xc1234567
```

固定窗口对应：

```text
root PA = 0x01234567
```

这条属性描述可达性和固定地址关系，但它本身：

- 不分配 DMA buffer；
- 不预留 DRAM；
- 不建立按设备区分的页表；
- 不提供越界保护或设备隔离；
- 不等于 DMA controller；
- 不等于 `#dma-cells`。

保留内存要看 `/reserved-memory` 等机制；为设备申请和映射 buffer 要通过操作系统 DMA API。

### 6.3 `ranges` 与 `dma-ranges` 是否共享 child space

对同一个 bus 节点而言，两者的 child 地址都以该 bus 的 address space 为坐标：

```text
/soc address space
├─ 0x4000....  ARM-local peripheral window   → ranges
├─ 0x7c00....  BCM2711 peripheral window     → ranges
├─ 0x7e00....  common peripheral window      → ranges
└─ 0xc000....  DMA-visible memory window     → dma-ranges
```

但“使用同一个 child address space 作为坐标”不代表它们是同一张映射表。二者服务于不同方向和类型的事务，可以给出不同的翻译关系。

### 6.4 Linux 查找 `dma-ranges` 的方式

这里必须区分规范语义和 Linux 实现行为：

- `dma-ranges` 属性仍然属于写出它的 bus 节点，并没有复制到后代节点；
- Linux 在为某个设备建立 DMA range map 时，会从设备向上查找第一个相关的非空 `dma-ranges`；
- DMA 地址的进一步翻译仍然沿 DMA parent/bus 层次处理。

因此可以说 Linux 会为设备**向上查找适用的 DMA range**，但不应说“子节点继承了 `dma-ranges` 属性值”。

## 7. `dma-ranges` 与 IOMMU

### 7.1 两者解决的问题不同

| 机制 | 核心问题 | 映射性质 | 隔离能力 |
|---|---|---|---|
| `dma-ranges` | bus DMA 地址与 parent 地址如何固定对应 | 静态窗口/偏移 | 无 |
| IOMMU | 某设备的 IOVA 此刻映射到哪些物理页 | 动态页表 | 有 |
| `iommus` / `iommu-map` | 某设备或 requester ID 应关联到哪个 IOMMU/specifier | 拓扑和身份描述 | 为页表选择提供依据 |

最短记忆：

```text
dma-ranges = 地址空间拓扑中的固定窗口
IOMMU      = 给 DMA 使用的可编程 MMU
```

`dma-ranges` 不是“简化版 IOMMU”。

### 7.2 无 IOMMU 的路径

```text
driver 调用 DMA API
        ↓
得到 device 可使用的 dma_addr_t
        ↓
设备发起 DMA transaction
        ↓
固定 bus/DMA 地址转换（可由 dma-ranges 描述）
        ↓
system physical address
        ↓
DRAM
```

在这种情况下，`dma_addr_t` 不保证等于 CPU PA。若存在固定偏移，它可能是设备侧 bus address。

### 7.3 有 IOMMU 的路径

```text
Device
  │  IOVA + Stream ID
  ▼
IOMMU
  │  按设备身份选择 translation context/domain
  │  按页表把 IOVA 翻译为下游地址
  ▼
SoC interconnect / bridge
  │  可能仍存在固定 bus translation
  ▼
system PA
  ▼
DRAM
```

实际芯片中 IOMMU 与固定 bus translation 的先后顺序由硬件拓扑决定，上图只强调两类转换可以同时存在。

### 7.4 Stream ID、IOMMU domain 和页表

三者不重复：

```text
Stream ID     → 这笔 DMA 请求是谁发出的
IOMMU domain  → 该设备被放入哪套 DMA 地址空间和权限环境
page table    → 这套环境中 IOVA 到 PA 的具体映射
```

完整链路：

```text
(Stream ID = 17, IOVA = 0x1000)
              ↓
IOMMU 根据 Stream ID 找到 Domain A
              ↓
Domain A page table
              ↓
IOVA 0x1000 → PA 0x81234000
```

多个 Stream ID 可以指向同一个 domain：

```text
SID 10 ─┐
SID 11 ─┼──> Domain A ──> Page Table A
SID 12 ─┘
```

这表示设备身份不同，但共享同一个 DMA 地址空间和权限集合。常见于：

- 同一复杂设备的多个 function；
- 同一多媒体流水线中的多个协作 IP；
- 同一虚拟机的多个直通设备；
- 硬件拓扑无法安全拆分的 IOMMU group。

`iommu_group` 与 `iommu_domain` 也不是一回事：

```text
iommu_group  → 能安全隔离的最小设备集合
iommu_domain → 当前分配给设备集合的 DMA 地址空间/保护域
```

## 8. `#xxx-cells` 与 provider/consumer 模型

### 8.1 统一结构

许多子系统用下面的形式描述资源提供者：

```dts
provider: controller@... {
    #xxx-cells = <N>;
};

consumer@... {
    xxxs = <&provider arg0 arg1 ... argN-1>;
};
```

其中：

```text
&provider       → 找到 provider 节点
#xxx-cells = N  → phandle 后有 N 个参数 cell
arg0...argN-1   → 参数具体含义由 provider binding 定义
```

`#xxx-cells` 只回答“specifier 有多长”，通常不单独回答“每一格是什么”。

### 8.2 常见对应关系

| consumer 属性 | provider 属性 | 常见参数语义 |
|---|---|---|
| `clocks` | `#clock-cells` | clock ID 等 |
| `resets` | `#reset-cells` | reset line ID |
| `dmas` | `#dma-cells` | DREQ/request selector 等 |
| `phys` | `#phy-cells` | PHY 实例、lane 等 |
| `pwms` | `#pwm-cells` | channel、period、flags 等 |
| `power-domains` | `#power-domain-cells` | power domain ID |
| `iommus` | `#iommu-cells` | Stream ID、context 信息等 |
| `thermal-sensors` | `#thermal-sensor-cells` | sensor index；也可能为 0 个参数 |
| `xxx-gpios` | `#gpio-cells` | pin、flags 等 |

这种对应不是靠字符串相似度自动推导。它由 DTSpec 或子系统 binding 定义，操作系统子系统再显式按该配对解析。

概念上，Linux 通用解析接口会同时接收两个名字：

```c
of_parse_phandle_with_args(np,
                           "phys",
                           "#phy-cells",
                           index,
                           &args);
```

所以并不存在如下通用语法魔法：

```text
看到属性名 yyy
    ↓
自动猜测应找 #xxx-cells
```

自定义 `#banana-cells` 在 DTS 语法上可能可以出现，但没有 binding 和 consumer 驱动约定，就没有公认语义。

### 8.3 BCM2711 的几个例子

#### DMA provider

```dts
dma: dma-controller@7e007000 {
    #dma-cells = <1>;
};

hdmi0: hdmi@7ef00700 {
    dmas = <&dma 10>;
    dma-names = "audio-rx";
};
```

解析为：

```text
&dma → 使用 BCM2835 DMA provider
10   → 一个由该 DMA binding 定义的请求/DREQ specifier
```

`#dma-cells = <1>` 不表示控制器只有一个 DMA channel，也不描述 DMA 地址宽度。

#### 0 参数 provider

```dts
thermal: thermal {
    #thermal-sensor-cells = <0>;
};

thermal-sensors = <&thermal>;
```

phandle 已经足以唯一指定资源，所以后面没有参数。

固定时钟也常见：

```dts
clk_27MHz: clk-27M {
    #clock-cells = <0>;
};
```

#### 一个节点同时提供多类资源

```dts
pm: watchdog@7e100000 {
    #power-domain-cells = <1>;
    #reset-cells = <1>;
};
```

该节点既可作为 power-domain provider，也可作为 reset provider。`#xxx-cells` 表示它对某一类 specifier 的编码契约，不限制一个节点只能扮演一种角色。

### 8.4 `#address-cells` 与普通 `#xxx-cells` 的差别

二者形式相似，但解析模型不同：

```text
#address-cells/#size-cells
  → 结构化父子地址关系
  → 由 child 的直接父节点规定 child.reg

#clock-cells/#dma-cells/#reset-cells/...
  → provider/consumer phandle + specifier 关系
  → 到 phandle 指向的 provider 节点读取
```

不要把所有 `#xxx-cells` 都理解为“继承给子节点”。

## 9. 中断模型为什么特殊

### 9.1 经典 `interrupts` 写法

```dts
/ {
    interrupt-parent = <&gicv2>;
};

uart2: serial@7e201400 {
    interrupts = <GIC_SPI 121 IRQ_TYPE_LEVEL_HIGH>;
};
```

逻辑上仍然需要 provider + specifier：

```text
provider  = &gicv2
specifier = <GIC_SPI 121 IRQ_TYPE_LEVEL_HIGH>
```

GIC 节点规定：

```dts
gicv2: interrupt-controller@40041000 {
    interrupt-controller;
    #interrupt-cells = <3>;
};
```

因此 `interrupts` 每 3 个 cell 为一项。三个 cell 的含义由 GIC binding 规定，而不是由 `#interrupt-cells = 3` 自身规定。

### 9.2 `interrupt-parent` 的祖先查找

`interrupt-parent` 是本文范围内最典型的“会向上解析”的机制。

规范模型是：

1. 节点若显式写 `interrupt-parent`，就使用该 phandle；
2. 若没写，其 interrupt parent 默认为设备树父节点；
3. 若该父节点不是中断域根，继续沿中断树/设备树关系解析，直到找到拥有 `#interrupt-cells` 的合适父节点或经过 `interrupt-map` 映射。

因此从使用效果上，可以理解为设备会找到最近适用的显式 `interrupt-parent`：

```text
/
├─ interrupt-parent = &gicv2
└─ soc
   └─ uart2
      └─ interrupts = <...>
```

`uart2` 最终使用 `gicv2`。但更精确的说法不是“所有属性都从根继承”，而是：

> 中断规范为 `interrupt-parent` 单独定义了父链解析规则。

节点可以覆盖它：

```dts
hdmi0: hdmi@7ef00700 {
    interrupt-parent = <&aon_intr>;
    interrupts = <0>, <1>, <2>, <3>, <4>, <5>;
};
```

此时 HDMI 的 1-cell specifier 要按 `aon_intr.#interrupt-cells = <1>` 解释，而不是按根 GIC 的 3-cell 格式解释。

### 9.3 `interrupts-extended` 更像普通 phandle-array

```dts
interrupts-extended =
    <&gicv2 GIC_SPI 80 IRQ_TYPE_LEVEL_HIGH>;
```

它把 provider phandle 和 specifier 写在一起，形式更接近：

```dts
dmas = <&dma 5>;
clocks = <&clk 3>;
resets = <&rst 2>;
```

`interrupts-extended` 还允许同一设备的不同中断连接不同 controller。

### 9.4 `interrupt-map` 是中断 namespace 之间的翻译

PCI host 等 interrupt nexus 节点可能定义：

```dts
interrupt-map-mask = <...>;
interrupt-map = <child-unit-address
                 child-interrupt-specifier
                 &parent-controller
                 parent-unit-address
                 parent-interrupt-specifier>;
```

它不是普通属性继承，而是把一个中断 domain 的 specifier 映射到另一个中断 domain。

### 9.5 多个控制器节点共享一个 GIC IRQ

BCM2711 中多个 UART 都写：

```dts
interrupts = <GIC_SPI 121 IRQ_TYPE_LEVEL_HIGH>;
```

多个 SPI controller 也共享 GIC SPI 118。设备树表达的是它们最终连接到同一个 GIC interrupt specifier。软件处理共享 level IRQ 时，通常需要让每个候选 handler 检查自己的状态寄存器：

```text
公共 IRQ 到来
   ↓
检查 UART2 status → 是我的则处理并清除
检查 UART3 status → 是我的则处理并清除
检查 UART4 status → ...
```

只要仍有某个 source 保持 pending，level-triggered 公共线就会继续保持有效。设备树本身不会描述驱动内部如何区分来源，这由硬件状态寄存器和驱动实现完成。

## 10. 哪些字段会向上找，哪些不会

“继承”一词容易把四种机制混为一谈：

| 机制 | 例子 | 本质 |
|---|---|---|
| 直接父节点决定格式 | `reg` ← parent 的 `#address-cells/#size-cells` | 只看一层，不递归 |
| 显式 phandle 跳转 | `clocks = <&clk ...>` | 直接找指定 provider |
| 沿祖先/父链解析 | `interrupt-parent`、Linux 查适用的 `dma-ranges` | 属性专门定义的查找算法 |
| 逐级 namespace 翻译 | 多级 `ranges`、`interrupt-map` | 每一级都参与，不是继承 |

### 10.1 本文涉及属性的查找矩阵

| 属性或关系 | 去哪里取规则/值 | 会不会向祖先找最近值 | 备注 |
|---|---|---|---|
| `child.reg` 的编码 | child 的直接父节点 `#address-cells/#size-cells` | **不会** | 缺失时使用规范默认 `2/1`，不是继承 |
| 当前节点的 `#address-cells/#size-cells` | 当前节点本身 | **不会** | 它们规定当前节点的 children |
| `ranges` | 当前 bus 节点本身 | **不会找一个来继承** | 地址到 root 时逐级应用每一层映射 |
| `dma-ranges` | 所属 bus 节点 | Linux 会从设备向上找适用项 | 是查找/组合，不是属性值复制 |
| `interrupt-parent` | 当前节点；缺失则按中断父链上行 | **会** | 最终还可能经过 `interrupt-map` |
| `interrupts` | 当前节点本身 | **不会继承中断列表** | 编码宽度取解析出的 interrupt parent 的 `#interrupt-cells` |
| `interrupts-extended` | 当前节点，每项内含 phandle | **不会** | 每项直接指定 provider |
| `clocks` / `resets` / `dmas` / `phys` / `iommus` / `power-domains` | 当前 consumer 属性中的 phandle | **不会** | 到被引用 provider 直接读取对应 `#xxx-cells` |
| provider 的 `#clock-cells` 等 | phandle 指向的 provider 节点 | **不会沿 provider 祖先找** | specifier 长度必须由 provider/binding 明确给出 |
| `compatible` / `status` / `reg-names` / `clock-names` / `dma-names` | 当前节点 | **不会** | 普通局部属性 |

最安全的阅读原则是：

> 除非 DTSpec 或具体 binding 明确规定父链查找，否则不要假设属性会继承。

## 11. 用 BCM2711 节点串起这些概念

### 11.1 `avs-monitor` 与 `thermal`

```dts
avs_monitor: avs-monitor@7d5d2000 {
    compatible = "brcm,bcm2711-avs-monitor",
                 "syscon", "simple-mfd";
    reg = <0x7d5d2000 0xf00>;

    thermal: thermal {
        compatible = "brcm,bcm2711-thermal";
        #thermal-sensor-cells = <0>;
    };
};
```

这里：

- `avs-monitor.reg` 由其直接父节点 `/soc` 的 `1/1` 解释；
- `thermal` 没有 `reg`，所以不存在其地址该按谁解释的问题；
- `thermal` 是 thermal sensor provider，`#thermal-sensor-cells = 0` 表示消费者只需引用 `&thermal`，无需附加 sensor index；
- `simple-mfd` 表示该寄存器块内部包含可作为子设备建模的功能块。

### 11.2 PL011 是 UART controller，但通常不是地址总线

```dts
uart2: serial@7e201400 {
    compatible = "arm,pl011", "arm,primecell";
    reg = <0x7e201400 0x200>;
};
```

PL011 本身就是 UART controller。节点名使用 `serial@...`，并不表示它不是控制器。

UART 通常是点对点链路，没有 SPI chip-select 或 I²C 从地址那样的天然多从设备 address namespace，所以传统 UART 节点通常不需要 `#address-cells/#size-cells`。使用 serdev 描述蓝牙、GNSS 等 UART 子设备时，child 也通常不是靠 `reg = <地址>` 区分。

### 11.3 SPI controller 同时是 MMIO device 和 bus

```text
/soc namespace
  └─ spi4@7e204800
       reg = MMIO address + size
       │
       └─ SPI namespace
            ├─ sensor@0 → CS0
            └─ flash@1  → CS1
```

这正是“同一个节点面对父节点是 device，面对子节点是 bus”的典型例子。

### 11.4 Pixel Valve 属于显示流水线

```text
framebuffer / DRM planes
          ↓
HVS：合成与缩放
          ↓
Pixel Valve：扫描和显示时序
          ↓
HDMI / DSI / DPI / VEC encoder
          ↓
display
```

`pixelvalve1@7e207000` 是显示控制流水线中的时序输出单元，概念上接近 DRM CRTC，而不是 UART/SPI 那样的通用通信控制器。它的中断可用于 vblank 等显示时序事件。

### 11.5 `emmc2bus` 为什么单独成一层

```dts
emmc2bus: emmc2-bus@fe000000 {
    compatible = "simple-bus";
    #address-cells = <2>;
    #size-cells = <1>;
    ranges = <...>;
    dma-ranges = <...>;

    emmc2: mmc@7e340000 {
        reg = <0x0 0x7e340000 0x100>;
    };
};
```

eMMC2 被放进独立 bus，是为了让 firmware 能针对不同 SoC revision 修改这一层的 DMA constraint。这个例子说明：增加一层 bus 不只是排版；它会建立新的 child address/DMA domain，并允许该层拥有独立的 `ranges` 和 `dma-ranges`。

### 11.6 PCIe 的 3-cell address 不能按普通 64-bit 地址硬拆

```dts
pcie0: pcie@7d500000 {
    #address-cells = <3>;
    #size-cells = <2>;
    ranges = <0x02000000 0x0 0xf8000000
              0x6 0x00000000
              0x0 0x04000000>;
};
```

PCI 的 3-cell address 是 bus-specific 编码，其中高 cell 还包含地址空间类型、prefetch 等标志。不能简单把三个 cell 当作 96-bit 纯数值地址。阅读特殊 bus 的 `reg`/`ranges` 时，除 cell 数外还必须查对应 bus binding。

## 12. DTS 是否“能编译”不等于描述正确

约束大致有三层：

```text
DTS grammar / dtc parser
  → 语法是否可解析

dtc semantic checks
  → unit-address 与 reg、cell 数等结构是否可疑
  → 很多问题可能只是 warning

dt-schema + device binding
  → compatible 对应节点是否满足该设备的正式约束
```

例如：

```dts
foo@1234 {
    reg = <0x5678 0x100>;
};
```

`@1234` 与 `reg` 第一地址不一致，规范上是错误描述，但某些 dtc 检查可能只给 warning。类似地，自定义属性即使语法可通过，也不代表操作系统或 binding 理解它。

因此：

> `dtc` 能生成 DTB，只证明输入基本可编码；不能证明硬件语义、binding 和地址拓扑都正确。

## 13. 阅读设备树的实用顺序

遇到一个陌生节点时，建议按以下顺序：

1. **先定位最终树结构**：检查 include、同名节点补充和 `&label` 修改。
2. **识别直接父节点**：当前 `reg` 属于谁的 namespace？
3. **读取直接父节点的 cell 配置**：不要向上猜测 `#address-cells/#size-cells`。
4. **按 bus binding 切分 `reg`**：确认 address 是否真的是 MMIO 数值。
5. **逐级应用 `ranges`**：需要 CPU/root 地址时，逐层翻译。
6. **单独分析 DMA 视角**：查看适用的 `dma-ranges`、DMA mask、IOMMU 关联。
7. **看到 phandle-array 就找 provider**：再读取 provider 的 `#xxx-cells` 和 binding。
8. **处理中断的特殊父链**：区分 `interrupt-parent + interrupts`、`interrupts-extended` 和 `interrupt-map`。
9. **最后看 names 属性**：如 `reg-names`、`clock-names`、`dma-names`，把多项资源与驱动中的用途对应起来。
10. **用 dt-schema 核验**：不要只以 dtc 能否编译为准。

## 14. 最终心智模型

可以把整套机制压缩成下面这张图：

```text
                         Device Tree
                              │
          ┌───────────────────┼────────────────────┐
          │                   │                    │
          ▼                   ▼                    ▼
   父子地址结构         provider/consumer       中断拓扑
          │                   │                    │
 parent cells            phandle + args      interrupt parent
          │                   │                    │
     child.reg           #xxx-cells          #interrupt-cells
          │                   │                    │
       ranges             binding 语义        interrupt-map
          │
   root/system PA

设备 DMA 另有一条视角：

Device DMA address / IOVA
          │
          ├─ IOMMU：动态映射、权限、隔离
          │
          └─ dma-ranges：bus 与 parent 的固定 DMA 窗口
                         │
                         ▼
                    system PA / DRAM
```

最后记住四句话：

1. **`reg` 永远先属于直接父节点定义的 namespace。**
2. **`#address-cells/#size-cells` 不从祖先继承；缺失时的 `2/1` 是默认值，不是最近祖先值。**
3. **`#xxx-cells` 只给 specifier 定长，consumer 与 provider 的配对及每个 cell 的含义由规范/binding 定义。**
4. **只有属性自己的规范明确允许时才沿父链查找；不要发明通用的“最近父节点继承”规则。**
