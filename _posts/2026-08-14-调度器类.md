调度器类是Linux早期所引入的一个机制。在引入这个vtable之前，Linux要在一个``
`scheduler()`logic中塞下应对不同payload场景的逻辑，并用if分支对他们做区分。比如说，有实时性要求比较高的任务，如UI刷新，也有要求比较低的任务，如批处理任务。对于实时性要求高的任务，应当进入优先级较高的调度器类型中运行。而批处理任务等则可以进入公平调度类中调度。

为了把不同调度器类的逻辑解耦，Linux便引入了所谓的`struct sched_class` vtable. 他本质上就是一个由回调指针组成的结构体。不同的调度器类型都去注册里面的方法，而上层的`scheduler()`
中只需要调用`vtable`中提供的接口，而不需要知道各个调度器的实现细节，因而实现了比较好的解耦。下面是这个`vtable`的一些比较重要的回调：
```c
// kernel/sched/sched.h
struct sched_class {
	/* enqueue a task. */
    void (*enqueue_task)(struct rq *rq, struct task_struct *p, int flags);
	/* dequeue a task. */
    bool (*dequeue_task)(struct rq *rq, struct task_struct *p, int flags);
	/* logic of picking out a task. For real-time scheduler, it may depends
	 * on the priority of the task. For fair scheduler, it may depends on the 
	 * time of the task already spent on the CPU.S
	 */
    struct task_struct *(*pick_task)(struct rq *rq, struct rq_flags *rf);
    /* pick out next task to be scheduled */
    struct task_struct *(*pick_next_task)(struct rq *rq,
                                          struct task_struct *prev,
                                          struct rq_flags *rf);
    void (*put_prev_task)(struct rq *rq, struct task_struct *p,
                          struct task_struct *next);
    void (*set_next_task)(struct rq *rq, struct task_struct *p, bool first);

    void (*task_tick)(struct rq *rq, struct task_struct *p, int queued);
    void (*prio_changed)(struct rq *this_rq, struct task_struct *task,
                         int oldprio);
    void (*update_curr)(struct rq *rq);
    // ... (more hooks)
};
```

可以看到，这个类基本上就定义了作为一个调度器需要向上层暴露的所有接口。上层只需要调用这些接口，而不用关心调度器内部的实现，实现了解耦。

Linux大致上把调度器分为了以下五类：
##### stop(stop_sched_class)
**File**: `kernel/sched/stop_task.c` 
这类任务的优先级是最高的，可以抢占任何位于其他类型的任务。这类任务通常是内核线程，不会和用户态直接产生交互。他用于一些特殊的，需要独占本地cpu的场景，如cpu核心的热插拔，负载均衡等等。

##### rt(rt_sched_class)
**File**: `kernel/sched/rt.c`
即实时调度类，用于一些对时间比较敏感的任务，比如UI刷新任务。通常会有两类算法用于这个调度器类：
-  SCHED_FIFO: 一直执行任务，直到一个优先级更高的任务醒过来，没有时间限制
- SCHED_RR: 即round robin算法。同优先级的任务会被划入等长的时间片中，每个时间片由一个任务占有运行。高优先级的仍然会抢占低优先级的。相比SCHED_FIFO，它可以避免同优先级的其他任务被饿死。
属于这类调度的任务有99个优先级，分别是`1-99`. 
内核为了防止RT类型的任务一直运行不睡眠，导致其他序列的任务无法得到运行，规定了RT类型的任务在每个1秒的时间窗口中，最多可以使用95%的时间窗口。其余5%要让给其他序列的任务。

##### fair(fair_sched_class)
**File**: `kernel/sched/idle.c`
即公平调度类。他会有如下策略：
-  SCHED_NORMAL: 用户态程序默认都是这个
-  SCHED_BATCH:
-  SCHED_IDLE
CFS和EEVDF调度器就属于这个类型。

##### idle(idle_sched_class)
**File**: `kernel/sched/idle.c`
即空闲任务。每个CPU的空闲线程都属于这个类。只有当其他类型的队列中都没有可以执行的任务时，才会执行到这个类的任务。通常这个任务是`cpu_idle_loop()`, 通常会执行对应架构的低功率指令，如ARM的`wfi`, x86的`hlt`. 

##### deadline(dl_sched_class)
**File**: `kernel/sched/deadline.c` 
即deadline类。属于这一类的任务，会向内核注册自己的以下信息：
- **Runtime（运行时间，`sched_runtime`）**：任务在一个周期内实际需要占用的 **CPU 执行时间**。
- **Deadline（截止时间，`sched_deadline`）**：任务必须完成执行的最大允许时间（相对于周期起点）。
- **Period（周期，`sched_period`）**：任务释放新实例的时间间隔。
- **硬性约束**：必须满足 `Runtime <= Deadline <= Period`。同时，所有 Deadline 任务的 `Runtime/Period` 总和**不能超过系统预留的 CPU 带宽**（默认上限为 95%，留出 5% 给内核和普通进程）。

他是优先级仅次于stop的调度类。内核保证注册在此类的任务会在规定的时间内得到执行。它常常用于一些硬实时且时间边界比较清晰的任务：
- **自动驾驶/ADAS**：传感器数据融合和决策控制周期（如 10ms 硬周期）。
- **工业以太网与运动控制**：PLC 循环周期（如 1ms 精确同步）。
- **高端音视频处理**：需要恒定帧率且不允许抖动的 8K 编解码。
- **航空航天与无人机飞控**：飞行姿态解算。

下表展示了rt和dl的区别。

| 维度        | **`rt_sched_class` (实时)** | **`dl_sched_class` (限期)**    |
| :-------- | :------------------------ | :--------------------------- |
| **核心保证**  | 低延迟（优先响应），但无时间上限保证        | 确定性（保证在 Deadline 前完成），有数学硬保证 |
| **优先级机制** | 静态优先级（1~99），数字大优先         | 动态优先级（谁的 Deadline 更早谁先跑）     |
| **准入控制**  | 无（CPU 可被 RT 任务占满导致系统卡死）   | 有严格准入（总带宽超限则创建失败，返回 `EBUSY`） |
| **过载保护**  | 无（长期高优先级 RT 会饿死其他任务）      | 有 CBS 节流（任务超时会被强制暂停，保护系统）    |
| **抢占关系**  | 可被 `stop` 和 `dl` 抢占       | 仅可被 `stop` 抢占（可抢占 `rt`）      |

这五个调度器类也是有优先级之分的。高优先级的调度器类的任务总是可以抢占低优先级的调度器类的任务。他们的优先级如下：
```
stop > deadline > real time > fair > idle
```
