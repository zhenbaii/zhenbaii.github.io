在计算系统中，有几个名词经常出现：ISA, 机器码，ABI， API， 编译器/库，源码。在现代计算机体系下，他们是有明确的层级划分的：
```
硬件 <- ISA <- 机器码程序 <- 编译器/库 <- API <- 用户源代码
```

### ISA(Instruction Set architecture)

ISA, 又称作指令集架构，完整规定了一颗CPU暴露给上层软件(就是操作系统了)的能力，包含多个维度：支持的指令集，内存访问，寄存器，中断，异常，特权级等等。他是CPU和操作系统的一份契约，操作系统必须正确遵循这份契约，才可以正确驱动这颗CPU。 比如对于下面的指令：、
```
add x10, x11, x12
```

ISA必须明确定义：
- `add` 是什么操作
- 它有几个操作数
- 哪个是目标寄存器
- 哪几个是源寄存器
- 运算是多少位
- 溢出时怎么办
- 指令对应怎样的机器码编码

比如，ISA还会规定这个架构有什么寄存器。比如RISCV下，就有32个整数寄存器，32个浮点寄存器，32个向量寄存器(如果开启了V扩展)。同时，还会规定哪些寄存器承担特殊用途，比如CSR寄存器组。以及，还会规定发生特权级切换等事件时，这些寄存器的值会如何变化。

ISA还会规定其支持什么指令，比如RISCV的通用指令：
```
add
sub
and
or
xor
sll
srl

ld
sd

beq
bne

jal
jalr
```

ISA还要规定指令的编码格式。我们在用汇编写程序时，这些汇编指令最终是要变成机器码的。CPU怎么知道这个机器码对应什么指令什么操作，操作数在哪，几个操作数呢？靠的就是指令的编码格式。简单来说，ISA还需要规定某串bits怎么被解读为正确的指令(如果这个bit串合法)。

ISA还要规定特权级，比如RISCV下的M-mode, S-mode, U-mode. 不同的特权级下，可以执行的代码和允许访问的寄存器也是不同的，这是操作系统实现安全隔离的关键。通常固件会运行在M-mode, 可以理解为他们就是一份裸机代码，用于初期的启动和一些安全策略，比如看门狗。而操作系统是特权级稍低一些的综合管理软件，用来高效地使用CPU和内存这些资源。

前面我们讲到，ISA是一份接口契约，其告诉上层软件这个CPU具备什么能力。反过来讲，只要CPU的实现符合这份契约，那么就可以运行遵守了同一份契约的软件。这就是所谓的**架构不等于实现**。 
同样实现了RV64 ISA的两个CPU, 他们内部的实现可以完全不同，比如可能流水线级不同，一个多发射一个单发射，一个不带分支预测一个带分支预测等等，只要他们的对外表现遵循那份契约。
简而言之，**ISA=CPU对外承诺什么，Microarchitecture=CPU内部如何实现这个承诺**。这个实现甚至不一定需要是硬件，比如QEMU。

在RISCV中，ISA是模块化的，通常是在RV64后面加后缀，表示支持了什么扩展。常见的扩展有：
```
M = Multiply/Divide
A = Atomic
F = Single-precision Floating Point
D = Double-precision Floating Point
C = Compressed Instructions
```

### ABI
讲完了ISA，即**CPU承诺自己有什么功能**， 接下来我们还要讲所谓的ABI， 即Application Binary Interface, 中文名叫做应用二进制接口。、
ABI解决的是软件之间的接口契约问题。我们来看一个比较简单的例子：
```rust
fn add(a: usize, b: usize) -> usize {
    a + b
}
let c = add(10, 20);
```

这是一个十分简单的函数调用， 源代码层面一目了然。但是从CPU层面，他只认识ISA框架下的东西，即寄存器和指令。因此，上面的源代码，最终是要变成机器码，也就是指令+寄存器访问的形式的。这个时候就有一个问题：源代码中的参数列表，要放到哪些寄存器？其返回值又该放到哪个寄存器？如果没有一个统一的规定，编译器就不知道如何把这个源代码翻译成机器码，因为机器码中不仅是指令，还有操作数。于是，ABI就承担了这个职责。他规定了源码到机器码的一些调用约定。比如，对于RISCV，常见的ABI约定就有：
```
x10 = a0 = 第一个参数
x11 = a1 = 第二个参数
x12 = a2 = 第三个参数
...
x17 = a7 = 第八个参数

a0 = 返回值
a1 = 返回值

callee-saved register,  caller-saved register
栈的安排
```

除了架构层面的ABI， 还有和操作系统，平台，语言相关的ABI。比如对于函数符号的修饰，不同语言就有不同的约定：
-  C： 一般不修饰名称。add()函数出现在符号表里就叫做add.
-  Rust & C++： 一般会修饰名称，添加一些前缀.
还有结构体在内存中的布局：alignment, padding, 结构体大小等。

操作系统相关的ABI，包括系统调用号的定义，发起系统调用时，参数的定义等等。
总之，ABI涵盖了非常多的东西。但凡涉及到两个软件模块之间的对接问题，都可以称作ABI。只要大家符合ABI约定，就可以对接成功。

我们以musl为例子，就可以比较好地理解ABI的概念。musl是一个glibc的实现，相当于是一个用户态库。里面提供了大量的API使用，包括线程相关的库，以及大量的cli命令。这些库本质上都是对底层OS的系统调用的封装，也就是都是用户态的程序。由于Linux是使用范围最广泛的开源操作系统，因此里面所有涉及到系统调用的部分，都是遵循Linux syscall ABI的。换句话说，musl中的程序期望按照LInux syscall ABI的约定发起系统调用。

如果我们编写一个新的OS，并且想要把按照Linux ABI编写的程序移植过来，或者说复用大量在Linux平台上一些成熟的工具链，那么有两种路径：
-  修改这些库和工具链的胶水层，使其适配我们OS自己的ABI约定
-  让自己的OS的系统调用ABI和Linux的兼容

显然，第二条路更加的方便。
