# Reproducing the Issue

## Zve32x

Zve32x is a standard subset of the RISC-V Vector extension intended for resource-constrained embedded and edge devices.

- It supports 8-, 16-, and 32-bit **integer** vector elements and the corresponding arithmetic, load/store, mask, and reduction instructions.
- It provides integer vector operations only.
- It allows a VLEN as small as 32 bits and also supports larger widths such as 64 and 128 bits.
- It is available on both RV32 and RV64.

Zve32x sets a minimum `VLEN` of 32 bits. The full `V` extension requires at least 128 bits. `VLEN` is the width of a single vector register, while `ELEN` is the maximum width of a vector element.

| Parameter | Meaning | How to read it |
| --- | --- | --- |
| **ELEN** | Maximum vector element width supported by the implementation | How wide can a single element be? |
| **VLEN** | Width of one architectural vector register, in bits | How many bits fit in a register such as `v0` or `v1`? |

## Reproduction and Call Chain

To reproduce the `check_size_align` assertion below, configure QEMU with `--enable-debug-tcg` before building it. This is a build-time option, not an option to pass to `qemu-system-riscv64` at runtime.

Enable `Zve32x` with the following settings.

```
VLEN = 32 BIT
ELEN = 32 BIT
```

Run a program containing these two instructions.

```
vsetivli zero, 1, e32, m1, tu, mu   # SEW = 32, LMUL = 1, vl = 1
vredsum.vs v3, v2, v1               # Add the active elements of v2 to v1[0] and store the result in v3[0]
```

The following command reproduces the issue.

```
/path/to/qemu-system-riscv64 \
  -M virt \
  -accel tcg \
  -cpu rv64,v=false,zve32x=true,vlen=32,elen=32 \
  -smp 1 \
  -m 128M \
  -bios none \
  -nographic \
  -monitor none \
  -serial none \
  -kernel /path/to/rv64-minimal.elf
```

QEMU aborts with this assertion failure.

```
qemu-system-riscv64: ../tcg/tcg-op-gvec.c:56: check_size_align: Assertion `(maxsz & max_align) == 0' failed.
Aborted (core dumped)
```

The test reaches the assertion along this call chain.

```
trans_vredsum_vs
  → opivv_trans
  → tcg_gen_gvec_4_ptr
  → simd_desc(oprsz=4, maxsz=4, data)
  → check_size_align
  → Assertion failure (QEMU exits with SIGABRT)
```

The failure occurs as the RVV translator passes `oprsz` and `maxsz` to TCG's GVEC code. The four-byte `maxsz` is what trips the assertion.

# Root Cause

This section assumes a working knowledge of GVEC.

### Generic GVEC and Instruction-Specific Helpers

The RVV frontend takes the following paths when it translates a vector instruction into TCG IR.

```
Decoding and translation
─────────────────────────────────────────────────────────
Guest machine code (RVV instruction)
  ↓
decode_insn32
  │  Match the encoding and extract fields such as register numbers and vm
  ↓
trans_*                              ← some generated by macros
  │  Check whether the instruction and operands are legal
  │  Select fn, the function that emits the RVV helper call for this SEW
  │  For example, fns[s->sew] = gen_helper_vadd_vv_w
  │  The call to fn comes later
  │
  ├─ The instruction offers a generic GVEC path, as vadd.vv/vx/vi do
  │    ↓
  │  do_opivv_gvec / do_opivx_gvec / do_opivi_gvec
  │    │
  │    ├─ The conditions for generic GVEC are met
  │    │    Unmasked, vstart=0, vl=VLMAX, logical group size ≥ 8 bytes,
  │    │    and !(s->vta && s->lmul < 0)
  │    │    ↓
  │    │  tcg_gen_gvec_add / adds / addi
  │    │    │
  │    │    ├─ Select the inline implementation
  │    │    │    → Emit vector or scalar TCG IR
  │    │    │
  │    │    └─ Select the helper specified by .fno
  │    │         → Prepare the helper arguments and descriptor
  │    │         → Call the corresponding gen_helper_*
  │    │           For example, gen_helper_gvec_add32
  │    │
  │    └─ The conditions fail
  │         → Emit the RVV helper call as shown in [H]
  │
  └─ The instruction uses an instruction-specific helper, as vredsum.vs does
       ↓
     opivv_trans
       → Go directly to [H]


[H] Emitting an RVV helper call
─────────────────────────────────────────────────────────
Prepare the call according to the operand form.

  vv form
    The else branch of do_opivv_gvec, or opivv_trans
      │  Build data with fields such as VM, LMUL, VTA, and VMA
      ↓
    tcg_gen_gvec_4_ptr
      │  Build the descriptor with simd_desc(oprsz, maxsz, data)
      │  Prepare pointers to vd, v0, vs1, and vs2, along with env
      └─ Call fn(...)

  vx / vi form
    opivx_trans / opivi_trans
      │  Build data and the descriptor directly
      │  Prepare pointers to vd, v0, and vs2
      │  Prepare the scalar or immediate operand, along with env
      └─ Call fn(...)
           fn has type gen_helper_opivx *
           gen_helper_opivx names the function type

In these examples, fn(...) calls a macro-generated function,
such as gen_helper_vadd_vv_w(...).
    ↓
  tcg_gen_call6
    ↓
  tcg_gen_callN
    ↓
  Emit INDEX_op_call

IR generation for the instruction is complete.
```

The main decision in the translation flow is shown below.

```
trans_*
  │
  ├─ Offers a generic GVEC path, as vadd.vv/vx/vi do
  │    │
  │    ├─ Conditions met
  │    │    → Inline TCG IR (.fni4 / .fni8) or GVEC helper (.fno)
  │    │
  │    └─ Conditions fail
  │         → Emit the instruction-specific helper call
  │
  └─ Uses an instruction-specific helper directly
       → Emit the instruction-specific helper call
```

**The translator uses generic GVEC when the instruction offers that path and meets its conditions. Otherwise, it emits a call to the instruction-specific helper.**

Most RVV instructions with a generic GVEC path use similar conditions, including this check.

```
vl_eq_vlmax == TRUE
```

The `do_opivv_gvec` implementation shows how the check is used.

```c
static inline bool
do_opivv_gvec(DisasContext *s, arg_rmrr *a, GVecGen3Fn *gvec_fn,
              gen_helper_gvec_4_ptr *fn)
{
    if (a->vm && s->vl_eq_vlmax && !(s->vta && s->lmul < 0)) {
        /* Generic GVEC path. */
        gvec_fn(s->sew, vreg_ofs(s, a->rd),
                vreg_ofs(s, a->rs2), vreg_ofs(s, a->rs1),
                MAXSZ(s), MAXSZ(s));
    } else {
        /* Instruction-specific helper path. */
        uint32_t data = 0;

        data = FIELD_DP32(data, VDATA, VM, a->vm);
        data = FIELD_DP32(data, VDATA, LMUL, s->lmul);
        data = FIELD_DP32(data, VDATA, VTA, s->vta);
        data = FIELD_DP32(data, VDATA, VMA, s->vma);
        tcg_gen_gvec_4_ptr(vreg_ofs(s, a->rd), vreg_ofs(s, 0),
                           vreg_ofs(s, a->rs1), vreg_ofs(s, a->rs2),
                           tcg_env, s->cfg_ptr->vlenb,
                           s->cfg_ptr->vlenb, data, fn);
    }
    finalize_rvv_inst(s);
    return true;
}
```

In QEMU, the flag combines three conditions.

```
vl_eq_vlmax =
    (env->vstart == 0) &&
    (env->vl == vlmax) &&
    (maxsz >= 8);
```

The final condition is what matters for a four-byte register. Before choosing an execution path, the translator obtains this flag from the translation block (TB) state.

When preparing that state, `riscv_get_tb_cpu_state` computes `maxsz` from the current vector configuration.

```c
int8_t lmul = /* LMUL encoding extracted from env->vtype */;
uint32_t vsew = /* SEW encoding extracted from env->vtype */;

uint32_t vlmax = vext_get_vlmax(cpu->cfg.vlenb, vsew, lmul);
uint32_t maxsz = vlmax << vsew;   /* Logical register group size in bytes. */

/* The group size helps determine vl_eq_vlmax. */
bool vl_eq_vlmax = (env->vstart == 0) &&
                   (vlmax == env->vl) &&
                   (maxsz >= 8);
```

For instructions that check `vl_eq_vlmax`, the generic GVEC path therefore requires **a logical register group of at least eight bytes**.

Whole-register moves such as `vmv1r.v` use a different condition. The table lists both sets of translation entries.

| Translation entries | Check for `vl_eq_vlmax` |
| --- | --- |
| Regular operations, moves/broadcasts, and gathers (44 entries) | Yes. This requires a logical group of at least 8 bytes. |
| Whole-register moves `vmv1r/2r/4r/8r.v` (4 entries) | The branch checks `vstart_eq_zero` only. |

### check_size_align(oprsz, maxsz, ofs)

The assertion comes from `check_size_align()`. The function runs inside `simd_desc()` when it constructs a descriptor. The generic GVEC path also calls it before choosing an implementation such as `.fni4`, `.fni8`, or `.fno`.

```c
static void check_size_align(uint32_t oprsz, uint32_t maxsz, uint32_t ofs)
{
    uint32_t max_align;

    switch (oprsz) {
    case 8:
    case 16:
    case 32:
        tcg_debug_assert(oprsz <= maxsz);
        break;
    default:
        tcg_debug_assert(oprsz == maxsz);
        break;
    }
    tcg_debug_assert(maxsz <= (8 << SIMD_MAXSZ_BITS));

    max_align = maxsz >= 16 ? 15 : 7;
    tcg_debug_assert((maxsz & max_align) == 0);
    tcg_debug_assert((ofs & max_align) == 0);
}
```

This check applies the following alignment rules to `maxsz`.

| Range of `maxsz` | Alignment requirement |
| --- | --- |
| Less than 16 bytes | A multiple of 8 bytes |
| At least 16 bytes | A multiple of 16 bytes |

```
oprsz ∈ {8, 16, 32}
    oprsz must be ≤ maxsz

For all other oprsz values
    oprsz must equal maxsz
```

For nonempty vector operations, the valid `maxsz` values are as follows.

```
8, 16, 32, 48, 64, …, 2048
```

Eight bytes is the smallest supported size. The diagram shows where each translation path applies the check.

```
RISC-V translator chooses a path
    │
    ├─ Generic GVEC path
    │    ↓
    │  check_size_align(...)
    │    ★ A four-byte size trips the assertion here
    │    ↓
    │  Select an implementation
    │    │
    │    ├─ .fniv / .fni8 / .fni4
    │    │    → Emit inline IR
    │    │
    │    └─ .fno
    │         → simd_desc(oprsz, maxsz, data)
    │              → Calls check_size_align(...) again
    │         → Emit a call to the generic helper
    │
    └─ Instruction-specific RVV helper path
         → simd_desc(oprsz, maxsz, data) builds the descriptor
              → check_size_align(...)
                   ★ The original 4/4 case trips the assertion here
         → Emit a call to the RVV helper
```

On the instruction-specific helper path, the assertion comes from descriptor construction. A count of the RVV translation entries shows that most build a descriptor for their helper call and use the size of a single physical vector register for `maxsz`.

| How the RVV helper call is emitted | Entries | Sizes |
| --- | ---: | --- |
| Through a `tcg_gen_gvec_N_ptr()` wrapper | **182** | 178 use `vlenb/vlenb`. The 4 whole-register moves use `vlenb × N` for both sizes. |
| The translator builds the descriptor and calls `gen_helper_*` | **220** | All use `vlenb/vlenb`. |
| Paths with no descriptor | **5** | Three `vset*` instructions and two vector-to-scalar reads. |

This makes descriptor construction a potential point of failure for much of the RVV frontend.

On the **generic GVEC path**, most entries use `vl_eq_vlmax` to keep groups smaller than eight bytes from reaching `check_size_align()`.

The generic path for `vmv1r/2r/4r/8r.v` uses `vstart_eq_zero` on its own. At VLEN=32, `vmv1r.v` operates on four bytes and trips the size assertion in `check_size_align()`. The two-, four-, and eight-register moves operate on 8, 16, and 32 bytes respectively.

### Where the Assertion Fires

- **Instruction-specific RVV helper calls.** Most entries pass `oprsz=maxsz=vlenb=4`. The call to `check_size_align()` inside `simd_desc()` then trips the assertion. The original `vredsum.vs` reproduction takes this path.
- **Generic GVEC expansion.** Most entries use `vl_eq_vlmax` to rule out groups smaller than eight bytes. Whole-register moves use a separate check. With `vstart=0`, `vmv1r.v` passes `4/4` directly to the generic GVEC expander, where `check_size_align()` fails before the expander chooses an inline implementation or `.fno`.

Whole-register move helpers use `vlenb × N`, so the size at each call site matters. To determine whether a path trips the assertion, check the **actual values of `oprsz` and `maxsz`** passed to the function.

The descriptor assertion applies only to paths that construct a descriptor. The generic GVEC path validates the sizes before it reaches `.fno`.

# Patch Implementation and Rationale

## Encoding and Decoding Changes

The original encoding for `MAXSZ` is `(maxsz / 8) - 1`, which decodes as `(field + 1) * 8`. The smallest size that formula can represent is eight bytes. The patch assigns field value `2` to four bytes. That value previously decoded to 24 bytes, which fails the existing requirement that maximum sizes of at least 16 bytes be multiples of 16.

In the `OPRSZ` field, value `2` already means “equal to MAXSZ.” The patch reuses this encoding within the existing field width.

```text
simd_desc(4, 4, data)
    MAXSZ field = 2, now represents four bytes
    OPRSZ field = 2, still means “equal to MAXSZ”
    ↓
simd_maxsz(desc) = 4
simd_oprsz(desc) = simd_maxsz(desc) = 4
```

`simd_desc()` handles `maxsz=4` as a special case and uses a debug assertion to require `oprsz=4`. Other sizes follow the original checks and encoding. `simd_maxsz()` decodes field value `2` as four bytes, which the existing `simd_oprsz()` logic then returns. All previously valid sizes retain their encodings, and the field layout still provides 22 bits for `DATA`.

The new encoding is limited to `4/4`. Mixed sizes such as `4/8` are outside its scope, and the existing alignment rules apply elsewhere.

## Cases Outside the Patch’s Scope

- At VLEN=32 with `vstart=0`, `vmv1r.v` still hits the `check_size_align()` assertion in the generic GVEC expander.
- Directly expanded whole-register loads and stores still access eight bytes at a time, exceeding the size of a single four-byte register.
- The big-endian branch of `vmvr_v` copies data on eight-byte boundaries. Its four-byte case still needs a fix and validation.
